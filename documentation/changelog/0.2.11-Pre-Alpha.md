## CHG-0780 · 2026-11-27 · A turn owns its own run state: one scope per turn, keyed by run, released by one finalizer

Type: Code (refactor; no change for the owner)
Event: Agreement and delivery
Scope: `packages/service` (`work/turnScopes.ts` and `work/allowances.ts` new; `work/turnRunner.ts`, `work/threads.ts`, `work/turns.ts`, `work/lifecycle.ts`, `work/approvals.ts`, `work/approvalContracts.ts`, `work/promptPolicy.ts`, `work/askOwner.ts`, `core/execution.ts`, `core/executionTypes.ts`, `core/endpoints.ts`, `core/index.ts`, `harness/harnessProcesses.ts`, `connectors/calls.ts`, `connectors/gateway.ts`, `connectors/connectors.ts`)
Summary: a turn's run state was spread over seven thread-keyed stores in six modules (the active map, the router's running map, the pool's entries and starting maps, Code Mode, the connector snapshot, the one-time approvals, and the session id written at the turn's end), and `turnRunner.ts` released three of them in an `Effect.ensuring` it had to keep in step. A second run on one thread (the Companion mention, thread-messaging blueprint) would have shared all seven: ending it would clear the main turn's one-time approvals, connector snapshot and interrupt route and overwrite its session id. Now a turn opens a scope (`makeTurnScopes(...).open`) under a run key. The thread's main run is keyed by the thread's id, so everything that asks by thread id (the tool server, steering, an interrupt) reaches it unchanged; a side run has a key of its own. Each store is keyed by the run key (`TurnRequest.runKey`, absent for a main run, read by the router and the pool; `Endpoints.holdCodeMode`/`releaseCodeMode`; `ConnectorCalls.takeSnapshot(thread, names, runKey)`; `Approvals` allowances, moved to `allowances.ts` to keep `approvals.ts` under the size limit, `endTurn(runKey)`). One finalizer, run when the scope ends however the turn ends, spends the run's approvals, drops its snapshot, forgets its route, and releases a side run's Code Mode, and clears nothing of another run. The thread's state and session are written only through a main scope: `lifecycle.endTurn` takes a `MainTurnScope`, and `completeTurn` takes the scope and skips that write for a side one. A side run's process neither replaces nor closes the main run's, and only a main run's process wakes the thread.
Defaults taken: the main run's key is the thread's id (so no stored or wire name changes and the existing tests pass unchanged); `TurnRequest.runKey` is optional and defaults to the thread's id; a thread's Code Mode setting stays after its main turn ends (its kept harness process outlives the turn), a side run's is released; the scope covers the harness run only, as the old cleanup did, so `wake` still admits the next turn as soon as the harness returns; `withdraw(thread)` (an interrupt or stop) still clears every run of that thread's one-time approvals; a side run's process never wakes the thread; the failure path (`recordTurnFailure`, `failTurn`) is not yet scope-guarded, because the removed-account refusal happens before any scope exists and a side run's failure record belongs with the Companion mention.
Reason: the owner's request of 2026-11-27 to make the Companion mention cheap (architecture audit 2026-11-27, candidate 2).
