## CHG-0699 · 2026-11-24 · The `!` terminal starts where the agent works, in a worktree it made itself

Type: Code
Event: Delivery
Scope: Conversation terminal, workspace attachment

Summary: The conversation `!` terminal now starts in the git worktree the agent moved into on its own (Claude Code's `EnterWorktree`, `git worktree add`, a `cd` in a shell command), not only in a worktree the service made for an own-copy thread.
No harness reports its current folder, so the service infers it from the thread's own tool calls: `cd` and `pushd` (relative paths from the previous folder, quotes, `cd a && cmd`), `git worktree add` with `git -C` and its options, `EnterWorktree` and `ExitWorktree`.
The service keeps the last candidate in a new `threads.working_folder` column (migration 0075) and, when the thread is read, offers it as the optional `ThreadView.workingFolder` only if it still exists as a real path and is a linked worktree of the workspace's own repository.
A folder that was removed, left the repository, or is the workspace's own checkout is none, and so is a thread in a scratch folder.
The app's `terminalFolderOf` prefers `workingFolder`, then the own copy, then the workspace, so an older paired host that sends no field behaves as before.
Reason: The owner wanted the terminal to open where the agent works, as an Outlore feature and not as an instruction to agents, and decided that the folder is inferred from tool calls because no harness reports its cwd (2026-11-24).
Validation: Focused tests cover the inference (`packages/service/test/work/folderMoves.test.ts`), the stored and checked folder against real git repositories (`packages/service/test/work/workingFolders.test.ts`), and the app's choice (`apps/app/test/conversation/terminalFolder.test.ts`).
Only Claude Code's and OpenCode's `Bash` calls are read; Codex and the ACP providers do not report shell commands as tool calls, so their threads keep today's starting folder.
The `EnterWorktree` input shape is unverified against a live run (the tool is refused in `-p` mode), and a pane already open keeps the shell it started until it is restarted.

## CHG-0705 · 2026-11-24 · Stdio-only ACP harnesses get Outlore's thread tools through a stdio-to-HTTP MCP bridge

Type: Code
Event: Delivery
Scope: Host service, ACP harnesses, desktop packaging

Summary: ACP harnesses whose `initialize` answer omits `mcpCapabilities.http`, such as Antigravity CLI `agy 1.5.16`, now receive a stdio MCP server entry that runs `packages/service/src/harness/acpMcpBridge.mjs`.
The bridge forwards newline-delimited JSON-RPC over stdio to the thread's local HTTP MCP tool server, handling JSON and SSE replies, HTTP 202 notifications, `mcp-protocol-version` negotiation and aborting in-flight SSE when stdin closes.
`noToolServerInstructions` is appended only when a session truly gets no tool server, and the desktop app ships the bridge as an unpacked resource (`OUTLORE_ACP_MCP_BRIDGE`).
Reason: ACP mandates stdio MCP support while HTTP is optional, so stdio-only harnesses could not call `open_thread`, `report_result` or `request_approval` after CHG-0691. See ADR 0005 and the T3 Code and Paseo research note.
Validation: New `acpMcpBridge.test.ts`, updated `acpProvidersHarness.test.ts` and desktop `packaging.test.ts`, and a live check against `agy 1.5.16` recorded in ADR 0005 (it spawned the bridge, listed tools, called one over SSE and ended the turn).
