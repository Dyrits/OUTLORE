## CHG-0725 · 2026-11-25 · OpenCode runs through the one ACP module, and Antigravity takes the starting context as its system prompt

Type: Code
Event: Delivery
Scope: Provider harnesses, ACP (OpenCode, Antigravity)

Summary: `opencode.ts` no longer holds a copy of the ACP loop: OpenCode is a dialect of `acpHarness.ts`, so session start and reopen, the lost-session fallback, the read loop, permissions, usage and file edits are the module's, and a fix to one reaches every ACP harness.
What stays OpenCode's own are hooks and data: the sandboxed launch (`openCodeLaunch.ts` now hands the module the command to start and how its containment is judged, instead of starting the process itself), the refusal re-prompt (OpenCode cancels its whole prompt when a permission is refused, so the module keeps each refusal and tells it in a new prompt of the same turn), the permission question judged by where the action runs (an edit naming no file, an executor not seen inside the sandbox, or a thread allowed to run without the sandbox asks as an escape), the tool server and starting context given through its configuration and a file, the model and effort set without being listed first, and the context read from the last prompt's token total.
Antigravity now takes the starting context as `_meta.antigravity.systemPrompt.append` on `session/new` when the agent advertises it (`agy` 1.5.16 does), so its first prompt is the owner's message alone; an agent that does not advertise it, and every other provider, still gets the context in the first prompt.
Small differences the unification brings, each pinned by a test: every ACP harness counts `cachedWriteTokens` as cache creation (only OpenCode did), answers a permission request that offers no matching option with "cancelled" instead of an option id the agent never offered (only OpenCode did), and a permission request's tool call is the session's earlier updates with the request's own fields on top (the earlier update alone was read before); OpenCode now sends the shared `initialize` (with `clientInfo`) and also reports the context window when its `usage_update` carries one; a turn that was interrupted counts as interrupted even if the agent's last answer was not "cancelled".
OpenCode still shows no `ToolCall` event of its own (the other ACP harnesses do); this is kept on purpose, as a dialect switch, until the owner decides.
Open, recorded and not decided: whether to set `SSH_CONNECTION` for Antigravity CLI 1.5 so that per-profile token storage works (T3 Code sets `SSH_CONNECTION="127.0.0.1 0 127.0.0.1 0"` to make the CLI honour `AGY_ACP_FORCE_FILE_STORAGE`); it needs a signed-in live check and stays in the backlog.
The account budget card that labelled nine harnesses "OpenCode" was already fixed by CHG-0697 and needed nothing here.
Reason: Architecture audit candidate H2 (2026-11-24) left OpenCode as the third copy of the ACP loop after CHG-0708, and the research note on T3 Code and Paseo (2026-11-24) supplied the Antigravity system-prompt finding.
References: [Architecture, Harnesses and accounts](../architecture.md), [the research note](../research/acp-antigravity-t3code-paseo-2026-11-24.md), [ADR 0008](../architecture-decision-record/0008-drive-harness-tools-directly.md).
Validation: See [the verification record](../verification/2026-11-25-opencode-through-the-acp-module.md).

## CHG-0726 · 2026-11-25 · Antigravity steers a running turn with a second prompt

Type: Code
Event: Delivery
Scope: Provider harnesses, ACP (Antigravity)

Summary: The shared ACP module now reads `agentInfo.version` from `initialize` (`acpAgentVersionOf` and `acpVersionAtLeast` in `acpSession.ts`) and adds a dialect option `steersWithPromptFrom`.
Antigravity sets `steersWithPromptFrom: "1.5.0"` in `antigravityProvider.ts`: when `agy` reports `>= 1.5.0`, steering a running turn sends a second `session/prompt` instead of refusing and waiting for the next turn, and never sends `session/cancel` (which kills Antigravity's running subagents and background commands).
`acpPrompt.ts` tracks the turn's running prompt flight (`AcpPromptFlight`, `steerAcpPrompt`), starts each prompt synchronously so a later `session/cancel` always follows it on the wire, ends the flight on the last prompt's answer, and reports superseded prompt answers as they arrive.
`acpHarness.ts` delivers steered messages to the pooled-process layer (`turn.deliver`), closes each superseded prompt's draft reply, and sums prompt usage across the flight while keeping the last prompt's context reading.
Interrupt behavior stays on Outlore's existing path for Antigravity and every other ACP harness: `session/cancel` is sent without aborting the prompt reader, `harnessProcesses.ts` waits up to `interruptGraceMillis` (10 seconds) for `session/prompt` to settle, keeps the process alive when it confirms cancellation, and closes it only on timeout.
Checking T3 Code (`pingdotgg/t3code` at `93a7cfe745ac784e559c727e4eccd90929dfd169`) confirms that `cancelBehavior: "wait-for-prompt"` matches what Outlore's pooled-process layer already does (including retiring the process on cancel timeout), that `preserveRuntimeOnSettledInterrupt` applies only to T3's post-settle background-command continuation (which Outlore's ACP harness does not have), and that no other ACP agent in T3 Code accepts a second `session/prompt` as steering (Grok and Kiro use proprietary extension methods, and standard ACP defines no mid-turn prompt steering).
Permission handling (`acpPermissions.ts`) and usage helpers (`acpSession.ts`) were split out of `acpHarness.ts` so the file shrinks below the 512-line hard limit (495 lines).
Reason: The owner approved Antigravity mid-turn steering and keeping the process alive on interrupt as the first batch from the T3 Code comparison, and asked to verify whether steering is Antigravity-specific or global across ACP harnesses.
References: [the research note](../research/acp-antigravity-t3code-paseo-2026-11-24.md), [Work in progress](../work-in-progress.md).
Validation: 38 tests in `acpProtocol.test.ts` (including 8 new tests covering steering on `>= 1.5.0`, process reuse after steering, refusal on `< 1.5.0` or missing version, interrupting a steered turn and keeping the process, refusing steer after prompt completion, leaving other ACP harnesses unsteerable, and version parsing/comparison) and the related harness suites pass against the configurable ACP stand-in; Biome and workspace typecheck pass.

## CHG-0728 · 2026-11-25 · One declarative account isolation for every harness, and no "+ Add account" where it is refused

Type: Code
Event: Delivery
Scope: Provider harnesses (native and ACP), Workshop Providers section; no provider is newly enabled and no provider's account support changes

Summary: Batch 1 of the multi-account plan replaces `configVariable`, `supportsAddedAccounts` and the ACP `StateHomeRule` with one `AccountIsolation` value (`accountIsolation.ts`): `{ kind: "computerOnly"; reason }` or `{ kind: "directory"; envOf(accountDirectory); needsConfiguredHome? }`, with `singleVarIsolation(variable, needsConfiguredHome?)` and `computerOnlyIsolation(reason)` as the two constructors.
Each harness declares it once, in its catalog facts or its ACP definition, and every surface derives from it: `accountEnvironmentOf` (Claude, Codex, OpenCode, Vibe and Pi launches, sign-in commands, plan limits and probes), `refusesAddedAccounts` (`addAccount`'s refusal), the new `HarnessInfo.supportsAddedAccounts`, and the ACP launch, sign-in command, model probe and sign-in read.
The same six providers stay `computerOnly` (Antigravity, Cline, Copilot, Cursor, Devin, Muse) and the same six stay `directory` (Claude `CLAUDE_CONFIG_DIR`, Codex `CODEX_HOME`, OpenCode `XDG_DATA_HOME`, Vibe `VIBE_HOME`, Pi `PI_CODING_AGENT_DIR`, Hermes `HERMES_HOME` with `needsConfiguredHome`), each with the variable and value it had.
`acpLaunchOf`, `acpSignInOf`, `makeAcpProviderHarness`, `probeAcpProviderModels` and `readAcpProviderSignIn` now take the definition and the account's `configDirectory` and resolve argv and environment per call; the frozen `AcpProviderProfile` (which carried `stateHomeEnv` and `needsConfiguredStateHome`) is gone, and `acpAdapterOf` no longer resolves a launch once at construction.
A Gemini-style home that the argv binds is a separate `pinnedHome: { resolve, variable }` on the definition, so Antigravity keeps CHG-0676's guarantee (one home in the flag and the variable for launch, probe, sign-in and plan limits) while its isolation stays `computerOnly`.
`HarnessDefinition.readSignIn` takes the `configDirectory` instead of a pre-built environment (`readVibeSignIn` no longer reads `VIBE_HOME` back out of one), Hermes's special case in `harnesses.ts` is deleted (`probedModelsOf` takes the folder, and a `needsConfiguredHome` isolation refuses a probe or a turn without one), and Pi's two hand-rolled `PI_CODING_AGENT_DIR` spreads use `accountEnvironmentOf`.
`HarnessInfo` gains the optional `supportsAddedAccounts` (an older host omits it, which reads as true), filled in `readHarness`; the Workshop hides **+ Add account** when it is false and says "Uses this computer's sign-in only." (`canAddAccount` in `providerRules.ts`).
Reason: The owner approved a clean multi-account architecture across providers; an audit found the refusal flag, the state-home rule, the single-variable helper and five surfaces each deciding the account's environment on their own, with the Workshop offering Add account on providers that refuse it.
Deviations from the proposed design, each with a reason:
- `pinnedHome` is separate from `AccountIsolation`, because `computerOnly` carries no environment and Antigravity must keep resolving and passing its Gemini home today; when its isolation becomes `directory`, `envOf` adds the account's variables beside it.
- A `computerOnly` isolation ignores any account folder, also for a pinned home, so a stale account row can never move a provider off the computer's sign-in; the old code honored it for a pinned home in the sign-in and probe, and ignored it in the adapter, which no account row could reach.
- Muse's unverified `MUSE_HOME` is dropped with its `configVariable`: nothing guesses its environment, and a pre-refusal Muse account row (if any exists) now signs in with the computer's environment rather than an unproven variable.
- A directory-isolated ACP provider probed without a folder now reads the computer's own sign-in, not an empty temporary home; only Hermes (refused without a folder) and the unregistered Kimi definition were directory-isolated ACP providers, so no registered provider's behavior changes.
- No decision record: the type is internal, one file, and reversible; the choices above are recorded here.
References: [provider accounts](../capabilities/provider-accounts/specifications.md#accounts), [ADR 0011](../architecture-decision-record/0011-accounts-as-harness-folders.md), [backlog](../backlog.md), [Work in progress](../work-in-progress.md).
Validation: new `accountIsolation.test.ts` (12 tests: the derived environment, the roster's six and six, a multi-variable pinned-home ACP definition giving launch, probe and sign-in one argv and one environment for an account and the pinned home alone for the computer, a computer-only provider ignoring a stale folder, and Hermes's refusal and probe through the registry), `providerRules.test.ts` for `canAddAccount`, a `harnesses.test.ts` check that `ListHarnesses` reports `supportsAddedAccounts` false for the six and true for the rest, and the ACP, hygiene, Antigravity, probe and definition suites moved onto the definition API; Biome and workspace typecheck pass; no provider turn or sign-in was run.
