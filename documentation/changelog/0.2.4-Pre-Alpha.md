# Changelog: 0.2.4-Pre-Alpha

## CHG-0676 · 2026-11-24 · Antigravity reads the computer's own sign-in

Type: Code
Event: Delivery
Scope: Provider harnesses, Antigravity

Summary: Outlore no longer sets `WSL_DISTRO_NAME` when it starts Gemini (Antigravity). Any value of that variable makes the CLI keep its tokens in a file under the Gemini home instead of the system keychain. Before this change, Outlore's launches and model probes looked only in that file. The sign-in window runs `agy acp --login` without the variable and stores the login in the keychain, so every launch answered "Authentication required" and the harness stayed not connected after a successful sign-in. The upstream OpenBot launch sets the variable, and Outlore had copied it.
Reason: The owner signed in to Antigravity from the Workshop, and the CLI reported the account as logged in, but Outlore still showed Antigravity as not connected (2026-11-24).
Validation: Live, against Antigravity CLI 1.5.16 with the owner's login, outside the sandbox: initialize then `session/new` on the pinned argv returned `-32000 Authentication required` with `WSL_DISTRO_NAME=Outlore` and returned a session with six models without the variable. The CLI's own log names the cause: "Using file-based token storage because WSL environment detected". The Antigravity, ACP profile and harness tests pass (35); the probe test now expects no `WSL_DISTRO_NAME`. The running desktop app was not checked; the fix reaches it in the next build.

## CHG-0677 · 2026-11-24 · Typing in a conversation terminal no longer reports a service failure

Type: Code
Event: Delivery
Scope: Conversation terminal, host service

Summary: The service answered typing, resizing, and closing a conversation shell with no value. The wire contract allows only `null` for those requests, so encoding each answer failed after the shell had already received the keys. The terminal kept working, but every keystroke and resize showed "The service failed unexpectedly." in the panel. These requests now answer `null`. The fault had been present since the shells moved into the host service (CHG-0644). The service's own tests called the handlers directly and never encoded their answers.
Reason: The owner reported that the terminal still showed "The service failed unexpectedly." after `git pull` in the 0.2.3-Pre-Alpha app (2026-11-24).
Validation: A new test in `packages/service/test/work/terminals.test.ts` sends each request as a wire frame through the real service and requires a Success frame. Before the fix, resize and close returned the owner's exact Failure frame; afterward, all 14 terminal tests passed when run outside the sandbox with a real pseudo-terminal, including typing into an open shell, and the frame tests passed. The running desktop app was not checked; the fix reaches it in the next build.

## CHG-0678 · 2026-11-24 · Opening a quest keeps an open realm pane open

Type: Code
Event: Agreement and delivery
Scope: Conversation panes

Summary: Opening a quest folded the realm's channel pane behind its notch every time (CHG-0613), even when the owner had it open. A quest opened from the realm's channel, from the sidebar, from a quest's list, or a new quest started there now opens beside the channel, and a channel the owner pressed back open beside one quest stays open when another quest opens. A channel that was folded, or not on screen, still opens folded.
Reason: The owner asked that opening an existing or a new quest while the realm panel is open should not close it (2026-11-24). "Panel real" was read as the realm's channel pane.
References: [Conversation panes specification](../capabilities/conversation-panes/specifications.md#the-window).
Validation: Two new tests in `apps/app/test/shell/paneChain.test.ts` cover the open channel's layout and weights; the 185 shell tests, Biome, and the seven workspace typechecks pass. The running desktop app was not checked.
