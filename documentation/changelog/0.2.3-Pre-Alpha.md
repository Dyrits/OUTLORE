## CHG-0671 · 2026-11-23 · Stop nesting buttons in the sidebar and log unexpected request failures

Type: Code
Event: Agreement and delivery
Scope: Sidebar, service request answers

Summary: A sidebar row is a plain view whose own button (its title, label, or name) lies beside the fold mark, the hover accessory, and the creation buttons, so no button holds another. This ends the dev warning `In HTML, <button> cannot be a descendant of <button>` that the Realms and Borderlands headings, the realm rows, and the quest, errand, and Ritual rows raised each time the window loaded. `react-native-web` draws `accessibilityRole="button"` as a real `<button>`, and the rows had nested these since the sidebar's first build (2026-11-11); the React and `react-native-web` versions are unchanged since 2026-11-05. `useRowActions` also returns `isHighlighted` (hovered or pressed) and `pressProps` so the whole row keeps its hover and press shade, and the row's own button takes the width between the others (`rowMain`). The service answers a request that ends in a defect or an interruption, which carries no typed failure, with the unchanged message "The service failed unexpectedly." and now logs the request's kind and the cause first, so the next occurrence shows what failed.
Reason: The owner saw the React error in the dev terminal and asked for a fix (2026-11-23). The cause of "The service failed unexpectedly." could not be found because `answerFrame` dropped it.
Validation: A new test in `packages/service/test/remote/frames.test.ts` answers a dying handler and checks both the unchanged answer and the logged request and cause. The service test passes, `bun run check` and `bun run typecheck` pass, and a throwaway desktop instance showed no console warning and no `<button>` inside a `<button>` on the shell, the quest, the Workshop, and Hosts, with hover, fold, creation, selection, and keyboard focus working as before.
Evidence: [Nested sidebar buttons verification](../verification/2026-11-23-nested-sidebar-buttons.md).

## CHG-0672 · 2026-11-23 · Make Islands the default layout, add the Slate theme, and color Black & white's states

Type: Code
Event: Agreement and delivery
Scope: Look, window frame, themes, panes

Summary: Islands (CHG-0668) is no longer a theme. It is the default **layout** of the desktop window in every theme, and the Look card's **Layout** choice offers it beside **Flat**, the frame the app had before. Its **Canvas**, **Gap**, **Radius**, and **Lift** settings no longer depend on the theme, show while the layout is Islands, and apply at once; the canvas (the theme's `ground` where it is darker than the islands, else the page shaded or lightened), its glow (the new palette tokens `glowCool` and `glowWarm`), the island's surface and hairline, and the shadow (the theme's ink in the light look, black in the dark) all come from the theme's palette. The settings stay in the browser's storage under `outlore:islands`, which now also holds `layout`; the Canvas, Gap, Radius, and Lift saved by the earlier build are read as the layout's, and a missing layout is Islands. Each open conversation pane (the realm's, the quest's or Ritual's, and the errand's) is its own island with the gap between them, a notch between two panes sits across the gap, a notch on a pane's outer edge takes the island's own color and leaves its hairline open there so it reads as cut into the pane, and the edge between them still drags; a screen without panes, such as the Workshop, is one island. The colors of the islands prototype became the new theme **Slate**; a stored theme `islands` opens Slate. **Black & white** keeps greys for surfaces, text, borders, and the canvas but its state colors are colored again: danger, success, warning, Waiting's violet, Resting's yellow, Attention's marker, and a new blue for Underway (the palette tokens `underway`, `underwaySoft`, and `underwayText`, which equal the accent in the other themes), so the activity indicator, the usage rings and graph, the Mana bar, and the status dots read as in the other themes. A phone, a narrow window, and the Android app keep the flat layout.
Reason: The owner said Islands should be the default layout and not a theme, that the prototype's colors should be a new theme, that Black & white should be black and white but keep color for the activity indicator, the usage circle, and the like, and that the realm, quest or Ritual, and errand panes should each be an island (2026-11-23).
Validation: Tests of the layout settings (including the earlier build's saved text), the canvas for every theme and look, the theme list and the stored `islands` name, the notch reach across a gap, the palettes' contrast, and Black & white's colored and grey tokens pass, as do lint and the seven typechecks. A throwaway desktop instance showed each theme in both looks with the Islands layout, the flat layout, a quest with an errand and a Ritual, a folded errand pane, the pinned and the overlay sidebar, Black & white's colored indicators, and the Look card changing the layout live.
Evidence: [Islands layout verification](../verification/2026-11-23-islands-layout.md).
