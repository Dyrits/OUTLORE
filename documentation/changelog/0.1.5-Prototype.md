# Changelog: 0.1.5-Prototype

## CHG-0292 · 2026-11-15 · Narrow windows and phones: a full-screen menu, Chronicler as the whole screen, Back to the parent

Type: Code
Event: Agreement and Delivery
Scope: App shell, phone web app

Summary: The owner reported that on a phone only the Guild Hall and Chronicler could be reached, asked for a menu fitted to a phone that opens full screen, for the same consideration of the sidebar and Chronicler, and for Back not to always return to the Guild Hall. Below 820 px the app now has a top bar whose menu button (a cross while open) opens a full-screen menu of large rows: Guild Hall, Realms, Borderlands, Rituals, Craft, Library, Lore, Archive, Reserves, Charter, Workshop, the current place marked. Quests are not listed in it; Realms opens the grouped overview and Borderlands its quest list. Choosing a row closes the menu. Chronicler takes the whole content area on a narrow window (its restore button closes it; opening it is not remembered), replacing the floating card and the corner pill. A quest's Back goes to its parent view (its realm's quests, or the Borderlands), not the Guild Hall. The Workshop, the archive, and All lore lose their Back to the Guild Hall wherever a top bar leads elsewhere. The spending line is left off the narrow bar. The recommended menu shape was an agent choice: the owner's question went unanswered twice, and their later comment asked for the same treatment for the sidebar and Chronicler.
Reason: The sidebar existed only on wide windows and narrow ones relied on each screen's own links, so most places were unreachable; the earlier drawer ran under the window buttons and kept the dense sidebar tree.
References: [backlog](../backlog.md) (narrow windows and the mobile version), [verification](../verification/2026-11-15-mobile-navigation.md), `archiveParentOf` in `apps/app/src/shell/navigation.ts`.
Validation: The owner's requests in this thread. Biome, workspace typecheck, and app tests (415 passed, 8 skipped) pass; a 390 × 780 drive in a throwaway window passes. No test is new: the menu and Back are checked by the drive only.
Evidence: Not checked: a real phone or its safe areas, the native build, light and Gild looks, a menu filled with quests (it lists none), a realm's quest's Back (only a Borderlands quest was driven), other screens at phone widths (the Workshop's cards are still cramped), and starting a quest on a phone: the quest lists have no "new quest" button on a narrow window, so only Chronicler starts one. The sidebar rows' hover-only buttons are untouched on wide windows.

## CHG-0293 · 2026-11-15 · The Dock icon bounces for a new summons

Type: Code
Event: Agreement
Scope: Desktop app, action approval

Summary: The owner asked that the app icon on the Mac wiggle up and down when a thread waits for them (Summons). When a new open question appears, the app calls the desktop bridge's new `requestAttention`; the main process validates the sender as it does for `setTheme` and, only while the window is not focused, calls `app.dock.bounce("critical")`, which repeats until the owner returns. It stops when the window gains focus. A browser has no Dock and does nothing. The existing no-content notification is unchanged and no longer depends on the Notification API being present.
Reason: A notification can be missed or silenced; a bouncing icon is hard to miss and needs no content.
References: [action approval](../capabilities/action-approval/specifications.md), CHG-0293's code in `apps/desktop/src/main.ts`, `apps/app/src/foundation/desktopAttention.ts`.
Validation: `desktopAttention.test.ts` (bounce asked, failure swallowed, no desktop app); typecheck of `app` and `desktop`; Biome. Not run: a real bounce on a Mac with an installed or development desktop app. The owner confirmed (2026-11-15) that the bounce repeats until they check what is happening, which is `critical` (bounces until focused), not `informational` (one bounce).

## CHG-0294 · 2026-11-15 · Fewer questions to leave the sandbox: the suite runs inside it, worktrees go in `.worktrees`

Type: Code
Event: Agreement and Delivery
Scope: Tests, tooling, repository conventions

Summary: The owner objected to being asked for permission all the time. The app's approval history of the last 3 days (aggregate counts and the shape of each command, nothing copied) shows about 120 "Run outside the sandbox" questions, and only 6 answered by a saved permission, because Always allow saves the exact command (CHG-0208). The repeated causes were a thread's own tooling, not what the thread was asked to do: the test suite (21; OpenCode's Seatbelt tests, the terminal tests, the disk-image tests and the process-table tests failed inside the sandbox, so every run escaped), `git commit` (13; the pre-commit hook runs the related tests), `git worktree add` and commands in worktrees (about 23), and `git push`, `git fetch` and process kills (about 24, by design). This change removes the first three causes without widening anything. A test that needs what a sandbox withholds (a Seatbelt profile of its own, a pseudo-terminal, a disk image, the process table) is skipped there and named as skipped (`packages/service/test/support/environment.ts`, `apps/desktop/test/support/environment.ts`); the test that only passed inside the sandbox because `sandbox_apply: Operation not permitted` was the message it looked for now runs only where it means something. `vitest.setup.ts` clears an inherited `CLAUDE_CONFIG_DIR` and `CODEX_HOME`, so the suite no longer needs `env -u CLAUDE_CONFIG_DIR`. `.agents/worktree-setup.sh` prepares a worktree by copying the installed packages without the files a sandbox cannot write (`bun install` fails there on `.gitmodules`), and AGENTS.md says to make a worktree in `.worktrees/<name>`.
Reason: Ordinary work should not ask (CHG-0208, CHG-0273). The product's rule for what asks is unchanged; the two product options that would ask less (an Always allow covering a command family, and a level that never asks to leave the sandbox) were put to the owner, who had not answered when this was built, so neither is built.
References: CHG-0208, CHG-0273, [action-approval specification](../capabilities/action-approval/specifications.md), [verification](../verification/2026-11-15-fewer-approval-prompts.md).
Validation: See the verification record. Before: 31 tests failed inside the sandbox. After: none fail there, and 53 are skipped there. Red then green for the environment clearing (the account-folder test fails without `vitest.setup.ts` with `CLAUDE_CONFIG_DIR` set).
Evidence: Not yet run: the guarded tests on the owner's machine outside the sandbox (to prove the probes find the capability when it is there); a live thread's number of questions after this lands.

## CHG-0295 · 2026-11-15 · The owner may let commands leave the sandbox without a question

Type: Code
Event: Agreement and Delivery
Scope: Action approval, settings, Permissions page, thread instructions

Summary: The owner asked for something more global than saved exact commands: "allow to work out of the sandbox", after which actions outside the sandbox need no permission, or only the sensitive ones. Built as one setting, `shouldAllowOutsideSandbox` (off by default, global), shown on the Permissions page and changeable only by the owner (`change_setting` refuses it). When on, at the default level, an escape runs unasked and leaves a line; a thread still asks through `request_approval` for what it judges consequential (pushes, publishing, deleting, paying), and its instructions say so. Still asking: a harness with no sandbox, widening a sandbox, a harness file change outside the folder, the linked-folder confirmation, and every prompt at Also commands and edits. Reverses nothing of CHG-0208's rule that no command is judged by its words; it moves the choice to the owner once, globally.
Reason: The owner's answer to the offered options after CHG-0294; exact-command permissions rarely repeat.
References: [action-approval specification](../capabilities/action-approval/specifications.md#working-outside-the-sandbox), CHG-0208, CHG-0294, `packages/service/src/policy/containment.ts`, `packages/service/src/work/approvals.ts`.
Validation: Tests written first; red then green for the one condition (2 failures with it reverted): `containment.test.ts` (an escape needs nothing once allowed, but unprotected, unsandboxed, widening and a file outside still need their capability), `approvals.test.ts` (an escape and a Codex-style escape run unasked with lines; unprotected harness and a thread's own question still ask; off by default), `instructions.test.ts`, `guildmaster.test.ts` (the setting kept to the owner). See the [verification](../verification/2026-11-15-fewer-approval-prompts.md).
Evidence: Not checked: the Permissions page in a window, a live Claude Code or Codex thread, the installed Outlore app (it runs its own build, so it has no part of this until rebuilt from `main`).
