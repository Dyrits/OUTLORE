## CHG-0618 · 2026-11-21 · Mistral Vibe's reasoning levels back in the Companion menu

Mistral Vibe's models list their reasoning levels in the Companion menu again. Outlore read them only from each model's `_meta["mistral.ai/thinking"]` in the `model` config option — levels a newer Vibe build carries — but the released `vibe-acp` 3.1.3 says none there, so every model read as taking no effort and the reasoning level vanished from the menu (the picker shows only when a model offers levels). A model that says none of its own now takes the levels of the session's own `thinking` config option, which 3.1.3 offers for every model alike (low, high, max); a build that reports a model's own levels keeps them.

See [Provider accounts](../capabilities/provider-accounts/specifications.md), the research note on [Mistral Vibe's ACP](../research/mistral-vibe-acp-2026-11-18.md), and [verification](../verification/2026-11-21-vibe-thinking-levels.md).

## CHG-0617 · 2026-11-21 · The Workshop's four permission modes

The Workshop's Permissions page offers the same four modes as the composer — Supervised, Auto-accept edits, Auto and Full access — as the default for every thread without a mode of its own, and the composer's Default permissions names the mode it means, such as "Default permissions (Auto)". What applies where stays one vocabulary everywhere, read as: the thread's own mode overrides the default for that thread alone.

The two approval levels (Sensitive actions only, Also commands and edits) are gone; the modes carry what they did, by name. A saved store translates its choices: Also commands and edits becomes Supervised, Sensitive actions only becomes Auto, and with "let threads run commands outside the sandbox without asking" on it becomes Full access — except beside Also commands and edits, whose prompts stay and whose escapes ask once again. The escape setting itself is gone: only Full access lets commands leave the sandbox without a question, per thread or by default.

The four modes reach every composer (amended within this record): a quest's and an errand's, in the host window and on a paired phone — the mode request left the host-only list — and the mode changes at any time, like the runner: a change during a running turn is kept, that turn finishes under the mode it was admitted with, and the next turn applies the new one automatically. A turn admitted before the change reads the mode the turn was admitted with.

Outlore's own approvals — publishing, sending, widening a sandbox for a turn — still ask at every mode, and a thread still cannot change the default mode (`change_setting` refuses it).

See [Permission modes](../capabilities/action-approval/specifications.md#permission-modes) for the modes and the migration.

## CHG-0616 · 2026-11-21 · Rituals become entities of the realm; each run an errand

Type: Documentation
Event: Agreement
Scope: Rituals

Summary: A Ritual is agreed to be a top-level entity of its realm, listed beside the quests with its own look (the moon, its schedule, a dot while a run is underway), opened in the middle pane like a quest, with its controls — schedule, Run now, the on or off switch, Edit — in its panel. Each run opens an errand beneath the Ritual, its opening request the trigger line ("Ritual · scheduled 07:00" or "Ritual · run by you"), never counting as the owner's words, and its report landing in the Ritual's conversation, which is the run history (the composer is hidden there: no thread takes turns at a Ritual's top, and Run now is the only on-the-spot start). A Ritual keeps a journal of its own shared by its runs, a budget of its own, and the fallback-Companion list, one-run-at-a-time rule, schedule presets, 5-minute grace, reviewed scope, and savepoint-start rule already agreed. It takes its realm from its origin quest (an open quest's panel offers **Schedule as a Ritual**, keeping a visible origin link), or is created by Chronicler's `create_ritual` or a **+ Ritual** button in the realm. The separate Rituals place and its rail category are removed. Deleting a Ritual asks once and removes it with its runs and history permanently; archiving a realm keeps each Ritual in place, switched off and marked **Realm archived** (CHG-0270's rule on its new home). Each existing Ritual's quest becomes the Ritual: past runs stay readable in its conversation and future runs open as errands.
Reason: The owner asked how and where a Ritual is displayed and proposed runs as errands of a quest; the design rounds settled instead on a first-class Ritual entity beside the quests, so repeated work keeps a home and a history of its own without mimicking a quest's main thread.
References: [Rituals](../capabilities/rituals/specifications.md), [mission-tracking](../capabilities/mission-tracking/specifications.md) (realm archive, sidebar), [mission-coordination](../capabilities/mission-coordination/specifications.md) (Rituals), [thread-tree](../capabilities/thread-tree/specifications.md), [mission-journal](../capabilities/mission-journal/specifications.md), [connectors](../capabilities/connectors/specifications.md), [computer-use](../capabilities/computer-use/specifications.md), [thread-panel](../capabilities/thread-panel/specifications.md), [architecture](../architecture.md), [glossary](../glossary.md) (Routine, The menu), [outline](../outline.md).
Validation: The owner settled the design in three interview rounds on this quest ("Yes for all", and the comment threads on quests-and-rituals in a realm and creation through a quest), then directed that the last three choices (the hidden composer, permanent delete, the Ritual's own journal) be settled as recommended and implementation proceed. Not built: this record authorizes the model; the implementation batch follows, and its Delivery will carry the checks.

## CHG-0615 · 2026-11-21 · Editable queued messages

Pending owner messages stay at the bottom of the conversation through new replies and live output. A steered message stays there until the harness acknowledges it. While a message is queued, the owner can edit its text in place or remove it and its attachments. Both commands check that the queue still holds the message before changing it.

See [Thread messaging](../capabilities/thread-messaging/specifications.md).

## CHG-0614 · 2026-11-21 · Architecture audit follow-through

The inbox declares a receiver wake when it records a deliverable message. The command still applies the wake after commit and after cancellations. Background wake admission decides inside one transaction whether an existing turn takes the work or a new turn starts. The Claude Code adapter captures file edits when it reports tool calls, and Codex builds its restart key with one Git grant lookup.

Pane content now has a kind before layout decides which panes fold. A reducer keeps pane focus, expansion and folds together, and the notch module supplies the edge padding. The sidebar names its host explicitly. The window derives which conversations it shows or parks behind the Workshop.

The Chronicle uses one target rule across the activity list and conversation panes. Quest and Chronicler conversations share feed and retry rendering, and shown conversations share the read hook. Lists and notches use the same urgency and activity comparison, with their existing filters and tie order.

See the [architecture audit](../architecture-audit/architecture-audit-2026-11-21-0702.html) and [verification](../verification/2026-11-21-architecture-follow-through.md).

## CHG-0612 · 2026-11-21 · Thread permission modes

The host composer offers Supervised, Auto-accept edits, Auto and Full access. The choice is saved for the thread. Default permissions uses the Workshop settings.

Full access answers individual harness tool requests automatically, including Vibe's shell requests. Outlore still asks when a thread uses its own approval tool for an action such as publishing. Automatic approvals appear in the permissions history.

See [Thread permission modes](../capabilities/action-approval/specifications.md#thread-permission-modes) for the behavior of each mode.

## CHG-0613 · 2026-11-21 · Fold the channel pane when a quest opens

A quest opened from the sidebar starts with only its own conversation pane open: the realm's channel pane is folded behind its notch (CHG-0592) on the quest pane's left edge. Pressing that notch (or the pane's Restore pane layout) brings the channel back beside the quest, and the panes keep the owner's folds and shares for the rest of the quest; the next quest opens folded again. The rule lives in the pane chain: a quest's pane memory starts with the channel folded (`openedQuestMemory`), and an empty chain (a tree still loading) prunes no folds on mount, so the default survives the first read.
