## CHG-0520 · 2026-11-18 · Mistral Vibe joins the harnesses: `vibe-acp` over ACP, one process per thread

Type: Code
Event: Agreement and Delivery
Scope: Provider accounts, contracts, service, app

Summary: The owner asked to add Mistral Vibe as a harness Outlore can run threads on ("add Mistral Vibe in the provider we can use"). `HarnessName` gains `vibe`, and a new adapter, `packages/service/src/harness/vibe.ts` (turns) with `vibeAccount.ts` (the short account probes: models, sign-in, plan limits), drives Vibe's own ACP server `vibe-acp` (JSON-RPC 2.0 on stdio, `agent-client-protocol` 0.11.0 / schema v1.16.0, read from the `mistral-vibe` 3.1.3 wheel; [research](../research/mistral-vibe-acp-2026-11-18.md)): one process per thread, one ACP session per thread (`session/new` with Outlore's tool server as an HTTP MCP server, `session/load` to continue), one `session/prompt` per turn. Each session is set to Vibe's `ask` mode so every tool call asks, and `model` / `thinking` config options carry the thread's Companion and effort; the starting context rides on the first prompt of a fresh session, and a session Vibe cannot load is replaced by a new one given the thread's handover text, with a Notice. `session/request_permission` names only the tool call's id, so the adapter judges from the `tool_call` updates (kind/rawInput/locations, as OpenCode's) and answers `allow_once`/`reject_once`; a denial lets the turn carry on, as Vibe does. `session/cancel` interrupts; ACP takes no mid-turn message, so steering waits for the next turn, as OpenCode. Usage is the session-cumulative `usage` of the prompt's answer read as a per-turn delta; `usage_update` gives the context gauge.
