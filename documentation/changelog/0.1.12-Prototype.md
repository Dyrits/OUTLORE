## CHG-0527 · 2026-11-19 · A quest's header: Mark as done and a quest icon; the panel's edge handle goes

Type: Code
Event: Agreement and Delivery
Scope: `apps/app` (`conversation/conversation.tsx`, `ui/questHeaderButtons.tsx`, `shell/shell.tsx`, `shell/questTab.ts`, `foundation/shellContext.tsx`)

## CHG-0528 · 2026-11-19 · The phone shows a realm's name again in the sidebar

Type: Code
Event: Delivery
Scope: `apps/app` (`shell/railStyles.ts`, `shell/railQuests.tsx`, `test/shell/railStyles.test.ts`)

Summary: On a phone, a realm's row in the sidebar showed its folder mark and no name. The name was styled on the quest rows' text style, which carries `flex: 1`, with `flexBasis: "auto"` and `flexGrow: 0` laid over it. Yoga, the phone's layout engine, reads `"auto"` as unset, so the name kept `flex`'s basis of 0 and got no width; the web build follows CSS and was never affected. The realm's name now has its own style, with only `flexShrink: 1`, so it takes the width of its text and shrinks when the row is short.
Reason: The owner reported it with a screenshot of the phone's sidebar.
References: CHG-0161 (the row), CHG-0497 (touch rows).
Validation: `vitest run apps/app` passes (77 files, 554 tests, 6 skipped, before CHG-0527's test) and the new guard reads the style's source (it cannot load react-native); Biome clean; `tsc --noEmit` in `apps/app` clean after the guard moved to `import.meta.glob`. Not checked: a phone. The cause is read from Yoga's rule, not seen in a build; no APK was made from this change.

## CHG-0530 · 2026-11-19 · The connector gateway over stored choices, proved on a fake backend (blueprint step 3)

Type: Code
Event: Delivery
Scope: `packages/service` (`connectors/`, `core/recentStoreMigrations.ts`, `policy/patterns.ts`, `work/approvals.ts`, `work/commands.ts`, `work/connectorHandlers.ts`, `work/connectorWiring.ts`, `work/threads.ts`, `harness/claude.ts`, `harness/codex.ts`, `service.ts`), `packages/contracts` (`connectorRequests.ts`)

Summary: The owner authorized building the connectors (Composio and Apple apps) and the design of the [blueprint](../capabilities/connectors/blueprint.md) was taken as agreed; this is its Order step 3, with no real server, no Vault and no screen.
- **Catalog** (`catalog.ts`, `catalogEntries.ts`): entries for Composio and Apple apps with classification, platform constraint, install notice, server and licence. Composio names no tool, so every call asks and none is ever `Read`; Apple apps names none either (the exact names come from the pinned server's listing in step 4), so none is offered and none could run unasked. A server's tool name is accepted only as letters, digits, `-` and `_`, at most 64 characters; a connector id has no `__`, so `<connector>__<tool>` splits one way.
- **Stored choices**: migration `0060_connectors` adds `connectors` (with `is_removing`, the first step of a removal), `connector_choices` (a realm's and a quest's rows cascade on delete) and `connector_tools`. Nothing else in `core/` changed, and a database saved before it migrates with its data intact (a test).
- **Who may use what** (`availability.ts`, pure): the global switch first, then the quest's own choice, then its placement (its realm, or the Borderlands only for a quest in no realm), then On; Chronicler follows the global switch alone. Tested including the counterexample (global on, Borderlands Off, a quest in a realm that inherits is On) and over every combination for the global switch.
- **The gateway** (`connectors.ts`, `connectorCall.ts`, `calls.ts`, `toolListing.ts`): `listingFor` and `call` behind the existing `ConnectorGateway` interface, which replaces `noConnectorsLayer` in the service; each call is registered with its own identifier before any policy is read, takes the turn's snapshot of the tools the thread was offered, asks through `Approvals.askToolUse` when it is not a catalog-classified read, is checked again after the owner's answer, and runs through the backend with the secret the Vault lends for that call alone. A switch change narrows the turn snapshots inside its own transaction and, once committed, stops the calls whose tool left the snapshot (a command follow-up, `shouldStopConnectorCalls`): a stopped read says the connector is off for the thread, a stopped write that reached the server adds "the action may already have happened", a question it waited on is withdrawn, and no write is ever retried (a read is, once, on `Unreachable`). Failures map to four public classes with fixed sentences; the server's own words are never forwarded, stored or logged, and every spelling of the secret (raw, URL-encoded, base64, base64url) is replaced by `[redacted]` in a result. `Disconnected` marks the connector Needs connecting for everyone, `Unreachable` and `Disconnected` put one warning line in the thread (the line a lost session leaves, `insertThreadLine`), `InvalidArguments` changes nothing.
- **Seams**: `ConnectorBackend` (`listTools`, `call`, `close`) and `ConnectorBackends`; `VaultPort` (`holds`, `removeAllOf`, `withSecret`), which the Vault errand's `vault/` will be adapted to (this folder does not import it); `ConnectorAsking` and `ConnectorNotices`, supplied by `work/`. Until the real adapters exist the service uses a backend that is unreachable and a Vault that holds nothing, so an installed connector offers no tool.
- **Asking**: a new capability `useConnectorTool` ("Use a connector's tool") with the pattern `<connector>/<tool>`, so a permission for one tool never covers another tool nor a command; the permission is saved in the thread's workspace, or its quest when it has none.
- **Removal** in three idempotent steps (unusable at once and its calls stopped; the Vault's `removeAllOf`; the rows and the standing permissions, matched by prefix, not `LIKE`); a step 2 that fails leaves it Removing with the owner told, and the service resumes any removal left halfway as it starts.
- **Owner requests and contracts**: `ListConnectors` (cards), `InstallConnector` (notice confirmed; refused for Apple apps off a Mac), `RemoveConnector`, `SetConnectorSwitch` (global, Borderlands, realm, quest; On, Off, Reset), `SetConnectorTool`, `ChooseAppleApps`. They are the owner's alone: no thread tool reaches them (a test calls their names as tools), and a paired device may send them. `PutSecret`, `ReplaceSecret`, `RemoveSecret` and `RequestApplePermission` are left for the Vault and step 4.
- **Harnesses**: each turn starts by listing the thread's connectors again and taking its snapshot (`ConnectorGateway.beginTurn`); Claude Code's allow rule names each connector tool the snapshot holds (`mcp__outlore__<connector>__<tool>`), and the names join the Claude Code and Codex restart keys (`access.connectorTools`; OpenCode's key holds all of `access`). A call to a name that reads as a connector's tool now reaches the gateway even when the thread is no longer offered it, so the thread is told the connector is off for it rather than that the tool is unknown (`codeMode.ts`).
Reason: The owner asked to start the connectors with Composio and Apple apps and authorized the build.
References: [connectors specification](../capabilities/connectors/specifications.md), [blueprint](../capabilities/connectors/blueprint.md), [ADR 0022](../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md), CHG-0321 to CHG-0330, CHG-0441, CHG-0447.
Departures from the blueprint, each for the reader to confirm: (1) policy revisions are replaced by narrowing the turn snapshots inside a switch's transaction, which gives the same order with less state (a tool switched off and on again within a turn stays off; a tool switched on is not added). (2) A connector that needs a secret is "connected" when the Vault holds it, computed at each read, so `needs` records only a refusal by the server. (3) `VaultPort` has `holds` beside the two methods the blueprint named, and `withSecret` lends the secret as a plain string inside the callback. (4) An Apple tool whose app the catalog does not name is not offered, because the choice of apps could not be enforced on it; the instruction to make every unnamed tool ask therefore holds for Composio and, for Apple apps, takes effect once step 4 names the tools. (5) The tool listing is asked of each connector the thread may use at each turn start, which puts one network call per usable connector on a turn's start.
Validation: Biome clean, `bun run typecheck` passes on all workspaces, and `TMPDIR=<repo>/.tmp-test CI=1 bun run test` gives 2,262 passed, 55 skipped, 28 failed: the same 28 tests that fail on a clean checkout in a thread's sandbox (`git init` cannot copy its hook samples there; CHG-0529). 135 new tests in `test/connectors/` (11 files) cover the catalog, availability, redaction, the registry of calls, the gateway on the fake harness named Claude Code, Codex and OpenCode in turn (46 cases), the owner's requests, removal and its resume, the harness access and Code Mode over the real gateway; two mutations (no narrowing on a switch, no snapshot check) were each caught by 6 tests. Not checked: a real Composio or Apple server, a real Vault, a live Claude Code, Codex or OpenCode (the three are the one fake harness under three names), a Steps line for a read (the fake harness reports no tool call), a screen, a phone. [Verification](../verification/2026-11-19-connector-gateway.md).

## CHG-0533 · 2026-11-19 · The Streamable-HTTP MCP backend and Composio's seven tools (blueprint step 4, first half)

Type: Code
Event: Delivery
Scope: `packages/service` (`connectors/backends/httpMcp.ts`, `connectors/backend.ts`, `connectors/catalogEntries.ts`, `connectors/index.ts`, `service.ts`, `test/connectors/`, `test/fixtures/connectorWorld.ts`)

Summary: The HTTP transport of the connectors (blueprint, Backends) and the Composio entry's exact tools, built on the gateway over stored choices (CHG-0530), with no request to the real Composio and no real key.
- **`backends/httpMcp.ts`**: a Streamable-HTTP MCP client, one JSON-RPC `POST` per request (`tools/list`, `tools/call`) and no session; an answer is read as JSON or as the text event stream Outlore's own tool server sends. The key the Vault lends (`VaultPort.withSecret`) travels in the one header the entry names, nowhere else; the adapter redacts the key's spellings from a result again, behind the gateway's redaction. An interrupted or stopped call stops waiting: the aborted request is real, and the server sees the client give up. Failures carry the adapter's own fixed words, never the server's: HTTP 401/403 is `Disconnected`, 429/5xx and any network failure are `Unreachable` (the class the gateway retries once for a catalog `Read`, never for anything else), a JSON-RPC `-32602` is `InvalidArguments`, everything else — an errored or unusable result included — is `Failed`.
- **The service's backends** (`connectorBackendsLayer`): it replaces the unreachable-everywhere default; an `Http` entry opens the adapter, and a `Stdio` entry stays honestly unreachable until the stdio half of step 4 is built (the Apple apps errand). `unbuiltBackendsLayer` is gone.
- **Composio's tools** (`catalogEntries.ts`): the seven meta-tools its Connect endpoint publishes, each classified after reading Composio's own words ([research note](../research/composio-mcp-2026-11-19.md)): `COMPOSIO_SEARCH_TOOLS` and `COMPOSIO_GET_TOOL_SCHEMAS` are `Read` (pure discovery: one search's answer does name tools and the apps already connected, the reach a tool listing has); the five that execute, connect or run code (`COMPOSIO_MULTI_EXECUTE_TOOL`, `COMPOSIO_MANAGE_CONNECTIONS`, `COMPOSIO_WAIT_FOR_CONNECTIONS`, `COMPOSIO_REMOTE_WORKBENCH`, `COMPOSIO_REMOTE_BASH_TOOL`) are `Write` and ask. A meta-tool Composio adds stays unnamed by the catalog, so it is unclassified and asks. The consumer key (Composio's "AI Clients" page) and the endpoint are the entry's `https://connect.composio.dev/mcp` with the `x-consumer-api-key` header.
Reason: The owner asked to start the connectors with Composio and Apple apps and authorized the build; this is the first half of the blueprint's Order step 4.
References: [connectors specification](../capabilities/connectors/specifications.md), [blueprint](../capabilities/connectors/blueprint.md), [Composio MCP research note](../research/composio-mcp-2026-11-19.md), CHG-0321 to CHG-0330, CHG-0441, CHG-0447, CHG-0530.
Decisions for the reader to confirm: (1) no `initialize` handshake: the client is stateless, one request per call, as the blueprint's "one request per call" says; whether `connect.composio.dev/mcp` serves these without a prior `initialize` is NOT verified against the real server, and the fallback if it refuses is one `initialize` request when the backend opens. (2) 429 and 5xx read as `Unreachable` (retryable once for a read) rather than `Failed`. (3) A search's answer names the apps connected on the owner's Composio account, which is why discovery is where the `Read` classification ends: everything that acts asks. (4) No server-side narrowing exists on the shared Connect URL; a read-only session of Composio's own kind is a Composio SDK feature (a project API key and sessions) that Outlore would have to adopt as a design decision (see the research note).
Validation: see [the verification note](../verification/2026-11-19-http-mcp-composio.md). In short: Biome clean; `bun run typecheck` green on all workspaces; nine new tests in `test/connectors/backends/httpMcp.test.ts`, five of the adapter against a real local fake MCP HTTP server (listing in one request with the key in its header alone; call arguments; an event-stream answer; redaction of the key raw and base64; each refusal class with none of the server's words; interruption making the client give up on a held answer) and four through the whole gateway over the real server (the Vault's key in the header of every request; a read the server could not take retried exactly once; a write never retried; a switch stopping a read underway, the client giving up on a real HTTP request). The connectors suite passes (144 tests), and the full suite (`TMPDIR=<repo>/.tmp-test CI=1 bun run test`, run in this worktree outside a thread's shell sandbox) gives 2,334 passed, 19 skipped, 1 failed: the DMG staging test (`apps/desktop/test/updates/swap.test.ts`), which needs `hdiutil` and therefore the owner's terminal; the 28 `git init` failures CHG-0530 recorded for a thread's sandbox do not happen outside it. Not checked: the real Composio server (no key was held); a live harness (the gateway tests' fake harness carries the wire this far); Windows and Linux.
