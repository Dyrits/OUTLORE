## CHG-0531 · 2026-11-19 · The Vault: encrypted connector secrets with key custody, states and one writer

Type: Code
Event: Delivery
Scope: `packages/service` (`vault/`, `service.ts`, `work/promptPolicy.ts`), `documentation/architecture-decision-record/0022-*`, `documentation/capabilities/connectors/`

Summary: Connectors blueprint, Order step 2. `vault/` holds secrets in a records file sealed with AES-256-GCM (identifier and connector bound in), beside a header that names the key holder chosen once when the Vault is made. Key holders: the macOS Keychain (`security -i`, key on standard input), Windows DPAPI, the Secret Service (`secret-tool`) and a key file, behind one `KeyCustody` interface. States: Absent, Ready, Locked (holder unreachable), Lost (key gone, or its identifier differs), Corrupt; none but Ready writes, a Lost Vault may be emptied by the owner, and no key is made or holder changed silently. Writers run one at a time; a key move to another holder is explicit and keeps the old key until the header's rename commits. `Vault` offers `state`, `list`, `put`, `replace`, `remove`, `removeAllOf`, `moveKey`, `protection` and `withSecret`, the only read, which hands the callback a `Redacted` value. A secret is stored only while the folder's denial is verified for every installed harness, which the probes of CHG-0530 showed must hold for every key holder, not for the key file alone. The service makes the folder (mode 0700) at start, and its prompt policy refuses Claude Code's own Read, Grep and Glob of a path in it. No owner request, no connector and no screen use it yet; nothing real is stored.
Reason: The owner authorized the build of connectors; secrets need a place before a connector can have one.
References: [ADR 0022](../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md) (amended), [connectors blueprint](../capabilities/connectors/blueprint.md), [verification](../verification/2026-11-19-vault-read-denial.md), CHG-0327, CHG-0328.
Validation: Biome clean; `bun run typecheck` passes on all workspaces; `CI=1 bun run test` gives 2,253 passed, 65 skipped, 0 failed in a thread's sandbox, and the Vault's folder of tests 73 passed outside it. Includes the secrecy property test (a random secret, raw and encoded, found in no file, answer or error through a turn and after removal) and key moves interrupted at each step. Not checked: Windows and Linux holders on a real host (stand-in runner only); a locked Keychain; an echoing connector backend (the gateway is built apart); the first Mac run of the whole path with a real secret. Open for the owner: whether the stricter rule (above) stands, and how Claude Code's denial gets verified, since `put` is refused on a host with Claude Code until it is.

## CHG-0532 · 2026-11-19 · The connector gateway over stored choices, proved on a fake backend (blueprint step 3)

Type: Code
Event: Delivery
Scope: `packages/service` (`connectors/`, `core/recentStoreMigrations.ts`, `policy/patterns.ts`, `work/approvals.ts`, `work/commands.ts`, `work/connectorHandlers.ts`, `work/connectorWiring.ts`, `work/threads.ts`, `harness/claude.ts`, `harness/codex.ts`, `service.ts`), `packages/contracts` (`connectorRequests.ts`)

Summary: The owner authorized building the connectors (Composio and Apple apps) and the design of the [blueprint](../capabilities/connectors/blueprint.md) was taken as agreed; this is its Order step 3, with no real server, no Vault and no screen.
- **Catalog** (`catalog.ts`, `catalogEntries.ts`): entries for Composio and Apple apps with classification, platform constraint, install notice, server and licence. Composio names no tool, so every call asks and none is ever `Read`; Apple apps names none either (the exact names come from the pinned server's listing in step 4), so none is offered and none could run unasked. A server's tool name is accepted only as letters, digits, `-` and `_`, at most 64 characters; a connector id has no `__`, so `<connector>__<tool>` splits one way.
- **Stored choices**: migration `0060_connectors` adds `connectors` (with `is_removing`, the first step of a removal), `connector_choices` (a realm's and a quest's rows cascade on delete) and `connector_tools`. Nothing else in `core/` changed, and a database saved before it migrates with its data intact (a test).
- **Who may use what** (`availability.ts`, pure): the global switch first, then the quest's own choice, then its placement (its realm, or the Borderlands only for a quest in no realm), then On; Chronicler follows the global switch alone. Tested including the counterexample (global on, Borderlands Off, a quest in a realm that inherits is On) and over every combination for the global switch.
- **The gateway** (`connectors.ts`, `connectorCall.ts`, `calls.ts`, `toolListing.ts`): `listingFor` and `call` behind the existing `ConnectorGateway` interface, which replaces `noConnectorsLayer` in the service; each call is registered with its own identifier before any policy is read, takes the turn's snapshot of the tools the thread was offered, asks through `Approvals.askToolUse` when it is not a catalog-classified read, is checked again after the owner's answer, and runs through the backend with the secret the Vault lends for that call alone. A switch change narrows the turn snapshots inside its own transaction and, once committed, stops the calls whose tool left the snapshot (a command follow-up, `shouldStopConnectorCalls`): a stopped read says the connector is off for the thread, a stopped write that reached the server adds "the action may already have happened", a question it waited on is withdrawn, and no write is ever retried (a read is, once, on `Unreachable`). Failures map to four public classes with fixed sentences; the server's own words are never forwarded, stored or logged, and every spelling of the secret (raw, URL-encoded, base64, base64url) is replaced by `[redacted]` in a result. `Disconnected` marks the connector Needs connecting for everyone, `Unreachable` and `Disconnected` put one warning line in the thread (the line a lost session leaves, `insertThreadLine`), `InvalidArguments` changes nothing.
- **Seams**: `ConnectorBackend` (`listTools`, `call`, `close`) and `ConnectorBackends`; `VaultPort` (`holds`, `removeAllOf`, `withSecret`), which the Vault errand's `vault/` will be adapted to (this folder does not import it); `ConnectorAsking` and `ConnectorNotices`, supplied by `work/`. Until the real adapters exist the service uses a backend that is unreachable and a Vault that holds nothing, so an installed connector offers no tool.
- **Asking**: a new capability `useConnectorTool` ("Use a connector's tool") with the pattern `<connector>/<tool>`, so a permission for one tool never covers another tool nor a command; the permission is saved in the thread's workspace, or its quest when it has none.
- **Removal** in three idempotent steps (unusable at once and its calls stopped; the Vault's `removeAllOf`; the rows and the standing permissions, matched by prefix, not `LIKE`); a step 2 that fails leaves it Removing with the owner told, and the service resumes any removal left halfway as it starts.
- **Owner requests and contracts**: `ListConnectors` (cards), `InstallConnector` (notice confirmed; refused for Apple apps off a Mac), `RemoveConnector`, `SetConnectorSwitch` (global, Borderlands, realm, quest; On, Off, Reset), `SetConnectorTool`, `ChooseAppleApps`. They are the owner's alone: no thread tool reaches them (a test calls their names as tools), and a paired device may send them. `PutSecret`, `ReplaceSecret`, `RemoveSecret` and `RequestApplePermission` are left for the Vault and step 4.
- **Harnesses**: each turn starts by listing the thread's connectors again and taking its snapshot (`ConnectorGateway.beginTurn`); Claude Code's allow rule names each connector tool the snapshot holds (`mcp__outlore__<connector>__<tool>`), and the names join the Claude Code and Codex restart keys (`access.connectorTools`; OpenCode's key holds all of `access`). A call to a name that reads as a connector's tool now reaches the gateway even when the thread is no longer offered it, so the thread is told the connector is off for it rather than that the tool is unknown (`codeMode.ts`).
Reason: The owner asked to start the connectors with Composio and Apple apps and authorized the build.
References: [connectors specification](../capabilities/connectors/specifications.md), [blueprint](../capabilities/connectors/blueprint.md), [ADR 0022](../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md), CHG-0321 to CHG-0330, CHG-0441, CHG-0447.
Departures from the blueprint, each for the reader to confirm: (1) policy revisions are replaced by narrowing the turn snapshots inside a switch's transaction, which gives the same order with less state (a tool switched off and on again within a turn stays off; a tool switched on is not added). (2) A connector that needs a secret is "connected" when the Vault holds it, computed at each read, so `needs` records only a refusal by the server. (3) `VaultPort` has `holds` beside the two methods the blueprint named, and `withSecret` lends the secret as a plain string inside the callback. (4) An Apple tool whose app the catalog does not name is not offered, because the choice of apps could not be enforced on it; the instruction to make every unnamed tool ask therefore holds for Composio and, for Apple apps, takes effect once step 4 names the tools. (5) The tool listing is asked of each connector the thread may use at each turn start, which puts one network call per usable connector on a turn's start.
Validation: Biome clean, `bun run typecheck` passes on all workspaces, and `TMPDIR=<repo>/.tmp-test CI=1 bun run test` gives 2,262 passed, 55 skipped, 28 failed: the same 28 tests that fail on a clean checkout in a thread's sandbox (`git init` cannot copy its hook samples there; CHG-0529). 135 new tests in `test/connectors/` (11 files) cover the catalog, availability, redaction, the registry of calls, the gateway on the fake harness named Claude Code, Codex and OpenCode in turn (46 cases), the owner's requests, removal and its resume, the harness access and Code Mode over the real gateway; two mutations (no narrowing on a switch, no snapshot check) were each caught by 6 tests. Not checked: a real Composio or Apple server, a real Vault, a live Claude Code, Codex or OpenCode (the three are the one fake harness under three names), a Steps line for a read (the fake harness reports no tool call), a screen, a phone. ## CHG-0533 · 2026-11-19 · The Vault joined to the gateway, its owner requests, and the Claude Code denial stamp (blueprint steps 2 and 3 merged)

Type: Code
Event: Delivery
Scope: `packages/contracts` (`vaultRequests.ts`, `requests.ts`, `results.ts`, `requestSources.ts`), `packages/service` (`harness/claudeDenialStamp.ts`, `harness/vaultDenials.ts`, `harness/claude.ts`, `core/execution.ts`, `vault/vault.ts`, `vault/protection.ts`, `work/vaultWiring.ts`, `work/vaultHandlers.ts`, `work/requestContext.ts`, `service.ts`), `apps/app` (`foundation/client.ts`)

Summary: The two delivered branches are merged and the Vault now stands behind the gateway's `VaultPort`, with the owner's Vault requests and a kept, keyed record of Claude Code's verified read-denial.
- **The port** (`work/vaultWiring.ts`): the real `Vault` adapted to `VaultPort` — `holds` (a missing secret is `false`, a locked or lost Vault is `VaultUnavailable` with its state as the reason), `withSecret` lending the value as a plain string only inside the callback (`SecretMissing` when absent), `removeAllOf` — and the service composition supplies it as `connectorVault` in place of `emptyVaultLayer`, built from the one `Vault` instance, so the gateway and the owner's requests read the same Vault. A `connectorVault` option still replaces only the port.
- **Owner requests and contracts** (`contracts/vaultRequests.ts`, `work/vaultHandlers.ts`): `ReadVault` (the Vault's state, its entries — connector, kind, added-at, holder, never a value — and whether a secret may be stored now, with the unverified harnesses named as the owner reads them), `PutSecret`, `ReplaceSecret`, `RemoveSecret` and `VerifyClaudeVaultDenial`. The secret field is `Schema.RedactedFromValue(Schema.String)`: it is wrapped on decode, never echoed in a result, and change announcements carry only a sequence number; no thread tool reaches any of them (a test calls their names as tools), and a paired device may send them, like the connectors'. `ReplaceSecret` calls `Connectors.clearNeeds` after the change, so a connector the server refused shows connected again. Failures map to the app's error kinds (`Exists`/`Invalid` to InvalidInput, `Missing` to NotFound, `NotProtected` to AccessRefused, the rest to ExecutionFailure). The app's client now encodes each frame through `ClientFrameJson`, so a `Redacted` secret travels as what was typed for the service to wrap, not as its `"<redacted>"` placeholder.
- **The denial stamp** (`harness/claudeDenialStamp.ts`, `harness/vaultDenials.ts`, `core/execution.ts`): Claude Code applies its sandbox only inside a live model turn, so a probe at start cannot try it. The owner-run live probe (`runClaudeVaultDenialLive`: one turn with the Vault's folder denied that must not read a disposable marker while reading a control, and one without the denial that must read both) writes a stamp into the Vault's folder, keyed to the Claude Code version and a SHA-256 of the sandbox settings the adapter writes. `readClaudeVaultDenial` answers from that stamp: Verified while it matches, Unverified (stale, with what changed) once the version or the settings differ, Unverified (no stamp) until the probe runs. The `VerifyClaudeVaultDenial` owner request runs the live probe through the harness adapter (`HarnessAdapter.runVaultDenialLive`) and, when it verifies, refreshes the Vault's memoized probe report (`Vault.refreshDenials`), so the stricter rule — a secret is stored only while every installed harness's denial is verified — applies without a restart. The app can trigger the probe later from the owner's side; no screen exists yet.
Reason: The blueprint's Order steps 2 and 3 had to be joined before the backends (step 4), and the Vault's rule needed a model-free record of Claude Code's denial that the owner can produce once.
References: [connectors specification](../capabilities/connectors/specifications.md), [blueprint](../capabilities/connectors/blueprint.md), [ADR 0022](../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md), CHG-0530 to CHG-0532.
Departures from the blueprint, each for the reader to confirm: (1) the stamp lives in the Vault's folder itself (denied to every sandbox, ignored by the Vault's own inspection) rather than beside it; its key hashes the adapter's sandbox settings with the per-thread worktree list left out, since worktrees never touch the folder's denial. (2) `VerifyClaudeVaultDenial` is the owner request that runs the live probe; the blueprint left the trigger open. (3) The app's frame encoding moved from plain `JSON.stringify` to the `ClientFrameJson` codec, which is what makes a `Redacted` field round-trip; for requests without one the wire text is unchanged.
Validation: Biome clean, `bun run typecheck` passes on all workspaces, and `TMPDIR=<repo>/.tmp-test CI=1 bun run test` gives 2,423 passed, 21 skipped, 1 failed — the one failure is `apps/desktop/test/updates/swap.test.ts` staging from a disk image (`hdiutil attach` is refused by the sandbox; the file is untouched by this change and the failure is environmental). 25 new tests: the contracts' frame round-trip and redaction (4), the stamp's key, round-trip, judgment and the start-up and live probes on a stand-in `claude` (8), the `VaultPort` adapter over a fake Vault (4), and the owner requests through the whole service on fakes — listing, put/replace/remove, validation, the unverified rule refusing storage, the live probe verifying and unblocking it, the failing probe staying refused, replace clearing Needs connecting, a secret found in no file of the service nor in any plain rendering, and no thread tool for the five requests (9). Not checked: a real Claude Code live turn (the opt-in `OUTLORE_LIVE_CLAUDE_PROBE=1` test stays the owner's to run), a real Keychain, a real Composio or Apple server, a screen, a phone.
