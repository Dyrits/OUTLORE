## CHG-0531 · 2026-11-19 · A modified file's diff, in its step

Type: Code and Specification
Event: Agreement and Delivery
Scope: `packages/contracts` (`activities.ts`, `activityRequests.ts`), `packages/service` (`work/fileChanges.ts`, `work/lineDiffs.ts`, `work/activities.ts`, `work/threads.ts`, `work/turns.ts`, `work/deleting.ts`, migration `0060_thread_activity_diffs`, the fake harness's `tooluse` line), `apps/app` (`conversation/callStep.tsx`, `diffView.tsx`, `stepsGroup.tsx`, `entries.ts`, `stepLabels.ts`), the action-approval specification and the requirements

Summary: The owner asked to see the diff when a file is modified, with or without git, in a fold either under the agent's message or as a step. Agreed: in the step, from the edit itself, only the diff stored, loaded on demand.
- **Placement.** In the turn's folded steps list, a call that modifies a file keeps its line and adds `+added −removed` (green, red); the line unfolds to a unified diff (added lines green, removed lines red, two lines of context, a gap line between stretches, long lines wrapping). The colors are the palette's `successSoft`/`successText` and `dangerSoft`/`dangerText`, so every look has its own.
- **Source.** No git, never `git init`. Claude Code's `Edit` and `MultiEdit`: the call's own old and new text, read from the `tool_use` input (nothing read from disk). A whole-file `Write`: the host reads the file's previous text in memory just before the write, diffs it, and drops it (a missing file is all additions). The race: Claude Code reports a call as it starts and may run it at once, so when the file already holds exactly the text written, the previous text is not known and the step says so (no counts, a note in its fold) instead of guessing. `NotebookEdit` gives no previous text: left out, its step is as before. A file or written text over 1 MB, and a binary file, get a note and no diff. The diff is my own line diff (common prefix and suffix trimmed, then a longest-common-subsequence table; a middle too large to compare is shown as removed then added): no library added.
- **Storage.** Migration `0060_thread_activity_diffs` (additive): one row per call with the counts, a note, and the diff lines as prefixed text, cut at 64 KB (`maxDiffBytes`) at a line with the note "Diff cut: only the first 64 KB is kept.", counts staying those of the whole change; no file is ever kept. Deleted with the thread (`work/deleting.ts`). A call that reaches the permission prompt shows as its action and keeps no diff (it may be denied), whichever of the prompt and the call's report comes first.
- **On demand.** The mission detail's steps list carries only `Activity.change` (`added`, `removed`, optional: absent from a host that predates it). The diff is read by the new `ReadFileDiff` request (thread, call) when a fold first opens, through the same client and transport as every request, so a paired phone reads it; a call with no diff answers NotFound.
- **Never sent to a harness.** Activities are read only by the app's mission detail; nothing about a diff, counts included, enters a prompt or session, so the model's context does not grow.
- **Contract and requirements.** The Activity contract's "never output or content" is relaxed for modified files only, in `activities.ts` and the specification (action-approval, "A modified file's diff"). The requirement it touches is Privacy and data, "Local data" (workspace contents stay on the computer): a new requirement, "A diff is changed text kept locally", says a diff stays local, is capped per file, is never sent to a harness or provider, reaches a paired device only over the encrypted connection, and is deleted with its thread.
- **Harnesses.** Claude Code only. Codex's adapter reads a `fileChange` item's paths only, to word an approval, and reports no tool calls; Vibe reports tool calls (`title`, `rawInput`) but its edit payload is not probed; OpenCode's adapter reports no tool calls: none gets a diff yet.
Reason: The owner asked to see what a thread changed in a file without leaving Outlore, and not to require git.
References: [action-approval specification](../capabilities/action-approval/specifications.md#a-modified-files-diff), [requirements](../requirements.md) (Privacy and data), CHG-0276 (the steps list), [verification](../verification/2026-11-19-file-diff.md).
Validation: Biome clean on 958 files; `bun run typecheck` passes on all workspaces; `TMPDIR=<repo>/.tmp-test CI=1 bun run test` gives 2192 passed, 55 skipped, 28 failed (2275 tests; the 28 are the sandbox-only `git init` failures recorded in CHG-0529). 32 new tests: `lineDiffs` (8), `fileChanges` (11) and `fileChangeSteps` (10, through the service with the fake harness: Edit, MultiEdit, Write over an existing file, Write of a new file, a file with no trailing newline, a Write already done when read, a very large diff cut, a diff read on demand, no diff for a call that reached the prompt either way, deletion with the thread, only counts in the steps list) and three in the app (counts text, the steps entry). Seen in a real throwaway window (fake harness, light look): an Edit and a Write over a real file, wide and at 390 px width. Not checked: a live Claude Code (the Write race has not been measured), a phone, the dark and other looks, whether Claude Code's `tool_use_result` carries a patch that would remove the race.

## CHG-0537 · 2026-11-19 · The Vault: encrypted connector secrets with key custody, states and one writer

Type: Code
Event: Delivery
Scope: `packages/service` (`vault/`, `service.ts`, `work/promptPolicy.ts`), `documentation/architecture-decision-record/0022-*`, `documentation/capabilities/connectors/`

Summary: Connectors blueprint, Order step 2. `vault/` holds secrets in a records file sealed with AES-256-GCM (identifier and connector bound in), beside a header that names the key holder chosen once when the Vault is made. Key holders: the macOS Keychain (`security -i`, key on standard input), Windows DPAPI, the Secret Service (`secret-tool`) and a key file, behind one `KeyCustody` interface. States: Absent, Ready, Locked (holder unreachable), Lost (key gone, or its identifier differs), Corrupt; none but Ready writes, a Lost Vault may be emptied by the owner, and no key is made or holder changed silently. Writers run one at a time; a key move to another holder is explicit and keeps the old key until the header's rename commits. `Vault` offers `state`, `list`, `put`, `replace`, `remove`, `removeAllOf`, `moveKey`, `protection` and `withSecret`, the only read, which hands the callback a `Redacted` value. A secret is stored only while the folder's denial is verified for every installed harness, which the probes of CHG-0536 showed must hold for every key holder, not for the key file alone. The service makes the folder (mode 0700) at start, and its prompt policy refuses Claude Code's own Read, Grep and Glob of a path in it. No owner request, no connector and no screen use it yet; nothing real is stored.
Reason: The owner authorized the build of connectors; secrets need a place before a connector can have one.
References: [ADR 0022](../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md) (amended), [connectors blueprint](../capabilities/connectors/blueprint.md), [verification](../verification/2026-11-19-vault-read-denial.md), CHG-0327, CHG-0328.

Reason: The owner asked to start the connectors with Composio and Apple apps and authorized the build.
References: [connectors specification](../capabilities/connectors/specifications.md), [blueprint](../capabilities/connectors/blueprint.md), [ADR 0022](../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md), CHG-0321 to CHG-0330, CHG-0441, CHG-0447.
