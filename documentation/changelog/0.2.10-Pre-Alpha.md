## CHG-0757 · 2026-11-26 · A sent image is not read back from the service after its own upload

Type: Code
Event: Agreement and delivery
Scope: Message attachments

Summary: The app already kept the images it fetched by attachment identifier (`imageCache`, 64 MB, least recently shown dropped first, one request for two simultaneous views), so a refresh, a scroll or another panel's change never fetched a sent image again.
The one read left was the first: the image the owner attached was sent to the service on upload, and its message then fetched the same bytes back with `ReadAttachment`.
The upload now puts the picture in the cache under the card's identifier (`imageCache.put`), so the sent message shows it with no request; removing or discarding a draft forgets it (`imageCache.forget`).
The cache is `sentImages` in `sentImage.ts`, shared by the message box and the thumbnails, and `dataAddressOf` writes the address both use.
Nothing changes on the service or the wire: `ReadAttachment` still serves another window, a restart, or an image from an older message.
Reason: The review's wave 2 asked that an image be read and sent once per screen (STD-PKG-02, 2026-11-26).
References: [message attachments](../capabilities/message-attachments/specifications.md), CHG-0750.
Validation: `imageCache.test.ts` (five new tests: put, no overwrite, eviction by a put, forget, a forgotten fetch that settles later) and `sentImage.test.ts` (two new), the first written red.
Not checked in a running desktop window.

## CHG-0758 · 2026-11-26 · A change tells a screen only the reads it concerns, and equal reads share one request

Type: Code
Event: Agreement and delivery
Scope: Host service change feed, app service client

Summary: A `Changed` frame now names the topics its changes touched, `work` and `spend`, when they touched only those (`topics`, absent when a change may have touched anything).
A turn's events (replies, activity, notices, steered messages, folder moves, admission and failure) announce `work`, and a turn's end announces `spend` as well; every other change stays unscoped.
`queryTopics` in `packages/contracts/src/topics.ts` lists the topics each read follows, and the app's `ServiceClient.subscribe` takes the tag of the read it refetches, so the settings, the Vault, the connectors, the paired hosts, the harnesses and the host's name no longer refetch while agents work.
A burst keeps one frame at once and one after the window, the second naming the union of what the burst touched, or none when one change in it was unscoped.
`ServiceClient.request` also gives one answer to equal reads asked together, so `ReadChronicle` asked from three places (and `ReadAccountBudgets` from four) is one frame on the wire, not three; the sharing ends at the next `Changed` frame and at any command, so a read asked after a change never takes an answer that may predate it.
Reason: The idle host traffic record recommended sharing identical queries and then scoping `Changed` (CHG-0724), and the review's second wave listed scoped topics (STD-PKG-01 part 2).
Each `Changed` made every mounted call site refetch, `ReadSettings` from up to 12 sites and `ReadChronicle` at 18 KB with 30 quests, about 120 KB with all mounted.
Safe by default: a read not named in `queryTopics` and a change that names no topics both refetch as before, and so does a screen that reconnects.
Not scoped yet, and open: the other publishers (lore, settings and connector changes, thread tools) stay unscoped, and the measurement of the loopback link and the relay's request count was not repeated, so the saving is shown by the tests below and not yet by a live reading.
References: [Architecture](../architecture.md), [verification of idle host traffic](../verification/2026-11-25-idle-host-traffic.md), CHG-0719, CHG-0724.
Validation: `packages/contracts/test/topics.test.ts` (the table names real requests and every request that reads by name), `useServiceQuery.test.ts` (a scoped change refetches only the reads that follow its topics; equal reads share one request until a change or a command), `idleTraffic.test.ts` (a turn's frames all name topics and the end names `spend`; unscoped and scoped bursts) and `commands.test.ts` passed, and the typecheck passes in all seven workspaces. Not checked in a running desktop window.

## CHG-0763 · 2026-11-26 · Dual-auth OAuth 2.1 on existing connectors and thirteen missing DCR remote connectors

Type: Code
Event: Agreement and delivery
Scope: Connectors (`catalog.ts`, `backend.ts`, `backends/httpMcp.ts`, `vaultPort.ts`, `connectorState.ts`, `toolListing.ts`, `connectorCall.ts`, `connectors.ts`, `connectorCards.ts`, `entries/`, `work/vaultWiring.ts`, `work/vaultHandlers.ts`), Charter UI (`connectorPanel.tsx`), specification

## CHG-0770 · 2026-11-26 · Phone control step 1 built: six `phone_*` tools, the phone's switches and card

Type: Feature
Event: Delivery
Scope: Phone control (CHG-0767, CHG-0768), `packages/contracts`, `packages/service`, `apps/app`
Summary: Threads on every harness can call `phone_info`, `phone_location`, `phone_clipboard_read`, `phone_clipboard_write`, `phone_open` and `phone_notify`. The host sends each call to the named paired phone (`PhoneCall` frame, `Sessions.sendTo`), the app runs it and answers (`AnswerPhoneCall`); the tools are listed only while a paired phone with that group switched on is connected. The phone's **Let threads use this phone** card (Menu, Settings, Permissions) holds one switch per group, off by default, stored on the phone and sent to the host as `SetPhoneTools`; the two phone requests are paired-device-only.
