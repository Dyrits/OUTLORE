# Changelog: 0.1.8-Prototype

## CHG-0445 · 2026-11-18 · The Android app no longer crashes once a pairing connects

Type: Code
Event: Delivery
Scope: App (Guild Hall hub), release

Summary: The owner reported that the Android app (0.1.7-Prototype, installed from the debug-signed build) crashed after a pairing was attempted. `adb logcat -b crash` held two crashes, both `TypeError: undefined is not a function` thrown in `hubOf` and called from `GuildHallHub`, which renders as soon as a pairing connects. Cause: `hubOf` sorted the quests with `Array.prototype.toSorted`, and Hermes, the phone app's engine (React Native 0.88.1), does not have it. The engine's own Array table in `libhermesvm.so` of the installed APK lists `toReversed`, `toSpliced`, `with`, `findLast` and `flatMap`, but not `toSorted`. TypeScript's library does know it, so the typecheck passed. `hubOf` now sorts a copy (`[...missions].sort(...)`). A guard test fails when the code the phone bundles (the app, `contracts`, `controller`) calls `.toSorted(`. This hotfix release carries that fix and nothing else; the version moves to 0.1.8-Prototype.
Reason: A phone that pairs but crashes on the first screen is unusable, and 0.1.7-Prototype is the first release with the Android app.
References: CHG-0298, CHG-0443, `apps/app/src/conversation/guildHall.ts` (`hubOf`), `apps/app/test/conversation/guildHall.test.ts`, `apps/app/test/foundation/hermesBuiltins.test.ts`, `apps/app/test/raw.d.ts`.
Validation: the new test in `guildHall.test.ts` ran `hubOf` without `Array.prototype.toSorted`: it failed with the crash's `TypeError` before the fix and passes after. The guard test failed on a planted `.toSorted(` call and passes on the tree. All 72 app test files (511 tests passed, 8 skipped), the app's typecheck and Biome pass. Not checked: the fixed app on the phone (needs the 0.1.8 APK), the rest of a pairing from the phone (camera, `outlore://` link), and other built-ins newer than Hermes: the client code was searched for `toSorted`, `toReversed`, `toSpliced`, `findLast`, `Object.groupBy`, `Array.fromAsync`, `Promise.withResolvers` and the new Set methods, and only `toSorted` is used (the few `.at(-1)` calls are on arrays, which Hermes has); a built-in outside that list was not looked up.

## CHG-0446 · 2026-11-18 · Proposal: Code Mode widened to every tool of Outlore's own tool server

Type: Documentation
Event: Proposal (the owner asked for it; the design is not yet agreed)
Scope: Connectors (Code Mode)

Summary: Asked whether Code Mode applies only to connectors, the owner pointed at Cloudflare's article and said it is exactly what Code Mode is for and that it should do many things. This proposal, written in the connectors specification (Code Mode) and not agreed, widens Code Mode from connector tools to every tool a thread reaches through Outlore's own tool server: its connectors' tools and Outlore's own thread tools (`open_thread`, `save_intel`, `read_journal`, ...), in one code tool (`run_code`), with `outlore.<tool>` beside `connectors.<connector>.<tool>`. A harness's own Bash, file, edit and web tools stay outside it, because they are not MCP tools and keep their own prompts. Four tools stay direct (`request_approval`, `answer_prompt`, `report_result`, `suggest_mission`). Each call from code goes through the same checks, questions and permissions as a direct call, and approvals still ask the owner while the code runs. The agreed text of CHG-0324 stays in the specification under **Agreed** until the owner decides; this proposal would change its sentences that say Code Mode "changes only how connector tools are shown and called" and that Outlore's own thread tools "stay as they are". Eight questions are listed under Open for the owner, each with a recommendation: the direct tools, a lower per-run count for `open_thread`, hiding the covered tools from the listing, a harness without the tool server, the setting's and the Charter label's names, reading the setting once per turn instead of per call, measuring before building, and whether Code Mode gets a capability of its own. The Charter switch's wording that would change is written in the specification; `apps/app` is untouched.
Reason: The owner's reading of Code Mode is wider than CHG-0324, which was agreed for connectors only; widening it changes agreed behavior, so it is proposed, not applied.
References: [connectors specification, Code Mode](../capabilities/connectors/specifications.md#code-mode), [ADR 0023](../architecture-decision-record/0023-code-mode-runs-in-quickjs-inside-the-host.md) (a note, no change to its decision), CHG-0324, CHG-0325, CHG-0441, CHG-0444, [Cloudflare's article](https://blog.cloudflare.com/code-mode/), `packages/service/src/work/mcp.ts` (`dispatchTool`, `listTools`), `packages/service/src/work/threadTools.ts`, `packages/service/src/connectors/codeMode.ts`, `apps/app/src/charter/codeMode.ts`.
Validation: documentation only; no code was changed, run or tested. Read from source: all three harnesses are given Outlore's tool server (`claudeArgs.ts`, `codex.ts:81`, `opencode.ts:153`); the setting is read on every call in `dispatchTool`; `readCallerRefusal` (the chatter guard) runs once per tool call in `callTool`; I found no cap on `open_thread` in `threadToolHandlers.ts`; Claude Code runs the tools marked unasked in `threadTools.ts` without asking, and `request_approval` and `answer_prompt` are the two that are not. From the article: it covers MCP tools and tools the application defines, not a harness's built-ins, and does not discuss approvals. Not checked: whether any harness lists tools only once at turn start (the per-call read is a reason to check, not a finding), and the gain, which is unmeasured.

## CHG-0447 · 2026-11-18 · Code Mode covers every tool of Outlore's own tool server, with no connector needed

Type: Code
Event: Agreement and Delivery
Scope: Connectors (Code Mode), service, app (Charter), harness restart keys

Summary: After the proposal (CHG-0446) the owner said "implement it properly". I took that as agreement to the proposal with each of its recommendations, and listed them in the specification for the owner to redirect. Built: the one tool is now `run_code` (it was `run_connector_code`); with Code Mode on it declares Outlore's own thread tools as `outlore.<tool>` beside the connectors' `connectors.<connector>.<tool>`, and the covered tools are no longer listed or callable directly ("Code Mode is on: call X from code, with run_code."). The four tools that stay direct are `request_approval`, `answer_prompt`, `report_result` and `suggest_mission`. Each call from code has the caller checks and the answer a direct call has (`ownToolsFor` in `work/mcp.ts`); a tool that asks the owner asks while the code runs. Calls to `open_thread`, `send_thread_message` and `interrupt_thread` count apart, at most 5 a run. With no connector the code tool still reaches Outlore's own tools. The setting is read once, when a thread's turn starts (`Endpoints.holdCodeMode`, set in `work/threads.ts`), and holds for the turn; `ThreadAccess.usesCodeMode` joins the Claude Code and Codex restart keys (OpenCode's already holds all of `access`), so a harness that keeps its process between turns restarts it and lists its tools again, which closes the question the blueprint left open. Claude Code runs `run_code` unasked only while Code Mode is on. The runner installs any nested set of host functions as globals. The Charter's switch is now "Code Mode", with a new explanation and state lines; a run shows in the thread's steps as "Run code that calls its tools". `apps/app`'s switch and its tests changed; no stored data changed.
Reason: The owner wants Code Mode to be what Cloudflare's article describes, many tools through one code tool, not only connector calls, and wants it to work now, not once connectors exist.
References: CHG-0324, CHG-0325, CHG-0441, CHG-0444, CHG-0446, [connectors specification, Code Mode](../capabilities/connectors/specifications.md#code-mode), [ADR 0023](../architecture-decision-record/0023-code-mode-runs-in-quickjs-inside-the-host.md), [verification](../verification/2026-11-18-code-mode-widened.md), `packages/service/src/connectors/codeMode.ts`, `codeRunner.ts`, `codeTypes.ts`, `packages/service/src/work/mcp.ts`, `threadTools.ts`, `threadToolAccess.ts`, `threads.ts`, `packages/service/src/core/endpoints.ts`, `execution.ts`, `packages/service/src/harness/claude.ts`, `codex.ts`, `apps/app/src/charter/codeMode.ts`.
Validation: Biome, the seven typechecks and `CI=1 bun run test` pass on the branch (2,061 passed, 54 skipped); new and changed tests: `codeMode.test.ts` (15, through the real MCP tool server with a fake gateway and the real thread tools), `codeExecutor.test.ts` (14), `threadTools.test.ts`, `activities.test.ts` (3), and the app's `codeMode.test.ts`. Measured with no connector: the listing a thread is given is 20,077 characters with Code Mode off and 18,619 with it on, 7% less, so the context saving from hiding definitions is small; the gain from chained calls is unmeasured. Not checked: a live Claude Code, Codex or OpenCode writing and running code against the declarations, the restart on a changed setting on a live harness process (only the keys and the fake harness), the Charter's switch in a window or on a phone, and a real connector.
