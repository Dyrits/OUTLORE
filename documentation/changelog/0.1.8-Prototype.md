# Changelog: 0.1.8-Prototype

## CHG-0445 · 2026-11-18 · The Android app no longer crashes once a pairing connects

Type: Code
Event: Delivery
Scope: App (Guild Hall hub), release

Summary: The owner reported that the Android app (0.1.7-Prototype, installed from the debug-signed build) crashed after a pairing was attempted. `adb logcat -b crash` held two crashes, both `TypeError: undefined is not a function` thrown in `hubOf` and called from `GuildHallHub`, which renders as soon as a pairing connects. Cause: `hubOf` sorted the quests with `Array.prototype.toSorted`, and Hermes, the phone app's engine (React Native 0.88.1), does not have it. The engine's own Array table in `libhermesvm.so` of the installed APK lists `toReversed`, `toSpliced`, `with`, `findLast` and `flatMap`, but not `toSorted`. TypeScript's library does know it, so the typecheck passed. `hubOf` now sorts a copy (`[...missions].sort(...)`). A guard test fails when the code the phone bundles (the app, `contracts`, `controller`) calls `.toSorted(`. The version moves to 0.1.8-Prototype.
Reason: A phone that pairs but crashes on the first screen is unusable, and 0.1.7-Prototype is the first release with the Android app.
References: CHG-0298, CHG-0443, `apps/app/src/conversation/guildHall.ts` (`hubOf`), `apps/app/test/conversation/guildHall.test.ts`, `apps/app/test/foundation/hermesBuiltins.test.ts`, `apps/app/test/raw.d.ts`.
Validation: the new test in `guildHall.test.ts` ran `hubOf` without `Array.prototype.toSorted`: it failed with the crash's `TypeError` before the fix and passes after. The guard test failed on a planted `.toSorted(` call and passes on the tree. All 72 app test files (511 tests passed, 8 skipped), the app's typecheck and Biome pass. A local release build with the fix, installed with `adb` on the owner's Android phone, opened the Guild Hall hub on the paired host with its quests listed, and the crash log stayed empty. Not checked: a new pairing from the phone (camera, `outlore://` link), and other built-ins newer than Hermes: the client code was searched for `toSorted`, `toReversed`, `toSpliced`, `findLast`, `Object.groupBy`, `Array.fromAsync`, `Promise.withResolvers` and the new Set methods, and only `toSorted` is used (the few `.at(-1)` calls are on arrays, which Hermes has); a built-in outside that list was not looked up.

## CHG-0446 · 2026-11-18 · Proposal: Code Mode widened to every tool of Outlore's own tool server

Type: Documentation
Event: Proposal (the owner asked for it; the design is not yet agreed)
Scope: Connectors (Code Mode)

Summary: Asked whether Code Mode applies only to connectors, the owner pointed at Cloudflare's article and said it is exactly what Code Mode is for and that it should do many things. This proposal, written in the connectors specification (Code Mode) and not agreed, widens Code Mode from connector tools to every tool a thread reaches through Outlore's own tool server: its connectors' tools and Outlore's own thread tools (`open_thread`, `save_intel`, `read_journal`, ...), in one code tool (`run_code`), with `outlore.<tool>` beside `connectors.<connector>.<tool>`. A harness's own Bash, file, edit and web tools stay outside it, because they are not MCP tools and keep their own prompts. Four tools stay direct (`request_approval`, `answer_prompt`, `report_result`, `suggest_mission`). Each call from code goes through the same checks, questions and permissions as a direct call, and approvals still ask the owner while the code runs. The agreed text of CHG-0324 stays in the specification under **Agreed** until the owner decides; this proposal would change its sentences that say Code Mode "changes only how connector tools are shown and called" and that Outlore's own thread tools "stay as they are". Eight questions are listed under Open for the owner, each with a recommendation: the direct tools, a lower per-run count for `open_thread`, hiding the covered tools from the listing, a harness without the tool server, the setting's and the Charter label's names, reading the setting once per turn instead of per call, measuring before building, and whether Code Mode gets a capability of its own. The Charter switch's wording that would change is written in the specification; `apps/app` is untouched.
Reason: The owner's reading of Code Mode is wider than CHG-0324, which was agreed for connectors only; widening it changes agreed behavior, so it is proposed, not applied.
References: [connectors specification, Code Mode](../capabilities/connectors/specifications.md#code-mode), [ADR 0023](../architecture-decision-record/0023-code-mode-runs-in-quickjs-inside-the-host.md) (a note, no change to its decision), CHG-0324, CHG-0325, CHG-0441, CHG-0444, [Cloudflare's article](https://blog.cloudflare.com/code-mode/), `packages/service/src/work/mcp.ts` (`dispatchTool`, `listTools`), `packages/service/src/work/threadTools.ts`, `packages/service/src/connectors/codeMode.ts`, `apps/app/src/charter/codeMode.ts`.
Validation: documentation only; no code was changed, run or tested. Read from source: all three harnesses are given Outlore's tool server (`claudeArgs.ts`, `codex.ts:81`, `opencode.ts:153`); the setting is read on every call in `dispatchTool`; `readCallerRefusal` (the chatter guard) runs once per tool call in `callTool`; I found no cap on `open_thread` in `threadToolHandlers.ts`; Claude Code runs the tools marked unasked in `threadTools.ts` without asking, and `request_approval` and `answer_prompt` are the two that are not. From the article: it covers MCP tools and tools the application defines, not a harness's built-ins, and does not discuss approvals. Not checked: whether any harness lists tools only once at turn start (the per-call read is a reason to check, not a finding), and the gain, which is unmeasured.

## CHG-0447 · 2026-11-18 · Code Mode covers every tool of Outlore's own tool server, with no connector needed

Type: Code
Event: Agreement and Delivery
Scope: Connectors (Code Mode), service, app (Charter), harness restart keys

Summary: After the proposal (CHG-0446) the owner said "implement it properly". I took that as agreement to the proposal with each of its recommendations, and listed them in the specification for the owner to redirect. Built: the one tool is now `run_code` (it was `run_connector_code`); with Code Mode on it declares Outlore's own thread tools as `outlore.<tool>` beside the connectors' `connectors.<connector>.<tool>`, and the covered tools are no longer listed or callable directly ("Code Mode is on: call X from code, with run_code."). The four tools that stay direct are `request_approval`, `answer_prompt`, `report_result` and `suggest_mission`. Each call from code has the caller checks and the answer a direct call has (`ownToolsFor` in `work/mcp.ts`); a tool that asks the owner asks while the code runs. Calls to `open_thread`, `send_thread_message` and `interrupt_thread` count apart, at most 5 a run. With no connector the code tool still reaches Outlore's own tools. The setting is read once, when a thread's turn starts (`Endpoints.holdCodeMode`, set in `work/threads.ts`), and holds for the turn; `ThreadAccess.usesCodeMode` joins the Claude Code and Codex restart keys (OpenCode's already holds all of `access`), so a harness that keeps its process between turns restarts it and lists its tools again, which closes the question the blueprint left open. Claude Code runs `run_code` unasked only while Code Mode is on. The runner installs any nested set of host functions as globals. The Charter's switch is now "Code Mode", with a new explanation and state lines; a run shows in the thread's steps as "Run code that calls its tools". `apps/app`'s switch and its tests changed; no stored data changed.
Reason: The owner wants Code Mode to be what Cloudflare's article describes, many tools through one code tool, not only connector calls, and wants it to work now, not once connectors exist.
References: CHG-0324, CHG-0325, CHG-0441, CHG-0444, CHG-0446, [connectors specification, Code Mode](../capabilities/connectors/specifications.md#code-mode), [ADR 0023](../architecture-decision-record/0023-code-mode-runs-in-quickjs-inside-the-host.md), [verification](../verification/2026-11-18-code-mode-widened.md), `packages/service/src/connectors/codeMode.ts`, `codeRunner.ts`, `codeTypes.ts`, `packages/service/src/work/mcp.ts`, `threadTools.ts`, `threadToolAccess.ts`, `threads.ts`, `packages/service/src/core/endpoints.ts`, `execution.ts`, `packages/service/src/harness/claude.ts`, `codex.ts`, `apps/app/src/charter/codeMode.ts`.
Validation: Biome, the seven typechecks and `CI=1 bun run test` pass on the branch (2,061 passed, 54 skipped); new and changed tests: `codeMode.test.ts` (15, through the real MCP tool server with a fake gateway and the real thread tools), `codeExecutor.test.ts` (14), `threadTools.test.ts`, `activities.test.ts` (3), and the app's `codeMode.test.ts`. Measured with no connector: the listing a thread is given is 20,077 characters with Code Mode off and 18,619 with it on, 7% less, so the context saving from hiding definitions is small; the gain from chained calls is unmeasured. Not checked: a live Claude Code, Codex or OpenCode writing and running code against the declarations, the restart on a changed setting on a live harness process (only the keys and the fake harness), the Charter's switch in a window or on a phone, and a real connector.

## CHG-0451 · 2026-11-18 · The service transcribes a 16 kHz WAV recording with whisper.cpp

Type: Code
Event: Delivery
Scope: Service (voice, new `packages/service/src/voice/`)

Summary: `checkWav` reads a WAV header and refuses any recording that is not 16 kHz, mono, 16-bit uncompressed PCM, empty, or cut short, each with a plain reason. `transcribeWav` runs whisper.cpp's `whisper-cli` on that file with `-np -nt -l <language>` (`-ng` when the GPU is off), returns the trimmed transcript, and fails with a plain reason if the engine is missing, exits with an error, or runs past five minutes. `readTranscriberSettings` reads `OUTLORE_WHISPER_CLI`, `OUTLORE_WHISPER_MODEL` (both required), `OUTLORE_WHISPER_LANGUAGE` (default `auto`) and `OUTLORE_WHISPER_GPU` (default on) through `Config`, so a missing setting is an ordinary failure. Nothing is bundled, downloaded or shown in the app yet; the owner's environment names the engine and the model for now.
Reason: The first increment of the agreed approach, small enough to check against the real engine before the desktop's microphone, the phone, and the bundling are built.
References: CHG-0450, [ADR 0024](../architecture-decision-record/0024-speech-is-transcribed-on-the-owners-device-with-whisper-cpp.md), `packages/service/src/voice/transcribe.ts`, `packages/service/test/voice/transcribe.test.ts`, whisper.cpp at commit `8302b819` (MIT), model `ggml-base.bin` (sha256 `60ed5bc3dd14eea856493d334349b405782ddcaf0028d4b5df4088345fba2efe`, from the Hugging Face repository `ggerganov/whisper.cpp`).
Validation: the tests run on the worktree with `ELECTRON_RUN_AS_NODE=1 npx electron node_modules/vitest/vitest.mjs run packages/service/test/voice/transcribe.test.ts`. Without the engine: 7 passed, 2 skipped (the engine's tests need its paths). With the engine built from the pinned commit and the `base` model, with the GPU off (the sandbox aborts Metal): 9 passed, including the transcript of whisper.cpp's sample `jfk.wav`. Biome and `tsc -p .` in `packages/service` pass. Measured on this Mac, inside the sandbox, the CPU run on the 11-second sample took 0.53 s; automatic language detection gave the same sentence. Not measured: peak memory (the sandbox hides the engine's process from `ps`), the GPU path outside the sandbox, latency on a phone, and Windows or Linux. The original batch's full suite passed (2,055 passed, 56 skipped). The composer and phone remain untested.

## CHG-0453 · 2026-11-17 · Own copy: a side-quest works and commits in a git worktree Outlore makes, without asking

Type: Code
Event: Agreement and Delivery
Scope: Workspace attachment, thread tree, action approval, service

Summary: Threads kept asking the owner for anything done with a git worktree ("Create the code-mode worktree. This runs outside the sandbox"). Cause: Claude Code (2.1.326) blocks writes to `<folder the thread starts in>/.git/worktrees` inside its sandbox (a built-in rule, beside `.git/hooks` and `.git/config`, that Outlore's `allowWrite` cannot lift), so `git worktree add` and `remove`, and every `git add`, `commit` or `checkout` in an existing worktree from the checkout (they lock `.git/worktrees/<name>/index`), failed in the sandbox and asked. Edits and other commands in a worktree already ran unasked (CHG-0273). A live probe (Claude Code in `-p` with the sandbox on, started inside a linked worktree) showed that a thread whose folder *is* the worktree may write that worktree's own records, `.git/objects`, `refs` and `logs`, while `.git/hooks` and new `.git/worktrees` entries stay blocked. So the service now makes the worktree, and the thread starts inside it: `open_thread` takes `ownCopy: true`; the service (outside any sandbox) checks that the workspace is the top folder of a git repository, adds `/.worktrees/` to the repository's `.git/info/exclude` when it is not ignored already, and runs `git worktree add -b mission/<name> <workspace>/.worktrees/<name> <commit>`, from the commit the opener works on (the workspace, or the opener's own copy). `<name>` is the quest title's words and the thread's short id. The new thread's folder is that worktree; threads it opens share it unless they ask for their own. Its starting context names the copy, its branch and the workspace, tells it to commit there and name the branch in its result, and says the copy has no installed packages. Migration 0056 adds `threads.own_copy` and `own_copy_branch` (0054 is taken by `worktree/context-window`). A thread whose own copy folder is gone is held as a missing workspace. The thread instructions now steer branch work to `ownCopy` and say a self-made worktree, and each commit in it from the checkout, asks. The owner chose: build Own copy now, worktrees in `<workspace>/.worktrees/` (same disk, APFS clones) instead of the spec's `~/.iskios/worktrees/`, and no merge button or archive cleanup in this change; the opener merges with plain git, which runs unasked from the checkout.
Reason: The owner: "I always have this request for permission, for absolutely anything. Can we make worktree being part of the sandbox?"
References: [workspace attachment](../capabilities/workspace-attachment/specifications.md#own-copy), [action approval](../capabilities/action-approval/specifications.md), CHG-0273, `packages/service/src/work/ownCopies.ts`, `tree.ts`, `workspaces.ts`, `startingContext.ts`, `turnAdmission.ts`, `threadTools.ts`, `threadToolHandlers.ts`, `packages/service/src/harness/instructions.ts`, `packages/service/src/core/recentStoreMigrations.ts`.
Evidence: [Verification](../verification/2026-11-17-own-copy.md).
Validation: the block was reproduced in this thread's sandbox (`touch .git/worktrees/<name>/index.lock`: Operation not permitted) and located in Claude Code 2.1.326's own sandbox rules; the probe above ran once with the owner's approval. Six new tests in `test/work/ownCopies.test.ts` (naming; a worktree in `.worktrees` on a `mission/` branch with the thread started there and the repository status clean; a thread beneath sharing the copy and the opener staying in the workspace; refusals with no workspace and for a subfolder of a repository), written with the code, not seen red. Biome, the workspace typecheck and the full suite inside Claude Code's sandbox pass (2,014 passed, 54 skipped). Not checked: a live Claude Code side-quest opened with `ownCopy` committing unasked through Outlore (the probe used a plain `claude -p`); Codex and OpenCode in an own copy (their sandboxes write the folder only, so their commits probably still ask); the owner's own Own copy choice when opening a side-quest, the merge button and archive cleanup (not built).
Note: first recorded as CHG-0441 on `worktree/own-copy` (built 2026-11-17 on `6bc53e8`), whose number Code Mode core took; merged into `main` on 2026-11-18 and renumbered, its entry moved here because 0.1.7-Prototype was already released.
