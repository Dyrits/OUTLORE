# Changelog: 0.1.11-Prototype

## CHG-0522 · 2026-11-18 · Vibe sessions open: the HTTP MCP server is sent as ACP requires

Type: Code
Event: Delivery
Scope: Provider accounts (Mistral Vibe adapter)

Summary: The owner reported that a Vibe turn failed with "Invalid params". Driving the real `vibe-acp` 3.1.3 reproduced it: `session/new` (and `session/load`) answered `-32602 Invalid params` because the adapter sent Outlore's tool server as `{name, url}`, while ACP's `HttpMcpServer` requires `type: "http"` and `headers` too. `mcpServersOf` in `packages/service/src/harness/vibe.ts` now sends `{type: "http", name, url, headers: []}`. The stand-in `stand-in-vibe.mjs` now validates `mcpServers` the same way and answers `-32602` otherwise, so the adapter tests go red on the old shape (7 of 10 failed) and green on the new. CHG-0520's "wire shapes match a real vibe-acp" was an assumption that this disproves for this one field.
Reason: The owner: "the last turn failed: Invalid params".
References: `packages/service/src/harness/vibe.ts`, `packages/service/test/fixtures/stand-in-vibe.mjs`, [research note](../research/mistral-vibe-acp-2026-11-18.md).
Validation: against the real `vibe-acp` 3.1.3 (signed-in account): `session/new` with the old shape fails with -32602 naming `mcpServers.0.HttpMcpServer.headers`; with the new shape it opens, `session/set_config_option` for `mode`, `model` and `thinking` succeed, a prompt answers "pong", and `session/load` with the new shape succeeds. `vibe.test.ts` 10 of 10 pass, Biome clean. Not checked: the full suite, a thread in the app, the Outlore tool server actually answering Vibe's MCP client (the probe used an unreachable URL), permission requests and interrupts on the real server. Also seen: this Vibe lists thinking levels `low|medium|high` as a config option, so the handoff's open question about newer builds needs a re-look.

## CHG-0523 · 2026-11-19 · The send-delivery setting is removed; Steer and Interrupt get icons

Type: Code
Event: Agreement and Delivery
Scope: `packages/contracts` (`Settings.defaultDelivery`), `packages/service` (`settings.ts`, `messagesHandlers.ts`, `suggestions.ts`), `apps/app` (Settings Messaging card, `useThreadConversation.ts`, `threadConversation.ts`, `conversationEntries.tsx`, `composerIcons.tsx`), the thread-messaging specification and blueprint

Summary: The owner had no Steer or Interrupt on a queued message because their saved `defaultDelivery` was still "Steer" (CHG-0519 changed only the default of a fresh install), so every message was delivered at once and never queued. They said the setting "makes no sense to have" and asked for it removed. A message the owner sends, and one a suggestion continues, now always queues; Steer and Interrupt are chosen after sending. `SendMessage.delivery` stays, so a caller can still ask for Steer. Saved settings that still hold `defaultDelivery` decode and ignore it. Steer and Interrupt each get a small icon (a bending arrow, a skip mark) beside the word.
Reason: One behaviour with the choice made per message, as CHG-0519 meant; a setting that silently turned it off hid it.
References: CHG-0519, [thread messaging](../capabilities/thread-messaging/specifications.md#delivery).
Validation: Biome clean, `bun run typecheck` passes on all workspaces, `CI=1 bun run test` passes (267 files, 2,179 tests passed, 55 skipped). Not checked: the look of the icons and the card in a window or on a phone, and that an existing database with the old key opens in the running app (read from the schema only).

## CHG-0524 · 2026-11-19 · The summons and the owner's turn get their own corner marks; the teal dot goes

Type: Code
Event: Agreement and Delivery
Scope: `apps/app` (`shell/railRows.tsx`, `shell/railQuests.tsx`, `shell/railStyles.ts`, `shell/questListRows.tsx`, `foundation/theme.ts`, `foundation/palettes.ts`, `foundation/onePalettes.ts`)

Summary: The teal "your turn" dot read as confusing, so the owner asked for it to go and for a mark like the summons. A quest or errand that waits for the owner now carries a grey mark in its lower-left corner, 50% of the row's width and height; its dot stays grey. A summons carries its amber mark in the same corner, 75% of the width along the bottom and 75% of the height up the left side, rounded at the corner (replacing the full 1 px ring of CHG-0512). Both are overlays drawn over the row, since a border cannot cover part of a side. Sidebar quest and errand rows get a 1 px bottom margin so a mark does not touch the row below. Teal is removed from the four palettes. The quest list's lines keep a grey dot and no mark, since they have no summons ring.
Reason: The owner found teal confusing for "my turn" and asked for the summons' treatment in grey, with the mark on the lower-left corner for both.
References: CHG-0512, CHG-0513, [summons and your turn handoff](../../.agents/handoffs/2026-11-18-2105-summons-your-turn-errand-archive.md).
Validation: Biome clean on the changed shell and foundation files, `tsc` passes for `apps/app`, `CI=1 vitest run apps/app/test` passes (75 files, 550 tests passed, 6 skipped). Not checked: the look in a window or on a phone (the owner's look is pending), hover and selected states over the marks, and the full workspace suite.
