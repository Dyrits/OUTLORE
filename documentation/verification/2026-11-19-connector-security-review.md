# Connector security review fixes · 2026-11-19

Reviewed at the state after `f35dd295`: three findings accepted, each fixed with a regression that was first shown failing (see below), except where noted.

**Cross-origin redirect credential forwarding (`httpMcp.ts`).** The adapter's `fetch` followed redirects by default, so a 3xx answer from the connector's server (or something between) re-sent the key's header — `x-consumer-api-key` for Composio — to whatever origin the `Location` named, including another host or a plainer scheme. The adapter now sends `redirect: "manual"` and refuses any redirect answer (a 3xx status, or the opaque redirect of status 0 some runtimes give) with the class `Failed` and its own fixed words; no redirect is ever followed, so the header cannot leave the origin the catalog entry names. The regression spins two real local servers — the entry's, answering 301, 302, 307 and 308, and the target's, recording what it is sent — and checks the failure words, that the redirecting server saw exactly one request, and that the target saw none; a same-origin redirect and a keyless listing are refused the same way. A real `https`→`http` downgrade is covered by the same mechanism (no redirect is followed at all) but was not exercised against a TLS server, and no real Composio was contacted.

**Vault folder reachable by recursive search (`work/promptPolicy.ts`).** The refusal checked only whether a tool's literal path named something inside the Vault's folder, so Claude Code's own Grep or Glob — which run outside its command sandbox (ADR 0022) — could be rooted at an ancestor (`/`, the owner's home, the data directory that holds the Vault's folder) or at a link to one, and walk into the folder without naming it. A new `searchReachesVaultFolder` (vault/folderAccess.ts) resolves the search root through links, as far as it exists, and says whether the Vault's folder is at or below it; the prompt policy refuses a Grep or Glob whose root — the `path` given, or the thread's own folder when none is — reaches the folder, with the same words as before. The named-file rule for Read, NotebookRead and path-like patterns is unchanged. Unit tests cover the root being the folder, an ancestor, the disk's root, a link up, a relative climb, a sibling and a child; a live policy test refuses the parent, `/`, and a link to the parent, and still allows a search of the sibling `missions` folder and a rootless search (the thread's own folder, which the service places beside, never above, the Vault's). This was verified against the tool-input shapes only: no live Claude Code traversal was run, so whether some other field or tool spelling could reach the folder is not proven, only these paths.

**Stale denial-probe cache (`vault/vault.ts`).** The layer kept one probe report for the service's life, so a harness installed after its "not installed" answer — or a Claude Code upgrade past the version its stamp names — still stored a secret against a protection that no longer held. The report is now asked of the adapters afresh at every protection read (the Vault's section, and each storing and key move), serialized on a semaphore so two probes cannot fight over the probe's marker file, and still only when a protection check first needs it, never at service start. Two regressions through the whole service use a stand-in `claude` that changes under it: Claude Code appears after an earlier probe and the next storing refuses at once; Claude Code upgrades and the stamp goes stale, replacing refuses while the stored secret stays sealed and listed, until the owner runs the live probe again. The first version of the fix still froze each adapter's answer at the layer's start (`probeAll` built once); both regressions failed against it, which is why the effect now re-invokes `probeAll` per read. The cost: each protection read starts each installed harness's own short probe again (a `--version` and, for Codex and OpenCode, sandboxed marker reads), where the old code did so once.

When protection fails, new storings and key moves are refused (`AccessRefused`, naming the harness) and the Charter says so; existing records stay sealed and listed, and every harness's sandbox settings still deny the folder (claudeArgs, the Codex profile, the OpenCode wrapper) — turn admission consults nothing here, and no thread tool reaches the Vault's requests, so nothing per-turn needed gating. `refreshDenials` is gone from the Vault service: with nothing cached, there is nothing to forget.
