# The Vault keeps connector secrets in an encrypted file, the key in the operating system's secret store, and hides its folder from the harnesses' sandboxes

Drafted on 2026-11-16 for the owner's review, and revised the same day after a second opinion (CHG-0330) that found two blockers, both fixed below: a key file beside readable records, and a key lifecycle that chose a holder afresh at each start. The owner agreed the direction the same day (CHG-0327: encrypted records, the key in the operating system's secret store where the host can reach one and otherwise in a file only the owner's user can read, said plainly, and the store unreadable from inside the harnesses' sandboxes). The details below are mine and need the owner's confirmation. Nothing is built, and nothing here was run: every claim about a harness's sandbox is from its source, schema or binary, and each is listed under "Unchecked" with the probe that settles it. The behavior is in the [connectors specification](../capabilities/connectors/specifications.md#the-vault) and the design in the [connectors blueprint](../capabilities/connectors/blueprint.md).

## Decision

- **Where it runs.** In the host service, in a folder of its own (`packages/service/src/vault/`), not in Electron: the host runs as its own Node program ([0018](0018-host-service-runs-on-its-own.md)), so Electron's `safeStorage` is not there to call, and on Linux without a secret store it falls back to a hardcoded password (stated in the specification's technical notes from Electron's documentation, not rechecked today).
- **What is stored.** One record per secret: an identifier, the connector it belongs to, its kind (such as "API key"), when it was added, and its ciphertext. Encryption is AES-256-GCM through `node:crypto`, one random 256-bit key for the Vault, a fresh nonce per record, and the record's identifier and connector bound in as additional authenticated data, so a record moved to another connector does not decrypt. No library is added ([Modules and dependencies](../conventions.md#modules-and-dependencies)).
- **Where it is stored.** A file in a folder `vault/` below the host's data directory, mode 0700 for the folder and 0600 for the file. Not the SQLite file: the sandboxes below deny reading by path, and the database must stay readable by them as it is today.
- **Where the key is kept.** Behind one Outlore interface, `KeyCustody` (read, write, name what holds it), with an adapter per platform: macOS Keychain through `security -i` (the key goes in on standard input, never in a command line); Windows through DPAPI for the current user, from PowerShell, the protected key kept in the Vault's folder; Linux through the Secret Service with `secret-tool` (key on standard input) when it is installed and a session bus is reachable. Where none works at creation, a **key file** in the Vault's folder, mode 0600. The holder is chosen **once, when the Vault is created**, and written with the format version and a key identifier in a header file; every later start uses that holder alone and never tries another. If it cannot be reached (a locked Keychain) the Vault is **Locked** and stays as it is; if the key is gone or the identifier differs it is **Lost**; if a record or the header fails to authenticate it is **Corrupt**. In none of these is a key made again, a holder changed or anything overwritten. Moving the key is an explicit owner action that keeps the old key until the new rewrite is durable. The Vault says which one holds the key: "Keychain", "Windows account", "Secret service" or "Key file: anyone who can read your files can read it". Only the macOS adapter is run on the owner's machine in the first slice; the others are written to the same interface and are unverified until someone runs them.
- **Who reads it.** Only the service, only when a connector's tool is called, through a function that hands the secret to a callback and keeps no copy. A secret is held as Effect's `Redacted` value from the moment a request carries it, so a log line or an error that includes it prints a placeholder. It is never put in a harness's environment, arguments or configuration, never in a thread's context, and a stdio connector's child process receives none in the first slice.
- **Protected, or no secrets.** A key file lies beside the records, so it is no second layer. While the key is a key file, the Vault stores no secret unless the folder's read denial is **verified for every harness available on this host** (a probe, with a disposable marker, failing closed). *As first drafted, with the key in a secret store an unverified harness left only encrypted records readable and the Vault allowed it, naming the harness. **Amended 2026-11-19 (CHG-0531, CHG-0532):** the probe found the macOS Keychain item readable from inside every sandbox, so a secret store is no second layer on a sandboxed command's reach, and the rule applies to every holder a sandbox can read, which today is all four (Keychain, Windows DPAPI, Secret Service, key file; the last three unprobed, so counted as readable). It awaits the owner's confirmation.*
- **Hidden from the sandboxes.** The Vault's folder is denied to reading in every harness sandbox, by that harness's own mechanism (see the blueprint): Claude Code's `sandbox.filesystem.denyRead`, a Codex permission profile with a `deny` entry for the folder, and for OpenCode's wrapper a `file-read*` deny in the Seatbelt profile and a hidden folder in bubblewrap. Outlore's own policy also refuses a harness file read of a path in the folder. The keys of the folder are not an exception: the key file lives inside it.

## Why this reading

- **The sandboxes read broadly by default.** OpenCode's Seatbelt profile begins `(allow default)` and then denies writing and process information only (`openCodeSandbox.ts`, `seatbeltProfileOf`); bubblewrap binds the whole filesystem read-only. Codex's current setting for Outlore, `workspace-write`, has no read restriction in its policy shape (the 0.169.0 schema). Claude Code's sandbox reads broadly unless `denyRead` is set, and Outlore sets none; the [security audit](../security-audit/security-audit-2026-11-14-0233.md) records that as an open question for `~/.ssh` and `~/.aws` and notes that `architecture.md` and CHG-0208 disagree about it. This decision is the first use of read denial and does not answer that question; it makes the same mechanism exist.
- **Two layers, so one gap is not the whole loss, but only with a secret store.** A thread that reads the ciphertext learns nothing without the key, and a thread that cannot reach the key store learns nothing from the ciphertext. Where the key is in the Keychain and a sandbox cannot reach it, a missing deny on one harness leaves an encrypted file only. A key file in the same folder gives no such separation, which is why it needs the verified denial above.
- **The service is the one place that already holds the owner's authority.** It asks the owner, applies the switches and calls the connector, so a secret has no reason to leave it ([Connector secrets stay on the host](../requirements.md#privacy-and-data)).

## Limits, stated plainly

- **A command that leaves the sandbox can read the Vault.** It runs as the owner. With "Let threads run commands outside the sandbox without asking" (CHG-0295) on, nothing asks first. A Keychain item made through the `security` command lists that command as trusted, so it may be read without a prompt by any process of the same user (a property of that tool as I understand it; not run). The Vault cannot protect against the owner's own full authority, and its card says so while that setting is on.
- **A harness with no enforced sandbox** already asks about every action ([action-approval](../capabilities/action-approval/specifications.md)); a read of the Vault folder is among them.
- **A same-user process outside every sandbox** is outside this decision, as it is for the owner token ([token isolation](../verification/2026-11-14-token-isolation.md)).
- **Errors and echoes.** `Redacted` protects the value when formatted, not text after it is unwrapped into a header. The gateway therefore forwards no upstream error text and replaces the secret (raw, URL-encoded, base64) in anything it does pass on; see the blueprint.
- **Backups.** Whether the backup feature copies the data directory, and so the Vault, is not checked; it must not copy the key file with the records.

## Findings of the probes, 2026-11-19

Run on macOS with disposable files and one disposable Keychain item ([verification](../verification/2026-11-19-vault-read-denial.md)):

- **The folder's denial works** in OpenCode's Seatbelt profile (`(deny file-read* (subpath ...))`, last in the profile) and in a Codex permission profile (`extends :workspace`, a `deny` entry, `network.enabled`), with an outside control that reads the marker and a control without the rule that reads it too. Codex keeps what `workspace-write` allows (checked with `codex sandbox` and `thread/start`; no live turn).
- **The Keychain is readable from inside all three sandboxes** (`security find-generic-password -w` and `security -i`), Claude Code's included. The "second layer" above is false for sandboxed commands; the denial of the folder is the only protection, whatever the holder.
- **Claude Code's denial has no probe that needs no model**: its sandbox is applied only in a live turn. `denyRead` is enforced for commands in a Claude Code sandbox (a path in this thread's own list answered `Operation not permitted`); the rest is an opt-in live test.
- `security -i` adds, reads and removes an item with the key on standard input.

## Unchecked, to settle before the build

- That each sandbox really denies the folder (first, with a disposable secret and before any production storage): a probe under each harness, with an outside control that reads it and an inside run that cannot, as the [token probe](../verification/2026-11-14-token-isolation.md) did. Claude Code's setting is read in its 2.1.322 binary and its Read tool's treatment of it is not; Codex's permission profile is in the 0.169.0 schema and moving Outlore's Codex threads from `workspace-write` to a profile changes every Codex thread's sandbox, so it needs its own test and may be refused.
- That a sandboxed command cannot read the key from the Keychain on macOS under Claude Code's, Codex's and OpenCode's profiles.
- `security -i` as the way to add a key without it appearing in a command line (the manual page lists the interactive mode; adding an item through it is not run).
- The Windows and Linux adapters.

## Considered Options

- **Electron `safeStorage`**: rejected as the only mechanism; see Decision. It could be one adapter where the host happens to run inside Electron, which no feature may depend on ([0020](0020-terminals-run-in-the-host.md)).
- **A native keychain library** (`keytar`, `@napi-rs/keyring`): not rejected, deferred. It would let a macOS item be readable by the host's program only, which the `security` command cannot do, but it is a prebuilt native addon for every operating system, architecture and Electron or Node version, and `keytar`'s repository was archived when last I saw it (not rechecked). The `KeyCustody` interface lets one replace the adapter.
- **A key file only**: kept as the fallback, rejected as the default; it adds nothing against a process that can read the owner's files.
- **Each secret directly in the operating system's store**: rejected; the stores differ in what they hold and how they list, and one key with a file is the same on every platform.
- **A passphrase the owner types when the host starts**: rejected; the host runs unattended from a login service ([0018](0018-host-service-runs-on-its-own.md)).
- **Secrets in the SQLite file**: rejected; the sandboxes deny by path, so hiding them would hide the whole database.
- **A secret broker under another operating system user**: the strongest, rejected as far heavier than the first slice and than the owner's setup warrants.
- **Asking for the secret at each call**: rejected; it defeats unattended use and a Ritual's run.
