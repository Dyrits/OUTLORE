# Computer use lives in the host, behind Outlore's own `computer_*` tools, with Cua Driver as a replaceable backend

Drafted on 2026-11-16 for the owner's review; the owner decided the direction the same day (CHG-0320, then the quest's decisions: Outlore's own `computer_*` tools in the host, Cua Driver the preferred backend, a paired phone may look and approve but not control, no app blocked). Not built. The behavior is in the [computer-use specification](../capabilities/computer-use/specifications.md); the evidence is in two research notes, [Cua and computer use](../research/cua-computer-use.md) (Cua read at `5ee5974`) and [alternatives](../research/computer-use-alternatives.md). Nothing was installed or run, so every claim about a backend's behavior below is from its source or documentation, not from use.

## Decision

- **Where it runs.** In the host service, as the owner's logged-in user, on the host's real desktop. Not in the Electron main process, so the desktop app, the web app and every paired device have it ([Same features in every app](../requirements.md#access), [0020](0020-terminals-run-in-the-host.md)).
- **What a thread sees.** A small set of Outlore-owned tools, `computer_screenshot`, `computer_read_screen`, `computer_click`, `computer_type`, `computer_key`, `computer_scroll` and `computer_open_app`, defined once in the thread tool catalogue and served by Outlore's own MCP tool server, so Claude Code, Codex and OpenCode get them the same way ([0005](0005-thread-tools-over-mcp.md)). They are offered only while computer use is on and a backend is ready.
- **Who does the work.** One Outlore-owned backend interface (look, read, act, report the screen's state, report permissions) with **Cua Driver** (MIT) behind it on macOS, a separate program the host starts and talks to through its stdio MCP entry point (`cua-driver mcp`, which forwards to its own daemon), pinned to one tested version because its contract is marked experimental. A different backend, or a later browser or VM backend, replaces it without changing the tools, the approvals, or the specification.
- **Who decides.** Outlore, not the backend and not the harness. The owner decided the grain on 2026-11-16: approval is **per application**, and inside an approved application only for a **really sensitive action**, with nothing blocked outright. So: a per-app question with the screenshot attached, answerable from any device; a second, one-time question for a sensitive action inside an approved app (the list of what counts is a proposal in the specification: a terminal's commands, a secure field, system settings changes enforced by the host from the app and the field's role, and sending, deleting or paying left to the thread's own judgment, since Outlore judges no action by its words); a host-wide lock, a check of the screen's state before each call, and a keep-the-display-awake setting held only while a thread uses the computer. Cua Driver asks nothing about clicks today (its consent modes are an unshipped plan), so the host owns every approval.
- **A first slice with no backend.** A view-only screenshot of the host's display, on demand, to a paired device, through the built-in `screencapture`.

## Why this reading

- **Harness access forces it.** Outlore starts Claude Code with `-p` and `--strict-mcp-config` and passes only its own tool server; Codex and OpenCode receive the same and nothing else; the external MCP capability is unbuilt (`claudeArgs.ts`, `codex.ts`, `opencode.ts`, the [tool-and-skill-loading specification](../capabilities/tool-and-skill-loading/specifications.md)). Claude Code's built-in computer use "requires an interactive session" and is not available with `-p`. The three harnesses' own computer-use features are therefore not reachable, and Outlore's own tool server is the one route that reaches all three.
- **Approvals need Outlore's own screen.** A phone owner can decide only when they see what the thread sees. A pass-through would leave each harness's own question, with no screenshot.
- **The sandbox does not contain it.** An agent that clicks in Terminal acts outside every sandbox; the [action-approval](../capabilities/action-approval/specifications.md) model and [Approval per action](../requirements.md#safety) therefore need a capability of their own, which Outlore can only provide if the host executes the tools.

## Consequences for earlier decisions

- **[0012](0012-desktop-conversation-terminals.md) and [0020](0020-terminals-run-in-the-host.md): terminals.** Computer use follows 0020's rule that a feature belongs to the host and not to Electron. It also reopens 0020's fence: a paired device may open a terminal only inside a sandbox, but an owner who approves "Control Terminal" on a phone gives a thread a pointer and keyboard in the real Terminal app with the owner's full access. That is not new in kind (a paired device already answers "Run outside the sandbox", with the owner's full authority, [device-pairing](../capabilities/device-pairing/specifications.md)), but it is a second way past the fence, so a terminal's commands are a sensitive action in the second tier: each asks its own one-time question, never covered by Always allow for the app. Whether those approvals should need the host's own window is open in the specification.
- **[0017](0017-typescript-and-effect-no-rust.md): no Rust.** Read as its text reads: "Iskios's own code stays TypeScript with Effect". Cua Driver is a Rust program the host runs as a separate process and speaks to over stdio MCP, as the host runs the harnesses' own programs; Outlore writes no Rust and no Swift. This **reading is mine and needs the owner's confirmation**; 0017's rejection was of a Rust host and a split codebase, and does not speak of dependencies. What it does add is a third-party Rust binary to install, sign, pin and update, a release concern that 0017 never faced. The TypeScript SDK `@trycua/cua-driver` is a native addon and is not preferred (it adds a platform-specific native package, and the research read that the driver's grants belong to the driver's own identity, which a child-process boundary keeps clear).
- **[0018](0018-host-service-runs-on-its-own.md): the host on its own.** The host runs from a login service with no window, as the owner, and "while nobody is logged in the host does not run". Computer use needs more than a running host: a logged-in, unlocked, awake display. The existing **Keep this computer awake while threads work** holds off system sleep only, which "is not enough" in Cua's own words; computer use adds a separate **keep the display awake** hold, and a refusal when the screen is locked or the display is asleep. The host never unlocks the computer; unlocking, as Codex's locked use does with an Apple authorization plug-in, would be a larger step. A host with no window cannot show the system's permission prompts, so the Workshop shows what is missing and only the host's own window opens System Settings. Where the macOS grants live is also a consequence: Cua Driver's grants belong to its own app (`CuaDriver.app`), and the host's `screencapture` to the host's own program (inferred); whether grants survive an Outlore update is not checked.
- **[0003](0003-per-user-relay-carrying-all-traffic.md) and [0016](0016-shared-relay-on-the-owners-free-cloudflare-account.md): the relay.** A screenshot per request travels the encrypted channel like any message; a stream would be a different cost class and is not part of this decision. The free plan's limits were not measured for images, and are measured before the slice ships ([Nearly free to run](../requirements.md#budget)).
- **[0008](0008-drive-harness-tools-directly.md): drive harness tools directly.** The vendors' computer-use tools are model tools whose actions the caller executes (Anthropic, OpenAI, Gemini). Outlore calls the harnesses' command-line tools, not the models' APIs, so it cannot add those tools itself; it gives the harnesses its own MCP tools instead.
- **[Local data](../requirements.md#privacy-and-data).** What a thread sees goes to its model provider; the setting says so before it is turned on, and Outlore stores no image of a thread's steps.
- **A new setting set and a new status card** in the Workshop (the switch, the Screen view switch, the keep-awake hold, the permission and driver status), changeable only from the host's own window, and refused to a thread, Chronicler and a paired device.

## Unchecked, to settle before the build

- That Outlore's tool server and each harness's adapter carry image content from a tool; how an unsandboxed MCP tool call is asked by each harness at the default approval level.
- `screencapture` and the backend on a locked screen and an asleep display; the right check for the screen's state in a plain-Node host.
- How the host reaches the driver's daemon without launching it through a gateway that "changes the responsibility chain" for its macOS grants (the driver ships no LaunchAgent on macOS and says a raw `serve` outside its bundle is unsupported).
- Whether the grants survive an Outlore update; how the backend is installed.

## Considered Options

- **Pass an MCP computer-use server through to every harness**: rejected. It needs the unbuilt external-MCP capability; each harness would show its own approval, with no screenshot and no one lock; how an unsandboxed MCP call is asked is unverified; and the driver's experimental interface would be exposed to every harness. It would be the cheapest demonstration and the hardest to make safe.
- **Claude Code's built-in computer use, and Codex's computer use**: rejected. Claude Code's needs an interactive session and is not available with `-p`. Codex's is documented for its desktop app, and whether its command-line tool or app-server has it is unknown.
- **The vendors' API computer-use tools**: rejected. Outlore drives the harnesses' programs, not the APIs ([0008](0008-drive-harness-tools-directly.md)); the caller executes those tools' actions, so it would have to be Outlore's own executor, which this decision is.
- **Remote desktop (VNC, Apple Screen Sharing, RustDesk, Chrome Remote Desktop)**: rejected. It is a person-driven route that lets the phone take the pointer, which the owner did not want, puts control outside Outlore's approvals and audit, adds a second network path outside the one encrypted relay, and RustDesk is AGPL. It remains a tool the owner may use on their own.
- **A whole computer-use agent framework (UFO, Agent S, UI-TARS-desktop, browser-use, Open Interpreter)**: rejected. Each brings its own model loop and replaces the harness, which Outlore does not do ([0008](0008-drive-harness-tools-directly.md)); UI-TARS-desktop is archived.
- **The source-available and AGPL parts of Cua** (the Spaces apps, `cua-spacesd`, the streaming and viewer crates, the `cua-perception` model): rejected by [Fully open source](../requirements.md#licensing); they are FSL or AGPL. Only the MIT pieces are used.
- **Outlore's own input code** (a native module such as robotjs, a Swift or Rust helper): rejected. robotjs moves the real pointer, reads no accessibility tree and is pre-1.0; nut.js has no licence read and paid builds; a Swift or Rust helper of Outlore's own would break [0017](0017-typescript-and-effect-no-rust.md)'s one-language rule and cost far more than Cua Driver.
- **A VM first** (Lume on a Mac, a container elsewhere): not rejected, only later. It is the safer place for risky work and a natural second backend behind the same tools, but it does not let the owner operate the Mac they own, which is the stated goal, and it needs about 50 GB per macOS guest.
- **Unlocking the computer** (Codex's locked use, an Apple authorization plug-in that unlocks it for a task): rejected for now. The host refuses with a clear message and never unlocks; a larger step needs its own decision.
