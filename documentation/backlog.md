- **Open the https pairing link in the phone app, not built** (the owner's scope, 2026-11-17; CHG-0436, CHG-0437): the QR code holds the web link, so on a phone with Outlore installed, the system camera or a tap opens the web app in the browser, which pairs the phone as a browser, not the app. Opening the app from an https link needs verified app links, all on the relay Worker's domain `outlore.dyrits.workers.dev`: (1) Android App Links: the Worker serves `/.well-known/assetlinks.json` (package `app.outlore.mobile`, with the SHA-256 fingerprint of the release signing key, which the owner holds in repository secrets, CHG-0298; a Play-signed build adds Google's fingerprint) with `application/json` and no redirect, and the Expo config adds an `https` intent filter for that host with `autoVerify` (`android.intentFilters`); (2) iOS universal links: the Worker serves `/.well-known/apple-app-site-association` (no extension, JSON, no redirect, `applinks` with the app ID `<Team ID>.<bundle identifier>` and the path `/`), the config adds `ios.associatedDomains` (`applinks:outlore.dyrits.workers.dev`), and the app needs an Apple Developer account for the Team ID and the entitlement (also what an iOS build needs at all, which does not exist yet); (3) the web app of the relay stays the fallback for a phone without the app, so the Worker serves both the file and the page, and the app must read the code from the https link's fragment (the same `readPairingInput`, already done). Cost: a small Worker change (two static files in `packages/relay/public` or a route), about ten lines of config, a signing-fingerprint step in the release workflow so the file always matches the key, and a check on a real device per platform, because verification fails silently and the link then opens the browser. Android is free; iOS waits for the Apple account. Caveats: App Links verification needs the fingerprint of the key that signed the installed build, so debug builds do not verify; Android and iOS both skip the app when the link is typed in the address bar or opened from some in-app browsers; a fragment survives the hand-over on both systems, but this was not checked.
