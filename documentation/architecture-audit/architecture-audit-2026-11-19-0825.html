Problem: six sites each re-implement "run an Effect from a plain callback": capture everything, run outside the fiber tree. Work so launched is not supervised by the caller's scope — interrupting the loopback server or relay loop does not cancel in-flight handling — and remote/controller.ts:28's orDie turns an expected storage failure into a defect. Six copies of one wiring is a locality failure.

Solution: one small core/run.ts offering forkInScope/runInScope that tie the fork to the current scope and route failures upward; separately, bring ownRelay.ts's thrown-Stop control flow into typed Effect failures with CloudflareApi as the single plain I/O seam.

  • locality: the callback bridge is written once, supervised everywhere
  • leverage: six call sites learn two names
  • applies ADR 0010's "Effect wherever possible" to the one large non-Effect module — closes a gap, does not reopen the record
Decision-record note: applies ADR 0010 (CHG-0361) rather than contradicting it — its plain-by-nature list names the carrier/channel/browser seams these sites bridge, not these six Effect-escape sites.

Top recommendation

Candidate 2 — break the work folder's import ring at the commands seam.

The service's largest folder (104 modules, ~15.5k lines) is one 43-file strongly-connected component, so no file inside it is a stable seam — every other service-side deepening (candidates 1 and 3 included) assumes seams the ring undermines. Moving the FollowUps constructors to a leaf and injecting the runner's collaborators as layer inputs is the smallest change that starts making the graph acyclic, and it removes the double-runner workaround in threads.ts:259-267. Runner-up on the app side: candidate 5 (folder index.ts seams), which unblocks the sidebar hot spot work in candidate 6.
