Short answer to "is that an architecture issue?": yes, two of them. Neither is a bug today; both are why a feature that sounds small costs about 1,500 lines. Glossary terms used: Quest, Errand, Realm, Chronicler, Companion, Mention.

Problem. "A quest the owner can see" is re-spelled in about 25 queries, and the spellings have drifted: some skip `is_deleting`, mentions.ts uses <> 'Archived' where missionSummaries.ts uses = 'Archived', guildHall.ts and realmLifecycle.ts look at neither is_deleting nor the same endings.

Solution. Deepen one module that owns the quest kinds and exposes reading and fragment interfaces (visibleQuestsOf(sql, scope)); the raw flags stop being read outside it. mentions.ts already has the seed: isOpenQuestOf.

  • Locality: a new quest kind (companion) changes one module
  • Leverage: one interface, about 25 call sites
  • Tests hit one interface, with every kind as a case
  • Drift between the spellings becomes visible and settled once
  • Unblocks the Companion mention at about 35 fewer edits

No decision record forbids it. ADR 0015 (realms tied or not, one Borderlands) is the nearest and is not touched.

Problem. What a turn holds is spread over six modules and released in an Effect.ensuring that must list each one; a second run on the same thread would clear the first's one-time approvals and connector snapshot and overwrite its session id.

Solution. Key run state by a run key held in one scope, with the thread's session id and state written only by the main scope; the pool and the router take the run key from the scope instead of reading request.threadId.

  • Locality: adding a store touches the scope, not the runner
  • Leverage: steer, interrupt and cleanup behind one interface
  • A leaked allowance after a failed turn becomes one test
  • The scope is the test surface: two scopes on one thread
  • A Companion mention can run beside the main turn

Touches harness/ files that API-key work is editing; sequence after that batch. ADR 0005 (thread tools over MCP) and ADR 0008 (drive harness tools directly) are not contradicted.

Moving skills from / to $ today edited about 25 files and missed one: pendingMessages.ts still looked for skills only when the text held a slash, so a $skill without a path got no instructions. Found by this review, fixed with an end-to-end test.

Problem. The grammar of a mark lives in the contracts, the app and the service separately; a change to a mark has no single place to be made or tested.

Solution. One module in contracts describes each mark once (trigger, token, chip kind, delivery line, whether it grants reach); the composer, the chips and the delivery note read it. The @ Companion mark then becomes one more row.

  • Locality: a mark changes in one file
  • Leverage: one table, three readers
  • One test per mark covers type, chip and delivery
  • The stale slash guard could not recur

Smaller than 1 and 2 and independent of both; worth doing before @ is added.

Top recommendation

Candidate 2, the turn scope first: it is the one the Companion mention cannot work around, and it is what makes a second run beside a main turn safe. Then candidate 1, so a hidden quest kind costs one module instead of about 35 edits. Candidate 3 is cheap and can go in at any time.

With 1 and 2 in place, the Companion mention is a thin feature: a hidden quest kind, a scope beside the main one, the reply copy, and the @ row. Without them it is the 1,500-line change described in the thread-messaging blueprint.
