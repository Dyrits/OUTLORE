# Architecture

Outlore is a desktop application whose host service owns all data in one SQLite file and runs every thread through harness adapters. One Expo app is the interface everywhere: its web build runs in the Electron desktop window and in browsers, and the native build runs on Android. One relay Worker, on the owner's free Cloudflare account and shared by every installation, carries paired devices' end-to-end encrypted traffic. The first slice is built (batches 1–18 in `documentation/work-in-progress.md`), with the service, harness adapters, provider accounts, scoped lore, and desktop interface. Rituals and pairing between installed Outlore instances are built too. The web app's first step is built (CHG-0286): a browser with no desktop bridge pairs with a running desktop host and uses it, checked against a local relay and a locally served build; the relay serves the last deployed web build (CHG-0287). Push notifications, webhook triggers, and workflows are not built yet. Agreed and not built (CHG-0282, CHG-0283): the host service runs on its own and can keep running after the desktop app quits ([0018](architecture-decision-record/0018-host-service-runs-on-its-own.md)), and the relay serves a separate web build for each release ([0019](architecture-decision-record/0019-browsers-use-the-relay-served-web-app.md)). The terminals and host-side updates have moved into the host service (updates: CHG-0517; terminals: CHG-0644, [0020](architecture-decision-record/0020-terminals-run-in-the-host.md)), so no feature of the conversation depends on Electron, while the app's own window, updater and icon still do.

## Future multiplayer: open architecture questions

Multiplayer must eventually support both invited people joining one host's missions and collaboration across people's own installations. The single-user design below describes the first build. Its modules and data model must preserve the hosted agreements below and identify assumptions that would block future execution or synchronization across installations.

For now, each shared mission has one host installation that owns its authoritative state. Collaborators join from a browser or their own installation. Collaboration pauses while that host is offline. The user accepted this working choice on 2026-11-04, subject to evolution; replicated state and offline edits remain possible future changes.

The following agreements define the first hosted version:

For the first hosted multiplayer version, all agents run on the mission host. Each guest has one of two permissions: triggering agents or discussing only. Discussion-only guests write in discussions beneath messages. Their discussion messages enter agent context only when the host explicitly submits selected messages. The host may instead write their own conclusion. The user confirmed these choices on 2026-11-05 (CHG-0016). Automatic discussion summarization is deferred in the [backlog](backlog.md).

Only the host approves risky actions, grants standing permissions, and changes budgets. Guest-triggered work uses the host's provider account and counts toward the mission and global budgets (CHG-0017). Guest permission to trigger agents does not grant approval or budget authority.

When sharing a mission, a toggle controls whether its agents retain access to the host's selected MCP connections, skills, and lore. It is on by default, and applies regardless of who triggers a turn. With it off, all turns in that shared mission use only resources the host explicitly selects. Guests see shared conversations and agent results; resource settings, credentials, and unshared lore remain hidden. Agent replies may reveal information obtained through enabled resources. The user confirmed this access and visibility boundary on 2026-11-05 (CHG-0018).

Guests use a separate identity approved by the host; no central Outlore account is required. Each invitation is single-use and grants access to one mission, with discussion-only permission by default. The host may grant permission to trigger agents when inviting or later (CHG-0019). Opening an invitation creates a pending request with the guest's chosen name. The host verifies the person through a channel they already trust, then approves access; a name or possession of the link alone does not establish identity. An unused invitation expires after 24 hours, and the host may cancel it earlier or create a replacement (CHG-0021).

An invited guest sees the whole mission, including past conversations, all its threads, and results. Before sharing, the host sees that this is the scope of access. Removing a guest immediately blocks their access, cancels their queued requests, and stops turns they triggered that are still running. Completed results remain in the mission; removal cannot undo actions already performed. Changing a guest from triggering agents to discussion-only cancels their queued requests but lets turns already running finish. They retain discussion access and cannot start further turns. The user confirmed these choices on 2026-11-05 (CHG-0020).

- A paired device represents the owner. Guest access uses its own identity and mission grant; possession of a device pairing must not imply permission to all missions.
- Workspace paths and harness processes belong to the mission host in the first hosted version. Future execution across installations will need workspace identities beyond local paths.
- One host service owns mission state under the current working choice. If independently writable replicas are introduced later, they will require synchronization and conflict rules.

The first hosted version keeps mission documents and data on the host and transmits shared conversations and results to invited guests. Guest local copies are a future direction; their scope, synchronization, and retention rules remain to be designed (CHG-0021). Removing access cannot erase information a guest has already saved or copied.

Mission-state ownership is settled provisionally. Execution, guest discussion behavior, host authority, spending, resource access, guest identities, mission invitations, history access, revocation, permission downgrades, and host-held mission data are settled for the first hosted version. Future guest local copies and collaboration across installations remain design work. SQLite and the service boundary do not by themselves require replacement.

## Stack

- **Language**: TypeScript everywhere, in one Bun workspace.
- **Runtime**: Node for the host service; Bun for package management and scripts. No Rust ([0017](architecture-decision-record/0017-typescript-and-effect-no-rust.md)); Bun as the host's runtime is weighed in the backlog.
- **Effect**: Effect 4 in all code that is not UI: the host service, the relay, and the shared `channel`, `relay` client and `controller` packages. Plain by nature: the Noise code and `Session`, the `Carrier` seam, the browser-facing entry points, `pairedHosts` and pure helpers. In the UI only Effect Schema's decode and encode functions and `Match`. See [0010](architecture-decision-record/0010-effect-in-the-service-and-relay.md).
- **Toolchain**: Expo CLI with Metro builds the app. Vite+ is excluded. Vitest with `@effect/vitest` tests on Node; Biome lints and formats (CHG-0025).
- **Service host and transport**: Electron runs the service in a utilityProcess on its bundled Node; agreed instead, the host service runs as its own program on the desktop app's binary as Node, started by the desktop app or by a per-user login service ([0018](architecture-decision-record/0018-host-service-runs-on-its-own.md)). SQLite is reached through Effect's Node driver over `node:sqlite`. The app talks to the service over one authenticated loopback WebSocket; shared records are Effect Schema definitions in `packages/contracts` (CHG-0025).
- **Desktop shell**: Electron, an optional shell once the host runs on its own, kept for now with no Electron-only feature (CHG-0284). See [0004](architecture-decision-record/0004-electron-desktop-shell.md), amended by [0018](architecture-decision-record/0018-host-service-runs-on-its-own.md).
- **Installed app and development**: the owner runs a packaged "Outlore"; development and checks run as "Outlore Dev" with their own profile and data, so they never share the running app's window, lock, or database. See [0013](architecture-decision-record/0013-installed-app-apart-from-development.md).
- **Conversation terminals**: node-pty in the host service and xterm in the web composer, with sent transcripts persisted through ordinary owner messages; the desktop window opens the full login shell, and a paired device's screens open one through the service's requests, fenced in the OS sandbox while the host's switch allows it (CHG-0644, [0012](architecture-decision-record/0012-desktop-conversation-terminals.md), [0020](architecture-decision-record/0020-terminals-run-in-the-host.md)). The native phone app has no terminal surface yet. A terminal starts in the git worktree the thread's own tool calls last moved into, which the host infers from its `Bash` and worktree calls (no harness reports its folder) and offers as `ThreadView.workingFolder` only while it is a linked worktree of the workspace's repository; the app falls back to the own copy, then the workspace (CHG-0689).
- **Storage**: one SQLite file, with full-text search for lore; `sqlite-vec` later if semantic search is needed. See [0002](architecture-decision-record/0002-one-local-service-owns-all-data.md).
- **Harness integration**: each harness's command-line tool driven directly: Claude Code over its JSON stream, Codex through its app server, OpenCode and others through the Agent Client Protocol (ACP). See [0008](architecture-decision-record/0008-drive-harness-tools-directly.md).
- **Thread tools**: a local MCP server. See [0005](architecture-decision-record/0005-thread-tools-over-mcp.md).
- **Relay and phone hosting**: a Cloudflare Worker with one Durable Object per pairing, one shared by every installation on the owner's free account, carrying pairing, WebRTC signaling, and fallback traffic; desktop and web sessions upgrade to a direct WebRTC data channel (`werift` in Node, `RTCPeerConnection` in browsers) with a second Noise NK handshake inside it. See [0003](architecture-decision-record/0003-per-user-relay-carrying-all-traffic.md), amended by [0016](architecture-decision-record/0016-shared-relay-on-the-owners-free-cloudflare-account.md) and [0026](architecture-decision-record/0026-direct-webrtc-channels-with-werift-and-relay-fallback.md).
- **License**: Apache 2.0.
- One Expo app provides the UI for Electron, browsers, and Android, using `react-native-web` for the web build. See [0009](architecture-decision-record/0009-one-expo-app-everywhere.md).

## Parts

- The Electron desktop app starts the Node host service.
  The service owns the product records, runs the harness adapters and the Ritual scheduler, and hosts the MCP server that gives threads their tools.
  [ADR 0018](architecture-decision-record/0018-host-service-runs-on-its-own.md) describes the planned standalone host and login service.
- **Harness adapters**: a library inside the host service. Each one turns a harness's own protocol into one common event stream that the service stores as turns, and gives the harness the global and workspace MCP servers, the thread tools, and the skills in scope.
- **App**: the Expo app with every screen. It holds no product data and talks only to the host service's interface, directly on the desktop and through the relay Worker on a phone.
- **Desktop app**: the Electron shell that starts the host service and loads the app's web build. It serves device-pairing by showing the pairing code.
- The **web app** is the last deployed web build served as static assets by the relay Worker.
  It stores pairings in browser storage and uses `packages/controller` to open the encrypted channel to the host.
  The app and the host check each other's release before accepting a pairing.
  Phone layouts still need a device review, and [ADR 0019](architecture-decision-record/0019-browsers-use-the-relay-served-web-app.md) calls for serving a build per release.
- **Mobile app**. The same Expo app builds for Android arm64 with Hermes. The release workflow is configured to attach an APK signed with the owner's release key (CHG-0298). The app connects to a host, stores pairings in `expo-secure-store`, supplies `crypto` through `expo-crypto`, and identifies itself as a phone. A debug-signed APK built locally launched on the owner's phone (CHG-0443). The app also finds, downloads and installs a newer release's APK through a native installer module (`apps/app/modules/outlore-installer`, `apps/app/src/foundation/androidUpdates`, CHG-0460 and CHG-0461); an update check on a phone is still pending. Pairing and layouts still need a device check. Mobile terminals, iOS, and store distribution remain open. [APK verification](verification/2026-11-15-android-apk.md#follow-up-on-2026-11-17-chg-0443)
- **Relay Worker**: the Cloudflare Worker on the owner's account, shared by all installations (0016). Infrastructure for device-pairing and routine-running: it forwards encrypted traffic between the host service and paired devices without reading it, serves the web app, and is intended to forward webhook triggers to the host service. *(Status 2026-11-16: the relay carries pairing traffic and serves the last deployed web build; forwarding webhooks is not built.)* It owns no product data and queues nothing: each pairing's Durable Object (`roomCore.ts`, one Effect-based core shared with the Node relay the tests start) holds only the SHA-256 of the claim of the host that first took the room and its connections, and passes frames on unread. A room holds at most 8 clients and 1 MiB frames, and a connection's frame rate is capped; a gate counts connection attempts per source address (`limits.ts`, in memory, so approximate across Cloudflare locations). A host's claim travels in the WebSocket subprotocol, not the address; the address form is read, and logged, only until 2027-02-01 (`legacyClaimUntil` in `route.ts`) for hosts of earlier releases. The committed Worker bundle (`workerBundle.generated.ts`) is rebuilt with `bun run bundle` in `packages/relay`, and a test fails while it is stale.

### Inside the host service (as built)

Source layout (`packages/service/src`, CHG-0125): a folder holds modules that depend only on folders before it, and each folder's `index.ts` is its interface, exporting only what other folders use.
`core/` is the shared base (errors, changes, settings, store, spending, the local calendar, execution types, tokens, words), `harness/` the adapters and the tools that ask them (everything under "Harnesses and accounts" except `accounts.ts`), `lore/` the lore store and its policy (`loreTools.ts` sits in `work/`, beside the other thread-tool bindings), and `policy/` the permission patterns, quotes, and questions.
`connectors/` holds the catalog, the stored choices, who may use what, the connector gateway with its seams to the backends, the Vault and `work/` (CHG-0537), the generic host-side MCP OAuth 2.1 client in `oauth/` (RFC 9728, RFC 8414 / OIDC, RFC 7591 DCR, PKCE S256, loopback callback, and Vault-backed refresh; CHG-0732, ADR 0027), and, in `backends/`, the Streamable-HTTP MCP adapter (`httpMcp.ts`, CHG-0540; keyless entries and a header prefix such as `Bearer `, CHG-0730; MCP session initialization and `Mcp-Session-Id`, CHG-0732; the Wave 1 and Wave 2 entries live one per file in `entries/`, CHG-0731), the stdio MCP adapter over the shared line transport in `core/` (`stdioMcp.ts`, CHG-0541) and the one `connectorBackendsLayer` that opens each (`defaultBackends.ts`), Code Mode's tool and declarations, and the QuickJS executor (CHG-0441, ADR 0023).
`work/` holds the modules that call one another in a ring (threads, tree, lifecycle, missions, the Guildmaster, rituals, budgets, the tool server) and stays one folder until its own seams are settled; `service.ts`, `server.ts`, `main.ts`, and `index.ts` stay in `src/` as the entry points.
The files named below keep their names; find one by name under its folder.
The app groups features under `apps/app/src`.
The `shell` folder composes navigation and panes, while `foundation` holds shared platform and service-client code.
Tests mirror the folders under `test/`; shared fixtures stay in `test/fixtures/`.

- **Thread lifecycle** (`lifecycle.ts`): the only writer of a thread's state and blocker. Callers name a transition (start or end a turn, fail, hold in a turn or for a reason, release, stop, resume, recover at startup); each keeps the tree's rules, such as a parent left Waiting with nothing at work beneath it becoming Resting. It also works out the actions the owner can take on a thread.
- **Startup file cleanup** (`startupCleanup.ts`, run before Threads and the request handlers exist, and never alongside uploads): removes what an interrupted upload or deletion left, that is attachment rows with no message, attachment files with no row, and scratch folders of quests that no longer exist (a registered realm's folder is never removed); `recoverThreadStates` in `lifecycle.ts` returns threads left marked as deleting to Stopped. A file that cannot be removed is logged and retried at the next start, never stopping the start.
- **Waiting on the owner** (`attention.ts`): one way for approval questions and off-topic suggestions to ask inside a turn, wait without a time limit, and be answered or withdrawn.
- **Thread inbox** (`messaging.ts`): a thread's message history, its order, and what waits to be delivered; `activity.ts` records a mission's latest activity.
- **Thread tool catalogue** (`threadTools.ts`): each thread tool defined once, with its MCP listing, argument decoding, and whether it runs unasked derived from that definition; `threadToolHandlers.ts` answers each through the module that owns it, and `mcp.ts` is the transport.
- **Commands** (`commands.ts`): The thread layer supplies one runner for owner requests, thread tools, and turn events. A domain operation does its storage work and returns its follow-ups (`followUps.ts`), including whether owner-visible state changed, turns to cancel, threads and quests to wake. The runner commits it in one transaction, then announces the change once, cancels, and wakes, in that order, and does nothing of these when the transaction fails. Files are removed only after the commit: a failure removing a quest's scratch folder is logged and retried at the next start, and does not stop the attachments' removal or fail the committed deletion. Building blocks that run inside an operation's transaction still say "Callers run it in a transaction"; Approvals and Attention also announce changes that commit outside the runner.
- **Endpoints** (`endpoints.ts`): each thread's secret MCP URL, between Threads (which needs a URL to run a turn) and the tool server (which calls Threads).
- **Missions** (`missions.ts`, `missionDetail.ts`, `dashboard.ts`): starting a mission and its summary, what the owner reads of one mission, and the dashboard's list.
- **Realms and the Borderlands** (`workspaces.ts`): a realm is a `workspaces` row tied to a folder or, with a null path, to none; a quest's realm is its top thread's `workspace_id`, which also keys realm lore; a quest with no realm is in the Borderlands. Only a realm with a folder gives its threads a workspace to work in. See [0015](architecture-decision-record/0015-realms-tied-or-not-and-one-borderlands.md).
- **Lore** (`lore.ts`, `loreFading.ts`, `loreChanges.ts`, `loreDecisions.ts`, `loreProposals.ts`, `loreUndo.ts`, `loreViews.ts`, `loreTools.ts`): each thread's lookup scope and recall (scoped lore in full, global lore as an index), kinds and fading worked out when read, changes by threads (`loreChanges.ts`) and the owner's decisions on them (`loreDecisions.ts`), widening and narrowing proposals, undo, and what the panel and `search_intel` read, ranked and counted as uses. **The lore store** (`loreStore.ts`) is the only writer of `intels`, `intel_history`, and `intel_uses`: each named operation (save, correct, move, replace, pin, delete, restore, merge, count uses, undo, erase a thread's lore) records its history entry and fading steps itself, and an owner's deletion declines the lore entry's awaiting changes; the other lore modules keep only policy and reads.
- **Harnesses and accounts** (`harnesses.ts`, `harnessCatalog.ts`, `harnessProcesses.ts`, `lineProcess.ts`, `claude.ts`, `claudeArgs.ts`, `codex.ts`, `opencode.ts`, `fakeHarness.ts`, `execution.ts`, `harnessTools.ts`, `accounts.ts`, `runners.ts`): each harness is defined once in the registry (`harnesses.ts`: its adapter, sign-in and model reads, over the facts in `harnessCatalog.ts`), and `makeHarnessRouter` sends each turn to its thread's harness. **Harness processes** (`harnessProcesses.ts`) own each thread's process for every adapter: start or reuse by the adapter's restart key (model, effort where taken, working folder, account, access), idle close, interrupt with a grace period, close when a steered message was not taken in, and close all at scope end; each adapter keeps only its protocol over one line-per-JSON transport (`lineProcess.ts`) with two framings, Claude Code's stream-json and JSON-RPC for Codex (app server) and the ACP harnesses. **The ACP module** (`acpHarness.ts`) owns the Agent Client Protocol once for Vibe, OpenCode and the generic ACP providers: opening or reopening the session (`session/resume` where the provider's definition prefers it), the lost-session fallback, the read loop, permissions and the owner's questions, ask mode, usage and context, file edits, the refusal re-prompt, the starting context (in the first prompt, or as the system prompt where the agent takes it, as Antigravity does through `_meta.antigravity.systemPrompt.append`), and the tool server over HTTP, the stdio bridge, or the launch's own configuration; each harness is a dialect of small data and a few hooks (`vibe.ts`, `opencode.ts` with its sandboxed launch in `openCodeLaunch.ts`, and the provider definitions behind `acpProviders.ts`). A turn carries `askOwner`, bound to Approvals: Codex and OpenCode ask about their harness's permission requests in-process, and a failure ends the turn; `answer_prompt` stays on MCP only as Claude Code's `--permission-prompt-tool` and is listed only to Claude Code threads. `harnessTools.ts` asks each tool for its version, sign-in, and models, and opens its sign-in; `runners.ts` works out a new thread's harness, account, model, and effort from its opener. See [provider-accounts](capabilities/provider-accounts/specifications.md), [0005](architecture-decision-record/0005-thread-tools-over-mcp.md), and [0011](architecture-decision-record/0011-accounts-as-harness-folders.md).
- **Starting context** (`startingContext.ts`, with `turns.ts` for admitting, completing, and failing a turn): one module assembles a thread's starting context, its system part (working folder and the fixed thread, journal, lore, and approval instructions, no titles) and each turn's note (position line, journal, opener's messages, lore, budget line), and measures a thread about to be opened from the same sections, so the size warning counts what the harness receives. Titles stay in the note, so a rename never changes the system prompt (CHG-0058).
- **Budgets** (`budgets.ts`, `budgetViews.ts`, `budgetPeriods.ts`, `spending.ts`): stops and releases at limits, what the owner reads, and the release when a global period starts over. Spending rows outlive the threads and missions that spent them.
- **Local calendar and timed sweeps** (`core/localCalendar.ts`, `work/timedSweep.ts`): one pure module reads every day, day key, budget period and Ritual next run in the computer's local calendar, built from local fields so a change of clock for daylight saving moves no midnight and no time of day. One helper runs a background sweep: its cadence (run, wait until it is next due, optionally wake early on a change) and a single error boundary that logs a failed run and runs it again at its next time, never sooner than a minute later, so a transient `SQLITE_BUSY` no longer ends the Ritual scheduler, the budget-period sweep, auto-archive, inactivity Missives or the price refresh for the session. Each sweep still builds its own layer, so its fiber lives and dies with its own scope.

## Flows

- **Open a thread**: a thread calls `open_thread` on the MCP server, or the user opens one in the app. The host service checks the budget, records the thread beneath its parent, builds the starting context (the journal, the lore in scope, the request from the opening thread or user), and starts the chosen harness through its adapter.
- **Subagent as thread**: each harness adapter switches off the harness's built-in subagent tool where it can, so agents open subagents through `open_thread` and every subagent is a full thread; the harness's own agent definitions pass through as the thread's agent. Where a built-in subagent still runs, the adapter mirrors its events into a child thread beneath the one that started it. *(Status 2026-11-15: the adapters switch the built-in subagent tools off; mirroring is not built.)* A message the user writes there is queued; when the subagent finishes, the thread continues as a full thread from its history with that message, unless the user chooses to interrupt and continue it at once. See [0007](architecture-decision-record/0007-subagents-become-threads.md).
- A thread calls `send_thread_message` to send a message to a thread it can reach under the [messaging rules](capabilities/thread-messaging/specifications.md#who-can-message-whom).
  The service records the message, then tries to steer it into an active turn or start a turn for the recipient.
- The user talks with **Chronicler**, the app's assistant, in the desktop conversation panes or from the narrow-screen top bar.
  The code identifiers keep the former name, Guildmaster.
  The host service stores this conversation as a hidden quest, reusing quest turns, messages, spending, and cards while excluding it from ordinary quest lists, searches, and ending actions.
  For requests sent to it, Outlore finds a matching mission, or proposes a new quest as a card whose Create opens it, on the Companion of a tier from settings (CHG-0173); it opens none itself.
  The **New quest** action in a realm or the Borderlands starts an empty quest through the app's service interface.
  The service builds its dashboard context and notifies it when a mission it opened reports a result, needs the user, or fails.
  The expanded [role of Chronicler](capabilities/mission-coordination/specifications.md#what-guildmaster-does-itself) is agreed in CHG-0132; its additional tools (`create_realm` and `rename_realm` are built, CHG-0175) need design and implementation under the service-enforced authority in [ADR 0005](architecture-decision-record/0005-thread-tools-over-mcp.md).
- **Handover**: the user or a thread changes a thread's harness, agent, model, or effort. The host service ends the old harness session and starts the new one with the thread's full history from its turns, summarizing the oldest part only when the history exceeds the new model's context window. *Implementation status (2026-11-15): built narrower than this target. Only stored owner, thread and agent text messages are replayed (earlier images are named, not resent; tool calls and results are not), the oldest messages are dropped beyond half the new model's context window with an omission notice, and summarization is not built (see [thread handover](capabilities/thread-handover/specifications.md#current-replay-boundary--2026-11-15)).* See [0006](architecture-decision-record/0006-handover-replays-full-history.md).
- **Approval**: a thread calls `request_approval` before a risky action; a harness's own permission request arrives through its adapter, and Outlore answers it from the thread's permission mode (its own, or the Workshop's default). The host service pauses the turn, sets the thread to Attention, shows the question in the thread and in the dashboard's list on every device, and resumes with the user's answer. Allow covers that one action only; Always allow also stores a standing permission, which the host service puts in the starting context of every thread it covers.
- **Computer use** (drafted, not built; [computer-use](capabilities/computer-use/specifications.md), [0021](architecture-decision-record/0021-computer-use-in-the-host-behind-computer-tools.md)): a thread calls an Outlore `computer_*` tool on the MCP server. The host service takes the computer lock, checks that the screen is awake and unlocked, asks the owner for the app (with a screenshot of it attached, answerable from the host or a paired device) through the same attention path as approvals, and, for a really sensitive action, asks again; then it has the computer backend (Cua Driver, a separate program) do it and returns the result. A paired device's **Screen view** is one `screencapture` image sent over the encrypted channel, with no thread involved.
- **Budget**: each harness adapter reports spending events as the harness streams them. The host service totals them per mission, Outlore, and global period; at a limit it stops the turns under that budget through their adapters, sets the threads to Attention, and asks the user to raise the budget or stop. Each thread's starting context and turns carry one line on its budget use.
- The owner chooses a workspace folder with the folder picker.
  On a paired host the picker stays within the host's browsable roots.
  The service uses the chosen folder, an own-copy worktree, or the quest's scratch folder and checks before each turn that the folder still exists.
  The [workspace attachment specification](capabilities/workspace-attachment/specifications.md) describes cloning a repository when creating a realm and tracks the planned workspace tools.
- **Journal update**: a thread rewrites the briefing or adds a change log entry through its thread tools. The host service stores the change with its author thread and time.
- **Routine run**: the scheduler fires a timed trigger, or the relay Worker forwards a webhook and the host service verifies its signature *(webhooks are not built; timed triggers are)*. The host service then opens an errand beneath the Ritual with the routine's instruction, the report landing in the Ritual's conversation. A scheduled run that cannot start is not lost: it starts inside its own savepoint, so a failure leaves none of its writes, and the run is marked Failed with the reason on the Ritual's card and its thread; the next scheduled run is not blocked.
- **Pair a phone**: the desktop app makes a key pair and a room identifier and shows them as a pairing code: a link to the phone web app with the room and keys after `#`, which browsers never send to a server. The phone opens the link, connects to the room on the relay Worker, and both sides derive the shared key. The phone says the release it runs, and a host of another release refuses it before the code is spent. As built so far, the host shows a QR code of the web link `<web app address>/#<code>`, that link and the app link `outlore://pair#<code>`, and the code as text (CHG-0434, CHG-0435): the web app pairs by itself from the fragment (then clears it), the desktop app registers `outlore://` and asks the owner to confirm, and Add a host takes a code or a link (`readPairingInput`, `packages/channel/src/pairingLink.ts`; the QR matrix is drawn from `uqr`). The phone app registers `outlore://` and has a QR scanner in Add a host (`expo-camera`, in a `.native` file so the web build carries none), both asking before they pair and both unrun on a phone (CHG-0436, CHG-0437); the web link opens the browser, not the app, on a phone (backlog: App Links and universal links). Once a desktop or web device is connected to a host of the same release over the relay, `PathLink` and `directUpgrade` (`packages/channel`) negotiate a direct WebRTC data channel inside the encrypted relay session and run a fresh Noise NK handshake inside it, falling back to the relay automatically on failure or drop (CHG-0717, CHG-0718, [0026](architecture-decision-record/0026-direct-webrtc-channels-with-werift-and-relay-fallback.md)); the mobile app stays on the relay.
- **Phone notification**: the host service sends a notification with no content (for example "a thread needs your approval") through the phone platform's push service; the phone loads the details over the encrypted connection when opened.
- **Use from the phone**: the phone web app and the host service exchange encrypted messages over the direct WebRTC data channel when upgraded, or through the pairing's Durable Object over WebSockets as fallback (and always on the mobile app), in both directions, asynchronously.
- **Keep a screen current**: the host service announces what changed to every connected screen (the owner's window, a browser, a paired device) in `Changed` frames and streams the reply a thread is writing in `Draft` frames (`packages/service/src/core/sessions.ts`, wire shapes in `packages/contracts/src/frames.ts`). Both are held in windows so an open screen costs little while threads work (CHG-0719): the first change goes out at once and a burst after it is one more `Changed` frame carrying the latest sequence 250 ms later, so a screen refetches at most four times a second and always once after the last change. A reply's first `Draft` frame carries the text so far; the later ones, at most ten a second per thread, carry only the new text and the offset it continues (`offset` is absent on a whole text). The whole text is sent again to a screen that joins mid-reply and after every fiftieth frame, and the app keeps each thread's reply per connection, so a screen opened mid-reply starts from the text so far and a frame it missed is repaired by the next whole text. Measured by `packages/service/test/core/idleTraffic.test.ts`: a 6,000-character reply written in 3-character deltas cost 2,002 frames and 6,155,152 bytes before, 40 frames and about 9,600 bytes after. Over the relay each frame counts toward the free plan's Durable Object request limit, so frame counts matter as much as bytes.

## Integrations

- The host service uses the computer's installed command-line tools.
  **Workshop → Providers** offers to install Claude Code, Codex, and OpenCode through npm and Mistral Vibe through uv.
  It offers updates through each harness's own updater and refreshes availability afterward. See [provider accounts](capabilities/provider-accounts/specifications.md).
- **App updates**: the installed desktop app updates itself (see [app updates](capabilities/app-updates/specifications.md)). Agreed, not built: the host service takes this over, so any app can update a host and a background host updates with nobody at it ([0018](architecture-decision-record/0018-host-service-runs-on-its-own.md)). The desktop main process owns it (`apps/desktop/src/updates/`, wired in `apps/desktop/src/updateSetup.ts`): a controller keeps the owner's switch and the status, an updater per platform finds, downloads, and installs, and the preload bridge shows both to the screens; the host service and its data are untouched. macOS uses our own updater (GitHub's release list, a SHA-512 check against the release's `SHA512SUMS.txt`, a copy beside the installed app, and a detached script that swaps the two after quit), because Squirrel.Mac, under `electron-updater`, needs a Developer ID the build does not have; Windows and Linux use `electron-updater` on the `latest*.yml` files the release workflow publishes. Nothing installs unasked. Trust is HTTPS from the repository's release and the checksum from the same release: no signing key. **A paired device can ask the host to update** (CHG-0518): `ReadHostUpdate` and `UpdateHost` are shared requests; the service's `HostUpdate` coordinator (`packages/service/src/update/`) arms an install and runs it once no turn is running (it counts `turns` rows with status `running`), and reaches the updater through `HostUpdater`, which the desktop wires over the utility process's parent port (`parentPortUpdater.ts`; the main process answers in `apps/desktop/src/serviceUpdates.ts` from the `UpdateController`, with a forced check that ignores the owner's switch). A service with no parent has no updater and reports unsupported. A device of another release reaches the host on an update link (`resumeHost` with `acceptOtherRelease`, `/host/<id>/update` on the loopback server); the hello and resumed messages are unchanged.
- **Harnesses (Claude Code, Codex, OpenCode, ACP harnesses)**: the host service starts them as local processes, and exchanges turns, tool calls, and permission requests. A harness that is not installed or not signed in shows as unavailable when choosing one; a thread whose harness fails stops with an error, and the user can hand it over to another.
- **Providers**: reached only through each harness, with the user's own subscription or API key. Outlore holds no provider credentials of its own; an added provider account is a folder the harness signs in to with its own sign-in ([0011](architecture-decision-record/0011-accounts-as-harness-folders.md)).
- **MCP servers (global and workspace)**: configured in Outlore and passed to every harness, subject to the thread's selection. Importing existing harness configuration is deferred. Conflicting names ask the user. A failed external server produces a warning; failed Outlore thread tools put the thread in Attention with Retry. See [tool-and-skill-loading](capabilities/tool-and-skill-loading/specifications.md).
- **Skills**: read from existing global and workspace skill folders and thread installations. The narrower scope wins; within a scope the chosen harness's folder wins, then `.agents/skills`, then other harness folders. Enabled skills' names, descriptions, and locations are available at turn start; full instructions load when used, with supporting files read as needed. Changes apply on the next turn; installation through the app is deferred. See [tool-and-skill-loading](capabilities/tool-and-skill-loading/specifications.md).
- The host service uses the computer's `git` to create a worktree when an agent opens an errand with `open_thread` and `ownCopy`.
  The New realm form can clone a Git repository by URL. Merging an own copy through the app remains planned. See [workspace attachment](capabilities/workspace-attachment/specifications.md).
- **Cloudflare**: the owner deploys the shared relay Worker to the owner's account; users sign in to nothing. When the relay is unreachable, or its free daily limits are reached, paired devices on another network wait and reconnect, and webhook triggers are lost unless the sender retries.
- **Computer backend** (drafted, not built): Cua Driver (MIT, Rust), a separate program the host starts and talks to over stdio MCP, pinned to one tested version; it holds the macOS Accessibility and Screen Recording grants under its own identity. Outlore writes no Rust ([0017](architecture-decision-record/0017-typescript-and-effect-no-rust.md), [0021](architecture-decision-record/0021-computer-use-in-the-host-behind-computer-tools.md)).
- The host service's connector gateway serves installed connectors' tools through each thread's own MCP endpoint.
  It applies the connector's approval rules and reads credentials through the Vault. See the [connector specification](capabilities/connectors/specifications.md) for implementation and live verification status.

## Deployment

- The release workflow builds Electron installers for macOS (Apple Silicon and Intel), Windows x64, and Linux x64 when a version tag is pushed.
  The macOS build has an ad hoc signature and the Windows build is unsigned.
  See [build and release](../README.md#build-and-release) for the workflow and update assets.
- The same workflow publishes a release-signed Android arm64 APK on GitHub.
  iOS and app store distribution remain planned.
- The workflow deploys the relay Worker and web app after publishing the release.
  The relay serves the last deployed web build.
- **Environments**: local development, and the installed app from the published prereleases.

## Requirements

| Requirement | How the architecture meets it |
| --- | --- |
| Fully open source | All parts are in one Apache 2.0 repository. |
| Respect upstream licenses | New codebase with no OpenBot code; MausBot modules (only from outside `enterprise/`) and Paseo's relay code keep their Apache 2.0 license and NOTICE attributions, and MausBot's brand is not reused ([0001](architecture-decision-record/0001-new-codebase-not-a-fork.md)). |
| Nearly free to run | One shared relay Worker runs on the owner's free Cloudflare account, which stops instead of billing at its limits, so it costs the project and every user nothing; users need no account ([0016](architecture-decision-record/0016-shared-relay-on-the-owners-free-cloudflare-account.md), amending [0003](architecture-decision-record/0003-per-user-relay-carrying-all-traffic.md)). Its free limits are shared by all users and are not yet measured against real use. |
| Local data | The host service owns product data; the relay Worker holds only connection state and the hash of each room's host claim, and queues nothing. Webhook bodies pass through the user's own relay Worker. Future hosted guests receive shared conversations and results under the local-data exception; mission documents and data remain on the host. |
| Bring your own provider | Providers are reached only through harnesses with the user's own accounts. |
| End-to-end encrypted phone traffic | Keys travel only in the pairing code, after `#`; the relay Worker forwards ciphertext only. |
| Approval per action | Every approval question stops at the host service, which asks the user for each action and never reuses a single answer across actions or threads; standing permissions are stored only when the user chooses Always allow, and listed on the Permissions page. |
| Single user | The first build serves the installation's owner through one host service and one SQLite file. |
| Future multiplayer | The hosted agreements above define identity, invitations, mission history access, host execution and authority, spending, resource sharing, and permission changes. Guest local copies, execution across installations, and synchronization remain undesigned. |
| End-to-end encrypted phone traffic (notifications) | Notifications carry no content; details travel only over the encrypted connection. |
| Comply with provider terms | Harnesses sign in through their own tools (`claude auth login` and equivalents); the host service never reads or stores their credentials. |
| Pair by QR code from anywhere | The pairing code opens the phone web app, which reaches the host service through the relay Worker from any network. |
| Use from a browser with nothing installed | Partly met (CHG-0286): the web build pairs with a running desktop host from a plain browser, keeps the pairing across reloads, and uses the host's quests, messages, folders and terminals through the relay, checked in Chromium against a local relay (the terminal from a paired browser is checked against a stand-in sandbox, not yet hand-driven). The relay serves the build (CHG-0287); a pairing from another network to a real Mac is not yet seen; no background host or phone layout. The browser trusts the HTTPS site that serves the build, separately from the encrypted transport ([0019](architecture-decision-record/0019-browsers-use-the-relay-served-web-app.md)). |
| Nothing else to install | Met for paired devices, which reach a host through the relay with nothing but Outlore. Browser access keeps to it: no Tailscale or tunnel (CHG-0282). |
| Host can outlive the desktop app | Not met: the desktop app starts the service and stops it when its window closes. Agreed: with Keep running after quitting on, a per-user login service runs the host, with its own lock and a port-and-token file for local clients ([0018](architecture-decision-record/0018-host-service-runs-on-its-own.md)). |
| Same features in every app | Partly met (CHG-0644): conversation terminals run in the host service and reach the desktop window, the web app, and paired devices through the same requests ([0020](architecture-decision-record/0020-terminals-run-in-the-host.md)); host-side updates answer through the service ([0018](architecture-decision-record/0018-host-service-runs-on-its-own.md)), while the app's own updater and the theme's app icon still live in the desktop main process, and the native phone app has no terminal surface yet. The app icon follows the theme on each platform through a platform adapter, as do the window's own title bar and the connection. |
| Updates keep the host reachable | Not met: the desktop main process updates the app, and only while its window runs. Agreed: the host service installs updates, restarts only Outlore, and puts the previous version back if the new one does not start ([0018](architecture-decision-record/0018-host-service-runs-on-its-own.md)). |
