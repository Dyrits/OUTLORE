# Device pairing

Authorized by the owner on 2026-11-12 (CHG-0201): control one Outlore from another instance of Outlore, from any internet connection, with nothing for the user to set up and no cost to the owner or the users. A phone uses the same pairing later; the phone web app is not part of this first slice. Unsettled points are in the [draft](draft.md).

Terms: the computer being controlled is the **host**; any other Outlore connected to it is a **paired device** ([glossary](../../glossary.md#devices)).

## Behavior

- A paired device reaches its host from any internet connection, through the shared relay ([0016](../../architecture-decision-record/0016-shared-relay-on-the-owners-free-cloudflare-account.md)). The user needs no account with any service and deploys nothing.
- The relay cannot read what it carries: messages between a host and a paired device are end-to-end encrypted, and the keys travel only in the pairing code ([requirements](../../requirements.md#privacy-and-data)).
- A host accepts paired devices only while "Allow paired devices" is on in the Workshop; it is off by default. Turning it off ends every paired device's connection and stops new pairings, and keeps the pairings.
- The host shows a pairing code as text. A code works once and expires 10 minutes after it is shown. The Outlore app on another computer pairs by choosing **Add a host** in its host menu and pasting the code. A QR code of the same code comes with the phone.
- The host lists its paired devices in the Workshop. Each shows its name, its kind (desktop, phone or browser), when it was last active, and a **Disconnect** button. Disconnecting a device ends its connection immediately and forgets its pairing; it can pair again with a new code. A paired device stays paired until it is disconnected. A pairing whose token never reached the device — the connection dropped before the host could answer — leaves nothing on the host: the device is not listed, and its code is not spent. The same holds when the owner presses Disconnect, or turns pairing off, while a pairing is in progress: nothing is kept, and the code (while pairing is on) can be used again for the rest of its ten minutes.
- A paired device has the owner's full authority over the host: it steers threads, answers approvals, changes budgets and settings, and creates and moves quests exactly as the owner does on the host, except that the folders it may name are limited as below (CHG-0274). Only the host itself shows pairing codes and disconnects devices.
- The host keeps a name, defaulting to the computer's name, and the owner can rename it from the host or from a paired device, in the Workshop's **Computer name** card (Accounts section), no longer in Remote access; the same name labels the computer's own sign-ins (CHG-0257).
- The Outlore app on a computer has a host menu at the top left, like OpenBot's: it lists **This computer** and each paired host, marks the one in use, and switches the whole app to the chosen one, with the same screens and the same abilities as on the host. The data shown is the host's, not the computer's own, and choosing **This computer** returns to its own.
- Choosing a realm folder no longer opens the system dialog, on this computer or on a host. One picker runs on the host: a search field taking typed paths and ranking matches (exact, prefix, substring, then fuzzy; folders only), suggestions from folders the quests already used, step-in browsing through `BrowseFolders`, and a New folder flow (choose the parent, then name it). A search stays inside its root and follows a symlink only if it resolves inside that root; hidden folders, `node_modules`, build output and Git-ignored folders are not offered; a path typed exactly always resolves where the caller may go; at most two filesystem calls run at once, so a stuck drive cannot freeze the host.
- **Where a paired device may look** (CHG-0253, replacing the open root of CHG-0202): only under the host's **browsable roots**, which the host owner sets in the Workshop, in the card "Folders open to Outlore" (they start with the host's home folder; **Add root** and **Remove root**, host only, so a paired device cannot widen its own reach). A typed path, a browse, a search, a suggestion, and New folder outside the roots are refused or left out for a paired device. The same holds for every request that names a folder: starting a quest, creating a Ritual or a realm, listing skills, naming files with `@`, and choosing a realm on a suggestion are refused for a paired device unless the folder lies under a root or is already a realm the host attached (CHG-0274). The host's own window uses the same picker but may reach any folder, as the system dialog did (CHG-0035). Paseo sets no such limit (it searches the host's home folder and resolves any typed absolute path; checked 2026-11-13).
- A host that no longer knows this installation (it disconnected it) refuses it for good: the app stops trying, says "The host no longer knows this computer. Pair with it again.", and offers **Use this computer**; a host that is merely unreachable is tried again, ever more slowly (a second, then doubling to half a minute), because each try asks the relay, whose daily allowance everyone shares.
- While a host is shown, what only works on the computer the window runs on is off, never aimed at the wrong computer: `!` stays ordinary text (the terminal on a host is a later batch); the Workshop's remote access section says that paired devices are managed on the host itself.
- The relay says why it closes a connection, in a text frame sent just before the close (no host, room full, host left, replaced, claim mismatch, a rule broken), and the host and the app act on it at once; the close itself can reach a Node client ten seconds late.
- The owner may use a relay of their own instead of the shared one, never required: the Workshop's Remote access card says where the web app opens (the shared relay's address, always; an own relay does not serve it, CHG-0289) and which relay is in use, and **Use my own Cloudflare account** deploys the relay to the owner's Cloudflare account with one API token pasted into the app. The card names Cloudflare's token page and the "Edit Cloudflare Workers" template, and says before the token is used what is done: a Worker named `outlore-relay` is put on the account (and a workers.dev address if it has none). The token is used once and kept nowhere. A token that reaches several accounts is refused with the way to limit it to one; a Worker of that name that Outlore did not make is left alone; a failure leaves the relay in use as it was and says why. Once the new relay answers, the host uses it, pairing codes name it, and devices paired through the other relay are disconnected and pair again (their pairings are kept, and work again on returning to the shared relay with **Use the shared relay**); redeploying to update the relay changes nothing for connected devices. Only the host may do this.
- **A browser as a paired device** (CHG-0286): the web build opened in a plain browser, with no desktop bridge and no local service on that computer, shows a pairing dialog that cannot be dismissed until it has a host. The owner pastes a pairing code and names the browser (default "This browser"); the browser keeps the host's key, room and device token in its own storage, so a reload resumes the same host without a new code, and the host menu lists only the hosts it paired with (no "This computer"). The browser uses everything a paired device does, on the host's data: quests, messages, approvals, and the folder picker, limited by the host's browsable roots; what only works on the computer a window runs on stays off. A pairing code naming a relay on this computer is accepted only by a page served from this computer. The browser keeps its pairing in storage the site's own code can read; disconnecting it at the host revokes it (0019).
- **Releases** (CHG-0286, CHG-0309): the host tells its release when a device pairs or resumes. A desktop or web app of another release (or a host that tells none) is refused with "This web app is release A, but the host runs B. Open the web app of the host's release, or update the host."; nothing is kept for a pairing the app cannot use, and the link stops trying and does not offer to pair again, which cannot mend it. A host that disconnected this browser says "The host no longer knows this computer. Pair with it again." and the banner offers **Pair again**, which replaces that pairing.
- While the host is unreachable, the app says so and reconnects by itself; what the owner does on a paired device reaches the host only while it is connected.

- **Relay capacity** (CHG-0309): a full room has its own refusal: “The host already has as many devices connected as the relay allows. Close Outlore on one of them, then try again.” It is distinct from a host that is offline, and reconnecting later may help.

## Acceptance

- Two instances on one computer, each with its own data folder, one acting as host and one as paired device through a locally run relay: pairing with a code succeeds once and a second use of the same code fails; an expired code fails; the paired device shows the host's quests and a message sent from it reaches the host's thread; the host's changes appear on the paired device; Disconnect cuts the connection at once; turning off "Allow paired devices" cuts it too.
- On a paired device, typing a path finds a folder on the host and not on the computer in use; a folder is created on the host; a hidden folder, `node_modules`, and a symlink pointing outside the root are not offered; a typed path to one of them still resolves when it is inside the root.
- A browser with nothing but a pairing code (checked in Chromium against a local relay and a host service, with the web build served from this computer): pairs once and not twice with a code; keeps the pairing across a reload; shows the host's quests and steers its threads; searches and chooses a folder on the host and makes a realm of it; says when the host goes away and reconnects by itself when it returns; says so for good when the host disconnects it and pairs again from the banner; and refuses a host of another release, naming both. Test: `packages/controller/test/browserDevice.test.ts`; drive: [verification](../../verification/2026-11-15-browser-access.md).
- The relay's stored messages and logs contain no plaintext (checked by reading what the relay received during the run above).
- The same flow, run once against the deployed relay on the owner's account, from a second network, with the owner's go-ahead before deploying.
- The own relay, with a real token on a test account: a first deployment, a host that moves to it and pairs a second service through it, an update at the same address, the return to the shared relay, a refused Worker of the same name, and the token found nowhere in the host's database (done on 2026-11-12, CHG-0212).
- The free-plan limits of the relay are read from Cloudflare's documentation and measured against a typical session before the first release.
