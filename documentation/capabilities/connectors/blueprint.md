# Connectors blueprint

Status: proposed technical design, 2026-11-16, revised the same day after a second opinion (CHG-0330), for the owner's review, under the [first slice design](../../first-slice-design.md) and the [connectors specification](specifications.md) (CHG-0321 to CHG-0327). Nothing is built. Read from source on 2026-11-16: `work/mcp.ts`, `work/threadTools.ts`, `core/endpoints.ts`, `work/approvals.ts`, `policy/permissions.ts`, `policy/patterns.ts`, `harness/claudeArgs.ts`, `harness/codex.ts`, `harness/opencode.ts`, `harness/openCodeSandbox.ts`, `core/store.ts`. No harness was run. The Vault's storage is decided in [ADR 0022](../../architecture-decision-record/0022-the-vault-encrypts-secrets-and-hides-its-folder-from-sandboxes.md) (proposed).

## Shape

Two new folders in `packages/service/src`, after `policy/` and before `work/` (a folder depends only on folders before it, [conventions](../../conventions.md#layout)):

- **`vault/`**: the Vault service and key custody. Depends on `core/` only.
- **`connectors/`**: the catalog, the stored choices, who may use what, the gateway that serves and runs connector tools, and the two backends. Depends on `core/`, `policy/` and `vault/`. It does **not** import `work/`: the one thing it needs from there, asking the owner, comes in as a port (`AskOwner`) that `work/` supplies, so the tool server (`work/mcp.ts`) composes the two without a ring.

The tool server stays the only door. Each thread's secret endpoint (`core/endpoints.ts`) already binds a caller to its thread; connector tools are served from that same endpoint, in Outlore's one MCP server, under names `<connector>__<tool>` (for example `apple__list-events`). The harness adds its own `mcp__outlore__` prefix. One server per thread, one approval path, one place that knows the thread.

## `vault/`

- `Vault` service: `state`, `list` (connector, kind, added-at, never a value), `put`, `replace`, `remove`, `removeAllOf(connectorId)` (idempotent), and `withSecret(connectorId, kind, use)`, the only read, which hands the secret to a callback and keeps nothing. A secret enters as `Redacted` in the request and stays `Redacted` until `withSecret` unwraps it inside the callback. `Redacted` protects the wrapped value when it is formatted; once unwrapped for a header it is protected only by the rules under "Errors and secrecy" below.
- **One writer.** `put`, `replace`, `remove` and a key migration run one at a time through a single queue (a semaphore of one permit in the service), each reading the current file, changing it and replacing it by rename, so two requests cannot lose each other's change.
- `records.ts`: the file of records and AES-256-GCM sealing and opening (`node:crypto`), additional authenticated data = record identifier plus connector identifier. A write goes to a temporary file in the same folder and is renamed over the old one, so a crash leaves the old file.
- `KeyCustody` interface (`read`, `write`, `holder`) with adapters in `keyCustody/`: `macKeychain.ts` (`security -i`, key on standard input), `windowsDpapi.ts`, `secretService.ts` (`secret-tool`), `keyFile.ts` (the fallback). `holder` names what keeps the key, which The Vault's section shows.
- **The holder is chosen once, when the Vault is created** (the first secret), by trying the adapters in that order, and is then written down. A header file in the Vault's folder holds the format version, the holder's name and a random key identifier, and each record carries the key identifier. On every later start the Vault reads the header and uses **that** holder only; it never tries another. Its state is one of: **Absent** (no header: nothing stored; the next `put` creates it), **Ready**, **Locked** (the holder cannot be reached now, such as a locked Keychain; the Vault stays as it is and retries), **Lost** (the holder answers that the key is gone, or its identifier differs from the records'; connectors that need a secret show Needs connecting, and the owner removes and enters the secrets again), or **Corrupt** (the header or a record fails to decode or authenticate; nothing is overwritten and the owner is told). Never is a key silently made again, a holder silently changed, or a Locked or Corrupt Vault written to. A disk or permission failure on write is an error to the owner, not a fall-through.
- **Moving the key** to another holder is an explicit owner action: write the new key holder, read it back, rewrite the records and header under the new key identifier as one durable rename, and only then delete the old key. The old key stays until the rewrite is durable.
- **Protected, or no secrets.** A key file lies in the folder that holds the records, so it is no second layer: it counts only while the folder's read denial is verified for every harness available on this host (the probe below, run at start and kept per harness). `put` is refused, with the reason shown ("Not protected from Codex" and the like), while the holder is the key file and any available harness lacks a verified denial. With the key in a secret store, an unverified harness leaves only the encrypted records readable and `put` is allowed, but the Vault's section names the harness. This is distinct from the agreed limit that a command which leaves the sandbox can read the Vault.
- The folder and its modes are made at start (`0700`, files `0600`), checked as a plain folder all the way down in the way `openCodeSandbox.ts` `ownedFolder` does for the wrapped OpenCode's folders, so a link a sandboxed process planted is removed rather than followed.
- `Vault` exposes no way to list, return or log a value, and no thread tool, Chronicler tool or paired-device read reaches it.

## `connectors/`

**Catalog** (`catalog.ts`, data, one entry per connector): `id` (letters, digits and underscore: it forms the permission's identity), name, plain description, platform constraint (Apple: macOS), the backend (`http` with a URL and where the key goes, or `stdio` with a pinned command and version), the secret kinds it needs, the notice shown at install, and the **classification** of tools: a record from the tool's exact name to `Read` or `Write`, and for Apple apps the app each tool belongs to. A tool the catalog does not name is unclassified and asks. The server's own labels (an MCP `readOnlyHint`) are never read. A tool name from a server is offered only if it matches the catalog's name pattern (letters, digits, `-`, `_`, at most 64 characters), so a hostile name cannot be crafted into another tool's identity.

- **Apple apps**: `MrGo2/icloud-mcp` (CHG-0322), pinned, run as a stdio child by the host. Its tools that only read are `Read`; the rest are `Write`. Classification is by **exact name, after reading what each tool does in the pinned version's source**: a prefix such as `list-` or `search-` is a hint to look, not a rule, since a tool named for reading may still write. The names are taken from that version's `tools/list` when this is built and stored as a fixture with the app each belongs to; a test fails when the pinned version lists a tool the entry does not name, which makes it ask rather than run, so a version bump cannot make a write run unasked.
- **Composio**: a remote MCP server (`https://connect.composio.dev/mcp`, the key in a request header from the Vault). Its meta-tools run any action chosen inside the call, so execution is never `Read`: every call to an execution tool asks. The catalog names separately, by exact name and after reading what each does, any pure discovery tool (searching the toolkits, reading a schema) that may run unasked; none is assumed. Narrowing a session to read-only toolkits, the spec's open item, is checked then and changes nothing here until it is.

**Stored choices** (`connectorStore.ts`, one migration after `0044`, own tables, nothing else in `core/` changes):

| Table | Holds |
| --- | --- |
| `connectors` | `id` (the catalog id), `installed_at`, `is_enabled` (the global switch), `options` (JSON: Apple's chosen apps), `needs` (null, or the plain reason it Needs connecting) |
| `connector_choices` | one row per explicit choice: `connector_id`, `kind` (`Borderlands`, `Realm`, `Quest`), `workspace_id` (set for a realm), `mission_id` (set for a quest), `choice` (`On` or `Off`); Inherit is no row. A realm's and a quest's foreign keys cascade on delete, so a deleted quest forgets its choices and a moved one keeps them |
| `connector_tools` | one row per tool switched off: `connector_id`, `tool` (on by default means no row) |

**Removing a connector** spans two stores, SQLite and the Vault, which no transaction covers, so it is three idempotent steps that resume after a crash: (1) in one transaction, mark the connector `Removing` (unusable at once, its in-flight calls cancelled); (2) `Vault.removeAllOf`; (3) in one transaction, delete its rows and its standing permissions (the `standing_permissions` rows whose kind is the connector capability and whose pattern begins `<id>/`). At start, any connector still `Removing` resumes at step 2. A failure in step 2 leaves it `Removing`, shown as such with Retry; the connector is never usable again and its secret is not gone until step 2 succeeds, which the owner is told.

**Who may use what** (`availability.ts`, pure, unit-tested): `usableOf(connector, subject)` resolves: the global switch off is unusable, whatever any choice says; otherwise the quest's own choice if it has one; otherwise **the quest's placement**, which is its realm if it has one and the Borderlands only if it has none (they are alternatives, never a chain: a quest in a realm whose choice is Inherit never reaches a Borderlands Off); otherwise On. A realm's or the Borderlands' Inherit means the global switch. A quest's subject is its own mission and its top thread's realm at read time, so a move needs no migration; a side-quest is its quest; a Ritual's quest is an ordinary quest; **Chronicler** resolves with the global switch alone. A connector is usable only if also installed and not `needs`. A tool is offered only if its connector is usable and it has no row in `connector_tools`.

**Gateway** (`gateway.ts`, the `Connectors` service):

- `listingFor(threadId)`: the tool listing entries (name, description, input schema) of the thread's usable, switched-on tools, read from the backend's `tools/list` cached per connector and refreshed on install, on a failed call and at each turn start. `work/mcp.ts` appends it to `toolListingOf(...)`.
- `call(threadId, name, args)`, in this order, each step refusing with a plain sentence the thread reads: (1) the name resolves to a catalog connector and a tool of its cached listing, else "Unknown tool"; (2) the call is allowed, by the contract below; (3) classify: `Read` runs, anything else asks; (4) the question, through the port, names the connector, the tool in the catalog's words and the arguments as received, and carries Always allow; (5) allowed again, then run through the backend with the secret from `Vault.withSecret`; (6) sanitize and cap the text returned, and return it. Backend failures are handled as under "Errors and secrecy".
- **The timing contract.** Every call has a **unique invocation identifier** (the `(connector, tool, thread)` tuple can name several calls at once) and is **registered with its cancellation handle before** policy is read, so a switch change that commits meanwhile finds it. A switch change takes a new, increasing **policy revision** in the same transaction; a call remembers the revision it read, and is allowed again after the owner's answer and **immediately before dispatch** by comparing with the current revision and re-reading policy when it moved. Each turn takes a **snapshot** of the thread's usable tool names at its start (and `listingFor` answers from it); a call is allowed only if its tool is in the snapshot **and** was not revoked at a revision later than the snapshot's, so switching a tool off and on again during a turn does not bring it back before the next turn, and switching one on does not add it. A cancelled call answers "off for this thread" and its open question is withdrawn.
- **What cancelling cannot undo.** Cancelling an HTTP call stops Outlore waiting; it cannot recall a request already sent. When a `Write` was dispatched, the cancelled answer says "stopped; the action may already have happened", and **no uncertain write is ever retried automatically**. A `Read` may be retried once on a network failure.
- **Asking**: `work/` supplies the port by adding one method to `Approvals` (`askToolUse`), built on the same `ask` and `record` as `requestApproval` (`work/approvals.ts`): an `Asked` of kind `Approval`, source `Thread`, `permission` = a new capability `useConnectorTool` ("Use a connector's tool") added to `policy/patterns.ts`, `pattern` = `<connector>/<tool>`, and a lookup through `findCoveringPermission(threadId, pattern, capability)` first. The capability makes the permission its own kind, so a connector permission never covers a command and a command's never covers a connector tool; the pattern is the connector's id, a `/` and the tool's exact name (a connector id has no `/`, so it splits one way only). `matchesPattern` already compares a saved pattern literally, as audit SA-10 required, so no new matching is needed. The permission is saved in the thread's workspace, or its quest when it has none, and widens from the Permissions page, as today. One question per call; the question's words are built by Outlore from the catalog, never from the server's text.
- **Stopping at once**: a switch change (global, realm, Borderlands, quest, tool, or a chosen Apple app) is a command in `commands.ts` whose follow-ups name the invocations to cancel, as it already does for turns; after the transaction commits, each registered invocation the change covers is interrupted.
- **Errors and secrecy.** A backend failure is mapped to a public class and the raw upstream text is **never** forwarded to the thread or stored: `Disconnected` (credentials rejected, permission refused; sets `needs` and shows Needs connecting), `Unreachable` (a warning line, no `needs`), `InvalidArguments` (the thread's own malformed call; a fixed sentence and **no effect on the connector's state**, so one bad call cannot make a connector unavailable everywhere), `Failed` (anything else; a fixed sentence). Any successful result and any message Outlore does pass on has every occurrence of the secrets it used (raw, URL-encoded, base64) replaced by `[redacted]` before it leaves the gateway, as a last guard: an upstream that echoes the key in another form is why errors carry no upstream text at all. Which existing path carries the warning line is open, below.
- A Ritual's run waits in Attention like any call; nothing here has a time limit (the tool server's keep-alive already holds a long call, `mcp.ts`).

**Backends** (`backends/`): one `ConnectorBackend` interface (`listTools`, `call`, `close`), and two adapters, written over the service's existing line transport (`harness/lineProcess.ts` is the model, but it lives in `harness/`, before `policy/`; a small shared piece moves down to `core/` as the conventions ask): `httpMcp.ts` (Streamable HTTP, a header key from the Vault, one request per call) and `stdioMcp.ts` (a child of the host, started on first use, closed when idle, restarted on failure, given no secret and an environment reduced to what it needs). A fake backend in `test/fixtures/` implements the interface for every test.

**Apple apps enforced** (`connectors/appleApps.ts`): the chosen apps (`connectors.options`) are enforced in two places: `listingFor` offers only tools whose app is chosen, and the gateway checks the tool's app again at the call and before dispatch (the timing contract); turning an app off is a switch change that cancels that app's in-flight calls.

**Apple permission** (`connectors/applePermission.ts`): macOS grants Automation to a program, and the program that talks to Calendar is the connector's own child process, not the host. So the permission is requested and checked **through that same process chain**: the host starts the pinned stdio child as it will at run time and calls one harmless read tool of each chosen app (listing calendars, say) through it, and reports `Allowed`, `Not allowed` or `Not asked yet` from the outcome. An `osascript` run by the host directly would prove a different program's grant. The request is refused unless it comes from the host's own window, through the origin `requestContext.ts` already gives each owner request. Which program macOS names in its prompt when the host runs from a login service rather than the desktop app is not known; see below.

## Owner requests and the app

- **Contracts** (`packages/contracts`): `ConnectorCard` (catalog fields, state, global switch, tools with class and switch, the Borderlands' choice), `ConnectorChoices` for the realm and quest panels, `VaultEntry` (connector, kind, added-at, holder), and owner requests `InstallConnector`, `RemoveConnector`, `SetConnectorSwitch` (global, realm, Borderlands or quest, with On, Off or Reset), `SetConnectorTool`, `PutSecret`, `ReplaceSecret`, `RemoveSecret`, `RequestApplePermission`, `ChooseAppleApps`. The secret field is `Schema.Redacted`; the request is excluded from the recorded owner words and from change announcements, and is never an input to Chronicler's `read_control_history`.
- **Authority**: all of these are owner requests (`requestAuthority.ts`): refused to a thread, to Chronicler and to a Ritual. No thread tool is added (specification, External contract).
- **Paired devices** send them through the encrypted connection as any owner request; the one refused there is `RequestApplePermission`.
- **App**: the Charter place (`apps/app/src/shell/placeCatalog.ts` placeholder) gets a `connectors/` folder in `apps/app/src` after `settings` in the folder chain (the chain is `…conversation`, `settings`, `shell`): cards with a Tools list, the Needs connecting line, install notices, and the Vault section (entering, replacing and removing; the holder line). The realm and quest panels list installed connectors with their On, Off, Inherit controls. The thread panel's tools line (right sidebar) reads `threadPanel.ts`. A paired device shows the same screens.

## Keeping the Vault unreadable from inside a sandbox

By harness, each with its own probe (see the ADR's Unchecked):

- **Claude Code**: `sandbox.filesystem.denyRead: [<vault folder>]` in the settings the adapter already writes (`sandboxSettingsOf` in `claudeArgs.ts`); the folder is in the restart key. Claude Code's own Read, Grep and Glob tools run outside the command sandbox, so Outlore's prompt policy (`work/promptPolicy.ts`) also refuses any such call whose path lies in the folder, after resolving links.
- **Codex**: replace `workspace-write` with a permission profile that keeps today's rules and adds a `deny` entry for the folder (the 0.169.0 schema has `read`, `write` and `deny` entries for a path or a glob). This changes every Codex thread's sandbox. If the profile cannot keep today's behavior, Codex keeps `workspace-write` and its denial stays **unverified**; then, by the rule in the Vault section, a key file is refused as a holder, and a key in a secret store is accepted only with the Vault's section naming Codex.
- **OpenCode**: in `seatbeltProfileOf`, `(deny file-read* (subpath (param "V")))` after the allow, passed as a parameter like the writable folders; in bubblewrap, `--tmpfs` over the folder. A test mirrors the token-isolation test: an outside control reads the folder, the wrapped process cannot.
- **The probe and its use.** Each adapter reports whether its harness's denial is verified, from a probe at start that tries to read a marker file in the Vault's folder from inside that harness's sandbox (a disposable marker, never a secret) and fails closed: not run, not verified. The Vault's `put` rule reads that report. The first build step runs these probes with a **disposable secret only** and stores no real secret until they pass.
- **A harness with no enforced sandbox**: nothing to add; every action there already asks.

## Seams and tests

- **Fakes, never mocks** ([conventions](../../conventions.md#tests)): a fake `ConnectorBackend` with scripted tools (reads, writes, a failing one, a slow one, an unclassified one); a fake `KeyCustody` (and the real macOS one, skipped where `security` or a Keychain is unavailable, as the Seatbelt tests are); the three fake harnesses and the fake clock; a real SQLite in a temporary folder; a temporary Vault folder.
- Further Vault tests: restart with the same holder; the holder unavailable (a fake store that fails, then recovers) leaves the Vault Locked and writes nothing, and never makes a new key; a Lost key and a Corrupt record each stop at their state and overwrite nothing; a key migration interrupted at each step keeps the old key until the rewrite is durable; concurrent `put`, `replace` and `remove` each keep every record. An **echoing backend** (a fake that returns the key in an error, a result, a redirect and a header echo, raw and encoded) shows no secret reaches a thread, `needs`, a log or the Vault listing. The Vault's secrecy is tested as a property: put a distinctive secret, run a turn that uses it through the gateway, then search every conversation, journal, lore entry, log line, tool result, device reply and relay frame the test can reach for it, and the file for it in clear. The same search runs after `remove`.

## Order

1. **The read-denial probes, with a disposable secret.** Before any production storage: the three adapters' denial of the Vault's folder, the Keychain read from inside each sandbox, and `security -i`, each with an outside control. It is first because the whole design rests on the sandbox claims, the least checked part; a failed probe changes the ADR before anything depends on it. Authorized separately from the build.
2. **The Vault.** Records, header and key lifecycle, key custody (macOS Keychain and key file), the tests above, and the denial in the three adapters. No real secret is stored until step 1 has passed for the harnesses the rule needs.
3. **The gateway with a fake connector.** Catalog, tables, availability, listing, call, asking, stopping, owner requests and contracts, with the fake backend. Provable on the three fake harnesses.
4. **The backends and the first two connectors**: http MCP and Composio; stdio MCP, Apple apps, its permission. Real harness conformance runs.
5. **The app**: the Charter, panels, the thread panel's tools line.
6. **Code Mode**: its core was built first, at the owner's choice (CHG-0441, [ADR 0023](../../architecture-decision-record/0023-code-mode-runs-in-quickjs-inside-the-host.md)), in `connectors/` (`gateway.ts` holds the `ConnectorGateway` interface `listingFor` and `call` that this blueprint describes, with a layer that offers no connector until slice 3; `codeMode.ts`, `codeRunner.ts`, `codeExecutor.ts`, `codeTypes.ts`). Slice 3's gateway replaces `noConnectorsLayer`; the Charter's Code Mode switch is built (CHG-0444, `apps/app/src/charter/`); what remains here is the rest of the Charter (slice 5) and the check that a run's calls follow the turn snapshot.

## Requirements

| Requirement | Design |
| --- | --- |
| Connector secrets stay on the host | `vault/` only; `Redacted` from the request to the callback; the sandbox denies; no read API; the property test. |
| Local data | Only what a tool's call carries leaves the host; install notices name Composio's and the model provider's reach. |
| Approval per action | One question per non-read call, through `Approvals`; a permission is per tool and its own capability kind. |
| End-to-end encrypted phone traffic | A secret typed on a device is an owner request over the encrypted channel; never relayed in clear, never recorded. |
| Nearly free to run | Each owner's own account pays; no service of the project. |
| Fully open source | The catalog entries name MIT servers, and a test keeps each entry's licence field consistent with the review that chose it, which proves the metadata, not the requirement. A hosted backend (Composio) is an opt-in third party service judged in the specification, not by a test. |
| Same features in every app | All of it is in the host service; the apps only draw it. |

- **The Composio notice and read-only narrowing**, and Composio's exact tool names, when it is built.
