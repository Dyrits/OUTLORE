# Conversation panes blueprint

Status: the desktop revision is built (CHG-0565 to CHG-0567). The original plan below records the earlier batches. See the desktop revision for the current design. Chronicle attention and History (CHG-0569) and phone navigation are pending.

## Starting point for the original batches

- `shell/shell.tsx` (453 lines) lays out, left to right: `Sidebar` (width, `EdgeResizer`, ⌘B toggle), the page (`props.children`), the quest panel column (`QuestColumn`), the Companions column, and Chronicler's column (`ChroniclerColumn`, `shell/chroniclerDock.tsx`). Below 820 px it shows the page alone with a menu screen and a Chronicler card. Widths are remembered in `shell/railStorage.ts`.
- `shell/appScreen.tsx` shows one destination. An open quest is one `Conversation` (`conversation/conversation.tsx`) for the quest, with the selected thread chosen by `selectedThreadId` and `onSelectThread`; its errands are picked in a tree, not shown side by side.
- `conversation/entries.ts` already builds `ThreadOpened` entries (an errand opened beneath the thread) into a conversation's feed; `conversation/useThreadConversation.ts` reads one thread's conversation.
- Chronicler is one permanent thread (`conversation/guildmaster.tsx`, `work/guildmaster*.ts`, `isGuildmasterThread`), with a realm hint (`guildmasterRealm`) for its next message.
- `ThreadSummary` (`packages/contracts/src/records.ts`) has `parentId`, `depth`, `isOpenedByAgent`; it has no anchor message. `records.ts` is 504 lines of a 512 hard limit, so new types go in a new contracts file.

## Batches

Each batch ends with Biome, typecheck and the suites; the owner's look comes after batches 1 to 3, which are the first usable layout.

1. **Overlay sidebar** (app only, no service change). A pure `shell/sidebarMode.ts` (modes `overlay`, `docked`; side `left`, `right`; stored keys in `railStorage.ts`) and a `shell/sidebarOverlay.tsx`: an edge hot zone with an open delay, close on leave, on choosing, on Escape, kept open while `questDrag` is dragging, the existing ⌘B shortcut and the top bar button for opening. The overlay renders the existing `Sidebar` over the panes with no layout push; docked keeps today's frame. The side and mode are Settings choices (Look card). Test seam: the mode and timing rules as data in `test/shell/`; the drag rule against `questDragTypes`; a window run for the hot zone (the hover cannot be unit-tested).
2. **Pane chain** (app only). A pure `shell/paneChain.ts`: from a chain of pane ids, a window width and the remembered state, it returns the visible panes (at most four, each at least its minimum width), the folded strips, equal shares, and the effect of open, fold, unfold and close; a longer chain shows the last four and folds the earlier ones. A `shell/paneHost.tsx` renders it with the `EdgeResizer`. A `ThreadPane` renders one thread's conversation from `useThreadConversation` (verified in batch 2: the conversation's feed and composer mount per thread, `ThreadPane` already took one thread's detail; it is now in `conversation/threadPane.tsx`); the quest and its errands become panes, opened by the `ThreadOpened` entry's reply line and by the sidebar (which opens the whole chain; as built, the chain is the path in the thread tree to `openThread`, so `navigation.ts` and `location.ts` did not change). The details panel stays where it is and follows the pane last pressed. Test seam: `paneChain` as data (widths, overflow, folding, closing and reopening), navigation events building the chain, and a window drive of a quest with two errand levels.
3. **The Chronicle as the first pane** (built, CHG-0564: the chain's first slot is the Chronicle, `shell/chronicle.tsx`; a quest Chronicler proposed is tied to the *proposal card*, not to a message: the `suggestions` row holds the suggesting thread, `targetMissionId` and `resolvedAt`, and the card stands just after the first reply written at or after `resolvedAt`; the receipt in `guildmasterProvenance.ts` is for structural actions and carries no message id; quests the owner started directly have no entry in the Chronicle yet, since the quest list holds no opening request and no `openedAt`, which batch 4's anchor and batch 6's events give). Chronicler's conversation (`ChroniclerConversation`) leaves its dock and becomes the first pane of the chain; `chroniclerDock.tsx`, the expand control and the narrow-window card are removed (the specification's *Supersedes*). Quests appear under their origin message as reply lines (the quest's `openedAt`/first message is the origin: *to verify* which message a quest created from Chronicler's proposal is tied to; the proposal receipt in `guildmasterProvenance.ts` may carry it). Test seam: the pane chain starting at the Chronicle, and the reply line's data from the quest list; a window drive.
4. **Reply and the errand anchor** (contracts, service, app). New contracts file `threadAnchors.ts` with a `ReplyToMessage` request (the message id, the text, an optional Companion) and an optional `anchorMessageId` on the thread record (a migration adds the column; old rows read as no anchor, shown as today's card). The service starts a quest (when the message belongs to a main conversation) or an errand (a quest's only: an errand's pane has no Reply, CHG-0558), refuses a second reply to a message that has one by returning the existing thread's id, and sets the anchor. Agent-opened errands get a distinct agent reply written by Outlore from the `open_thread` call. The reply retains the triggering message and carries the anchor. The app adds Reply beside Comment (`conversation/commentable*.tsx`, web build first; a phone shows it as a menu action). Test seam: service requests against the fake harness (quest from a channel message, errand from a quest message, duplicate reply, refusal in an archived errand), and a window drive.
5. **Channels** (service, app). A Chronicler conversation per realm and one for the Borderlands: a table of channel threads keyed by realm (or none), created on first open, found by `isGuildmasterThread` generalized to "a Chronicler thread"; its context is the realm's lore and, in the Borderlands, the global lore only (the existing lore scoping in `work/startingContext.ts`); its Companion uses the existing Companion setting per thread. A channel opens from the sidebar's realm row. The Chronicle stays the app-wide thread. Test seam: lore in a realm's channel context against the Borderlands', one channel per realm, the sidebar opening each, Companion changes per channel.
6. **The Chronicle's events and reminders, and moving a quest's message** (service, app). Events (a realm opened, a quest opened, and so on, the list per the draft) are written to the Chronicle as system lines at the commands that cause them; a reminder (such as a waiting errand a day old) is written by a clock-driven check, once per item per period. Moving a quest to another realm (the existing confirmed move) also moves its origin message to the other channel. Test seam: events from the commands, reminders with a fake clock, the move carrying the message.
7. **Phone.** One pane at a time: the pane chain collapses to the last pane with a Back chevron to its parent, reply lines open the next screen, channels are sidebar rows as realms are. Test seam: the chain-to-screen rule as data; a 390 px window.

## Desktop revision agreed on 2026-11-20

Batches 1–3 are historical deliveries. Batch 4 now stores agent-authored replies and proposal messages as anchors. Its persistence tests cover old rows and the errand's retained brief.

1. **Channels and shell.** Use one hidden Chronicler thread per realm identity and one for the Borderlands. Keep the legacy Chronicle thread for existing history and phone access. Give the channel thread the workspace identity so existing lore and Companion machinery apply. The desktop shell resolves channel, quest and the selected errand into at most three slots. The Chronicle opens from the sidebar.
2. **Follow-up work, activity and moves.** Refuse new nested errands and route attributed follow-up messages from an errand to the quest. The owner's Reply can start an errand from that message. Keep legacy tree edges and display an opened descendant in the errand slot with a parent return. Give the Chronicle activity links and deduplicated reminders. On a quest move, transfer its origin to the destination channel in the same transaction.
3. **Phone and pane identity.** Deferred. Keep the existing phone access.

Verify the first two increments with focused automated tests and a desktop window, alongside Biome, typecheck and the full suite.

The later Chronicle Activity agreement adds unread tracking, filters, direct message and request links, and a separate History tab. The activity list in this increment is a first view of recorded quest and realm events and current reminders. The richer Activity behavior remains open for implementation.
