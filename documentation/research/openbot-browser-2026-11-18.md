# OpenBot browser: primary-source notes

Researched 2026-11-18. Ideas only: OpenBot is under PolyForm Noncommercial 1.0.0 ([inspirations](../inspirations.md), [0001](../architecture-decision-record/0001-new-codebase-not-a-fork.md)); no code was copied and everything below is in my own words, with a few short phrases in quotation marks.

An earlier note on the same product covers its teams, invitations and WebRTC transport: [openbot-multiplayer.md](openbot-multiplayer.md). This one covers only how agents get a browser.

## Question

How does OpenBot (`nightly-labs/openbot`) give its agents a browser? Which engine, and is it bundled or downloaded? How does it run on a VPS with no browser or screen? How does the agent drive it (tools, MCP or not, accessibility tree or screenshots)? How are profiles and sessions isolated? What does the "user control" take-over do? What approvals and per-site permissions exist? How does a phone or other remote client view or control a tab? What are its known limits?

## Findings

### 1. The engine: Electron's own Chromium, driven over CDP

- **No separate browser is bundled or downloaded.** A tab is an Electron `WebContentsView` (`src/backend/browser-host.ts:3836-3850`), so the engine is the Chromium inside the OpenBot app itself. Electron is pinned at 45.3.0 (`package.json:591`). The README's architecture sketch lists a "sandboxed WebContentsView browser host" inside the Electron main process (`README.md:588`).
- **The page is driven through Chromium's debugging protocol (CDP).** Each tab's engine attaches Electron's built-in debugger, protocol version 1.3, on first use (`src/backend/browser-cdp.ts:3967-3968`). It is not a separate remote-debugging port. The design document describes one engine class that maps input tools to CDP operations and keeps tab ownership, queues, focus and deadlines in a separate host class (`docs/architecture/browser.md:114-124`).
- **Not Playwright or Puppeteer.** `playwright-core` is only a development dependency (`package.json:560` opens `devDependencies`; `:598`), used by tests, the dev-automation script and the benchmark (`README.md:443`; `scripts/browser-tools-bench.ts`). The agents' browser does not use it. I did not read the benchmark script itself, so I cannot say how it uses Playwright.
- **Web preferences of every tab**: sandbox on, context isolation on, no Node integration (also not in frames or workers), no `<webview>` tag, web security on, insecure content refused (`browser-host.ts:422-430`). A small preload runs in every frame to make page values look like Chrome (the same preload has no IPC) (`browser-host.ts:480-488`; `docs/architecture/browser.md:145-157`).
- **It tries hard to look like ordinary Chrome to bot checks.** User-agent tokens for OpenBot and Electron are removed (with one exception for Google's account step), client hints are supplied to match `navigator.userAgentData`, the CDP `Runtime` domain is left off because bot checks detect it, and on a server the WebGL vendor names are replaced with those of a common laptop GPU (`docs/architecture/browser.md:125-157`). Outlore should note this is a large, ongoing effort, and that the document itself says some checks still refuse it (see 9).

### 2. Running on a headless host or VPS

- **The whole app runs on the server; the browser comes with it.** A "self-hosted server" is the Linux OpenBot build on a machine with no screen, installed with one script on Ubuntu 24.04 or 26.04 with systemd (`docs/self-hosted-server.md:3-12`). There is no separate browser install step, because the browser is Electron.
- **It runs under a virtual display.** The service starts OpenBot under Xvfb with `OPENBOT_SERVER=1`; two nested `xvfb-run` displays exist, one for OpenBot's own windows (1280x800) and one "agent display" for computer use (`docs/self-hosted-server.md:329-341`). The agent display size does not change the browser: its pages have their own size, 1200x800 when no panel shows them (`docs/self-hosted-server.md:194-203`).
- **No GPU is assumed.** A server always composites on the CPU, keeps WebGL on SwiftShader (so sites such as the Figma editor work), and turns hardware acceleration off after a GPU-process crash (`src/main/linux-gpu-mode.ts:19-24`; `docs/TROUBLESHOOTING.md:78-90`).
- **Docker image, but of the whole host.** The image is the Linux release (extracted from the AppImage) on Ubuntu 24.04, run as a normal remote host (`docker/Dockerfile:1-8`; `docs/docker.md:3-6`). It adds CJK fonts "so the embedded browser can render" those scripts (`Dockerfile:26-27`). It runs as a non-root user with the Electron sandbox left on (`Dockerfile:41-42`; `docs/docker.md:461-466`). That needs a custom seccomp profile that allows user namespaces, plus `--shm-size 1g` because Chromium uses shared memory (`docs/docker.md:49-50`).
- **So their container is not "browser only".** The agents, their tools and the browser all live in one container. A virtual display in the container is reachable by other host programs if the host has the same display numbers (`docs/docker.md:83-85`).
- **Memory behaviour matters on a small VPS.** When free memory is low, the host opens no new tab and unloads idle pages sooner (`docs/self-hosted-server.md:169-172`). An idle tab sleeps after 15 minutes (5 when memory is low), and more than 3 idle loaded tabs sleep after 2 minutes; the page unloads and its renderer ends, but the tab stays (`docs/architecture/browser.md:620-621`; `browser-host.ts:329`, `:908`).
- **I did not confirm** the real memory cost of a tab, or whether the whole Electron app with a virtual display is a fair load for a 1-2 GB VPS. The guide says only to choose enough RAM, naming browser sessions as one reason (`apps/auth-api/src/content/guides/install-openbot-vps.tsx:31`).

### 3. How the agent drives it

- **A tool set, not MCP over a network.** `src/backend/browser-tools.ts:216-578` defines about thirty tools in an `openbot_browser` namespace: `open`, `list_tabs`, `status`, `snapshot`, `screenshot`, `navigate`, `click`, `type`, `fill_fields`, `press`, `hover`, `scroll`, `select_option`, `set_checked`, `drag`, `upload_files`, `wait_for`, `evaluate`, `set_environment`, `recording_start`/`recording_stop`, `handle_dialog`, `close_tab`, `run_script`, a legacy `act`, plus secret, vault, payment and takeover tools (`submit_secret`, `fill_card`, `request_vault_item`, `request_link_payment`, `request_takeover`, and others).
- **They are given to each provider through its own tool channel.** A comment in the catalog calls the three always-present tools "as Claude's in-process MCP server declares them" (`src/backend/agent/tool-catalog.ts:50`), and the same file feeds Codex-style dynamic tools. Only `open`, `list_tabs` and `run_script` are direct; the rest are deferred behind a search and a generic `tool_call`, and the first browser result brings the schemas of `open`, `snapshot`, `navigate`, `click`, `type`, `wait_for` and `run_script` (`tool-catalog.ts:40-58`, `:356-367`; `browser.md:311-325`). This is a design for saving context, backed by their own benchmark (`browser.md:326-343`); I did not rerun it.
- **Text from the accessibility tree first, screenshots second.** `snapshot` reads the page's accessibility tree with CDP (`Accessibility.getFullAXTree`, `browser-cdp-snapshot.ts:595-602`) and returns one line per element: a short reference, role, name and state. Text in the viewport comes first, output is bounded (200 elements, 20,000 characters of text: `browser-cdp-snapshot.ts:24`, `:32`), and a flag says when something was cut. An image is returned separately "when useful" (`browser-tools.ts:233-238`). `screenshot` is a separate tool, optionally for one element, and can save a PNG into the agent's workspace (`browser-tools.ts:547-552`). Refs go stale after navigation or the next snapshot, and the guidance tells agents to take a fresh one (`browser.md:173-174`).
- **A scripting tool to save turns.** `run_script` runs agent-written JavaScript in a QuickJS WebAssembly sandbox (not `node:vm`, because the backend process holds the vault), with no network, files or timers, at most 200 steps and 64 MiB; each step goes through the same checks as the single tool (`browser.md:440-487`; `src/backend/browser-script.ts`). Their reported figures favour it over an older fixed list of steps (`browser.md:453-459`).
- **A lot of work goes into tolerating how models call tools.** Arguments are rewritten before decoding (target strings in several forms, Playwright-style wait states, wrong field names) and `run_script` accepts forms models take from other libraries; their replay of 173 failed calls went from 79 accepted to 140 (`browser.md:345-392`; `src/backend/browser-tool-input.ts`). The check for page settling (`browser-settle.ts`) waits for loading placeholders to go before reading (`browser.md:294-309`).
- **Page dialogs** (`alert`, `confirm`) caused by the agent's own action go to the agent, which answers with `handle_dialog`; others stay for a person; this relies on private Electron events and has its own test that fails when Electron changes them (`browser.md:644-672`).
- **Tabs stay open after a turn.** Nothing closes a tab when a turn ends; the agent should call `close_tab`. A retry or a later turn in the same thread finds the same tabs, and a restart restores them from a state file (`browser.md:599-632`).

### 4. Isolation and profiles

- **No fresh throwaway profile by default; the default is the opposite.** A persistent shared profile (`persist:openbot-browser`, `browser-host.ts:806`) is used by every agent, so every agent of the server shares the same cookies and sign-ins. Alternatives: a profile "only for this agent", or a named profile that several agents share, kept in a table with at most 100 entries (`browser.md:489-541`). Tabs keep their profile for life; a tab whose profile is missing or malformed is dropped rather than falling back to the shared one (`browser.md:512-518`). Clearing or deleting a profile closes its tabs first (`browser.md:526-530`).
- **A private tab** opens in an in-memory profile and is cleared when its last tab closes; it exists for signing in on behalf of someone else, and is hidden from members who are not owner or admin (`browser.md:509-510`; `src/main/team-api/route-browser.ts:51-58`).
- **Per-profile proxy.** A named profile can use a saved proxy (SOCKS5, HTTP or HTTPS); a SOCKS5 proxy with a login goes through a local relay on loopback; the password is encrypted at rest and never sent back to clients; a profile with a proxy never falls back to a direct connection if the proxy fails; WebRTC is limited so the real address does not leak (`browser.md:543-581`). A profile's proxy can also be another member's own computer, carried over a WebRTC data channel, which refuses private and other non-public addresses (`browser.md:583-597`). This is an unusual feature; I did not read the mux code.
- **The page cannot reach the app.** No Node, a sandboxed preload with no IPC, and a statement in `README.md:688` and `SECURITY.md:33-45` that remote pages cannot reach the preload bridge or managed attachments, and that a tab is scoped to its owning agent and thread.
- **The agent, not the machine, is the sandbox boundary, and there isn't one.** `README.md:16-19` warns that agents run with full access and no per-action confirmation. `SECURITY.md:33-35` says this documented behaviour is not itself a vulnerability. The agent's browser therefore has the host's network, apart from OS-level egress rules that hosted and multi-instance servers add: the service user cannot reach private, link-local or router addresses (`docs/hosted-servers.md:1015`; `docs/docker.md:236-244`). I found no address filtering in the browser code itself (I searched `browser-host.ts`, `browser-navigation.ts`, `browser-tools.ts`, `browser-cdp.ts` and `browser-state.ts` for private-range and loopback checks and found none; I did not read those files in full).
- **Only http and https addresses** may be opened; other schemes are refused (`src/backend/browser-policy.ts:7-17`).
- **Page permissions**: only a sanitized clipboard write and the Storage Access API are granted; camera, microphone, location, notifications and clipboard read are refused (`browser-policy.ts:94-108`, `browser-host.ts:3915-3920`). A recorder permission exists for tab capture (`browser-host.ts:3917`; I did not read it).
- **Downloads** go to a managed folder under `~/OpenBot/Downloads` (`README.md:646`), with a cap on concurrent downloads and on size (checked as bytes arrive, not only from the declared size), and file names are cleaned (`browser-host.ts:3921-3960`). A download is refused while a secret is held in the tab.
- **Cookie banners** are refused automatically in an agent's tab (never accepted, only in the main frame, off in a person's tab) (`browser.md:182-195`).

### 5. Secrets, sign-in and payments

- **The model never receives secrets.** The agent calls `submit_secret` naming the kind of secret (password, one-time code, authenticator code) and the fields; the value travels to the host through a typed channel from the user's client, never through a prompt answer or a tool argument, and is typed into the page by the host (`browser.md:711-750`; `tool-guidance.ts:61`).
- **While a secret is held, the tab is locked down**: no inspection, capture, recording or remote input, live-view streams are invalidated, and afterwards the host clears the filled fields and the document, or reloads with GET, with protection staying until a new document loads (`browser.md:735-750`).
- **A vault** holds logins, cards and contact data. `fill_card` types a card into a page without the agent seeing the number, and the first fill of a card on a given page and set of frames needs the owner's approval, remembered per card and page (`tool-guidance.ts:70`; `src/main/vault-service.ts:764-771`). Payment through a "Link" account and a bank code from email are also handled (`browser.md:752-758`). I did not read the vault.
- **CAPTCHA and bot checks**: the host never solves a puzzle and sends no page data to a solver; it classifies a check on each snapshot (cleared, checking, click-once, needs a person, blocked) and tells the agent what to do next, including one click on a simple checkbox (`browser.md:197-236`).
- **A member can sign in on their own computer.** The desktop app opens the site in a window with an in-memory session, then sends only that site's cookies to the host over the encrypted connection, and the host sets them in the chosen profile (`PRIVACY.md:30-44`; `route-browser.ts:187-196`; `src/main/browser-sign-in-page.ts` decides when the window looks signed in). This avoids typing a password on a remote screen.

### 6. User control and take-over

This is the feature the opener pointed at. It is one mechanism with several entry points.

- **What it is.** A signed-in person (the owner on the desktop, or a member through a remote client) takes control of a host tab and later gives it back. The contract file records it as frozen and says so plainly (`packages/contracts/src/team-protocol/browser-user-control-v1.ts:1-10`): a member takes control of a tab they can see, the owning agent's tool calls on that tab wait until the release, and then tell the agent the page may have changed; any member who can see the tab can release it; the host refuses to take a tab while a secret request is active on it; and the host releases holds when the session ends.
- **The state is one map from tab to holder.** The holder is either the local person or a member with a member id and a session id (`browser-host.ts:598`, `:705`). `takeUserControl` stores the holder, invalidates the agent's element references, stops the cookie-banner script, clears the tab's diagnostics and queues behind any running operation (`browser-host.ts:1585-1607`). `releaseUserControl` does the reverse (`:1610-1618`).
- **What the agent sees.** The tool router checks the held tab before each browser call; while held, the call waits (`awaitUserControlRelease`), and when released it returns a fixed result: the tool did not run, the page may have changed, take a fresh snapshot (`src/backend/agent/openbot-tool-router.ts:968-970`; `src/backend/agent/prompts.ts:739-751`; `browser-host.ts:1692-1724`). A list-type call such as `list_tabs` waits while any usable tab is held. A held tab is also refused at the lowest tab-bearing layer, so remote gateways cannot bypass it (`browser.md:606-612`). A `run_script` that is running when a person takes control stops and returns its partial results with status `user_control` rather than waiting (`browser.md:464-466`).
- **Release when the person goes away.** `releaseUserControlHeldBy` releases everything held by a local window, a session or a member (`browser-host.ts:1677-1686`). It is called when a member is disabled (`src/main/host-service.ts:1708-1711`) and when a member is removed (`:1751`). The member's session id also ends holds when the session ends, per the contract above. Role changes revoke a member's sessions (`host-service.ts:1689-1690`).
- **Over the wire.** Three optional routes, `state`, `take` and `release`, each answering with the list of held tab ids; the host also sends a `browser-user-control-changed` event with the whole list (`browser-user-control-v1.ts:14-54`; `route-browser.ts:140-155`). The capability string means older hosts refuse it.
- **No lock on who may release.** Any member who can see a tab can release another member's hold (contract line 6; `route-browser.ts:148` calls `releaseUserControl` with no holder check). Teaching has a stricter rule: another holder's tab is refused, and only the starter can end the recording (`browser-host.ts:1625-1659`).
- **Agent-requested takeover.** The agent can call `request_takeover` when it hits a CAPTCHA, a passkey, an unclear account choice or a payment confirmation it cannot complete; the call waits for the person; the end of the agent's turn cancels it; in a routine (unattended) run the agent should report instead of asking (`tool-guidance.ts:52-56`; `browser.md:170-172`). The takeover prompt uses the same "attention" card system as other questions.
- **"Teach a task".** A person records steps in an agent's tab (page loads and clicks, never typed text), at most 200 steps and 10 minutes, kept in memory; on Save the client sends a message asking the agent for a skill, with the steps in an attached text file; the host stores no step (`browser.md:276-292`; `browser-host.ts:1625-1675`). Not available in a channel or on a phone.
- **"Learn from my browsing"** (off by default) lets the memory review learn from what a person does while holding a tab, recorded as steps with query strings and code-like path parts removed and redacted, kept for at most 30 days (`browser.md:254-275`; `PRIVACY.md:883-890`).

### 7. Approvals and per-site permissions

- **There is no per-site allow list and no per-site prompt.** The agent may open any http or https address. I found no setting that restricts or asks about sites (searched `browser-policy.ts`, `browser-navigation.ts`, `agent-store.ts` and the contracts for browser enable or allow settings; I did not read every settings file). The product's stance is that agents run without per-action confirmation after one first-launch consent (`README.md:16-19`, `SECURITY.md:33-35`).
- **Gates that do exist are narrow**: a per-card, per-page approval for card fill (above); owner approval for a few agent actions such as deleting agents; and per-channel setting "Browser" that gives the browser to one member or to none (`packages/contracts/src/ipc-chat-channels.ts:120`; `openbot-tool-router.ts:3186-3197`). In the channel case the refusal text names the agent that may use it. A per-agent browser profile choice is part of the agent's settings (`browser.md:491-507`).
- **Analytics notes the site, not the page.** The host sends the registrable domain (for example `linkedin.com`) and whether a user or an agent opened it, when analytics are on; subdomains, paths, titles and local names are not sent (`PRIVACY.md:303-308`).
- **Auto-approve** (`approval-automation.ts`) states that browser takeover is a separate flow with its own gate and is never asked there (`approval-automation.ts:15`).

### 8. A phone or remote client views and controls it

- **A remote client cannot see the host's tab directly**, because it is a native view on the host's screen. The host therefore streams it: it reads a CDP screencast (JPEG frames), and sends each frame as bytes over a websocket carried inside the existing WebRTC connection, using the tunnel that remote desktop already uses (`docs/architecture/browser.md:674-680`; `packages/contracts/src/team-protocol/browser-view-v1.ts:1-12`; `src/main/browser-view-gateway.ts:6-12`).
- **Input comes back as fractions of the frame, not pixels**, so the client and the host's viewport need no shared scale (`browser-view-v1.ts:10-17`). Input kinds include pointer, key down/up/char, paste, copy and cut (`browser-view-v1.ts:274-304`). The same access checks apply as for tool calls; the stream does not queue behind tool calls, so watching never delays the agent (`browser.md:677-678`).
- **Flow control.** Frames beyond four in flight wait, only the newest is kept, a held frame expires after 1 second, and a client that stops acknowledging is closed, so a slow phone sees fewer frames, not old ones (`browser-view-gateway.ts:47-74`).
- **Phone specifics.** The app draws the pointer itself, so the host sends cursor changes on request; it asks for a 1280x800 viewport and holds the page at that size while the socket is open; right-click menus are sent as messages rather than opened on the host; text the page copies (for example a "Copy code" button) is sent to the member only within 5 seconds of their own input (`browser.md:682-709`). The view runs in the hidden page that holds the peer connection, which passes frames to the screen as base64 (`browser.md:704-707`). The app has files for tabs, gestures, keys, a cursor and a help screen (`apps/mobile/src/features/browser/*`; I did not read them). Back, forward, reload, new tab and close tab use ordinary routes (`browser.md:707-708`).
- **Web client** (`/app`) uses the same live-view runtime; it hides controls that need native windows (`browser.md:23-28`).
- **A server flag** on the account service can turn the phone's browser off for a given app version (`browser.md:708-709`; `apps/auth-api/src/server/mobile-features-config.ts`).
- **Data path.** The live view's images and the watcher's input travel through the encrypted Team API connection, directly or through the project's relay (`PRIVACY.md:1121-1124`). A host "private network" setting makes this direct only.
- **Secrets and the view.** While a secret is being entered the host invalidates existing live-view streams and rejects remote input (`browser.md:735-738`).

### 9. Known limits (their own documents, plus what I saw)

- **Bot checks**: a great deal of the document is about passing them, which suggests it is an active problem. The host does not solve puzzles; a check that stays reads as "needs a person" (`browser.md:197-229`). Server GPU names are faked because SwiftShader reads as headless Chrome, but the same name still shows in a worker's OffscreenCanvas (`browser.md:150-155`).
- **Frames**: cookie banners in frames are not handled (`browser.md:193-194`); `fill_fields` handles only main-frame plain inputs; a secure-input card in a connected tab can be unavailable and then needs a person (`browser.md:165-172`, `:403-409`).
- **Dialogs**: `prompt` and `beforeunload` are not intercepted; dialogs from `evaluate`, `wait_for`, `fill_fields` or a cross-origin frame stay native (`browser.md:669-672`). On a headless host, a native box nobody sees is a risk; I did not check what the server does with one.
- **Phone**: no "teach", and a phone cannot share its own connection as a proxy because it has no TCP sockets (`browser.md:290-291`, `:579`).
- **Container**: remote desktop and computer use were not tested in the Docker image; Gemini sign-in through the browser of the container was not tested (`docs/docker.md:500-508`).
- **Same-profile sharing**: all agents of a server share cookies by default, so one agent's signed-in session is available to every other agent and member (`PRIVACY.md:36-40`).
- **Version dependence**: dialog handling relies on private Electron events, and bot-check handling on a single Electron/Chromium version, so each Electron upgrade needs those end-to-end checks (`browser.md:657-661`).
- **I did not confirm**: the memory cost per tab on a small VPS, how many concurrent tabs a server really sustains, what a stalled native dialog does on a headless host, or whether any other browser engine is planned.

## What this means for Outlore

This is for the person deciding; it does not make the decision.

**Worth adopting (as ideas):**
- **A text-first page reading that returns short element refs**, with an optional image separately, and with bounded output and a "truncated" flag. This is also what Playwright MCP's accessibility snapshot does; the OpenBot design is the same idea reached independently, and its numbers (200 elements, 20,000 characters of text) are a reasonable starting bound.
- **A "give the tab to a person" lock at the lowest layer that every browser call passes through.** Make the agent's calls wait, then return a fixed "the user controlled this tab, take a fresh snapshot" answer. Release when the holder's session ends, a member is disabled or removed, or the connection drops. Refuse a take while a secret is being entered.
- **Never put a secret in a tool argument or a prompt.** The model names the field and the kind; the value goes from the user's client to the host and is typed by the host. Lock the tab (no capture, no stream) until a new document loads.
- **Per-card, per-page approval** for a payment fill, rather than per-site approval for everything.
- **Streaming a tab to a phone as JPEG frames with input as fractions of the frame**, with a small in-flight limit and "drop to the newest" flow control. This works on a phone with no engine of its own.
- **A closed, short list of page permissions** (clipboard write only; refuse camera, microphone, location, notifications).
- **A small, fixed set of agent-facing tools**, with arguments repaired for common model mistakes and a combined-steps tool, measured with a benchmark on a stable set of pages.
- **Idle tabs that unload but stay listed**, with a tighter limit when memory is low, which matters on a small VPS.

**Avoid or do differently:**
- **Do not copy the single shared persistent profile as the default.** For an agent that browses the open web, Outlore's leading idea of a throwaway profile, with named profiles chosen by the owner, is safer than a profile every agent shares.
- **Do not rely on "agents have full access" as the only boundary.** OpenBot has no per-site prompt and no address filter in the browser code I searched. Outlore's draft already asks the owner before sites; keep that, and add a block on private, loopback and link-local addresses, so an agent's page cannot reach the host's own services or a cloud metadata address.
- **Do not make the engine the app's own Chromium.** OpenBot gets "no separate browser to install" because the browser is the Electron app. Outlore's service runs apart from its app (and may sit on a VPS with no app at all), so the same trick is not open to it. On a VPS it needs a browser it brings itself (a downloaded Chromium, or a container), as the opener already concluded.
- **Do not put the whole host in the container just for the browser.** OpenBot's container holds agents, tools and browser, with a custom seccomp profile and a 1 GB shared-memory flag. A browser-only container, as already proposed, is the narrower choice, and the shared-memory and user-namespace requirements are worth knowing for it.
- **Do not take on the bot-check evasion work as a goal.** OpenBot spends much of its browser document on matching Chrome's identity and WebGL names. For a view-only first batch this is out of scope, and the effort is large and never done.
- **Do not let any member release another's hold unchecked** if Outlore has several people; OpenBot allows it for take-over but not for teaching.
