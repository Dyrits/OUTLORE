# OpenBot connector and provider inventory

The comparison uses Nightly Labs' desktop OpenBot, the same project as the [browser research](openbot-browser-2026-11-18.md). I inspected its Git tree at `b1e5ea74206e1e16fa2eae62d8d131ea1349eaa0` and Outlore at `7026ce87`. This is a source inventory. Live sign-in and tool behavior remain to be verified.

## Proposed batches

1. Start with GitHub in the existing connector gateway. Verify owner setup, a repository read, the approval and denial paths for a write, and revocation from a running quest. Confirm the authentication method against GitHub's supported options before implementation.
2. Add the messaging connectors. Decide how inbound conversations map to Outlore quests and how an owner enables outbound replies.
3. Add the password-manager connectors. Decide what a quest may request and how the host uses secrets without exposing them to the model.
4. Add providers by runtime family. Reuse the existing ACP transport where it fits and verify each provider's account isolation, permissions and usage reporting. The [provider credential requirements](../requirements.md) apply to every runtime.
5. If marketplace parity is included, agree how Outlore will register remote MCP servers and authorize their tools. Inspect manifests and verify one signed-in connector end to end before widening the catalog.

The open scope question is whether “all the connectors” includes the marketplace as well as the eight built-ins. The upstream manifest count measures packages in the catalog. It is not a count of distinct connected applications or of tools verified to function.

## Provider registration design (2026-11-22, seam owner)

Decided while the adapter errands run; binding for shared registration (`harnesses.ts`, `harnessCatalog.ts`, `@outlore/contracts`, Workshop wiring).

**Mapping the 14 remaining provider IDs to Outlore shapes.**

- New harnesses, one registry entry each with its own CLI: `antigravity` (label Gemini), `cursor`, `cline`, `kimi`, `devin`, `copilot`, `hermes`, `grok`, `muse`, `pi`. Ten entries.
- `inception`, `deepseek`, and `openrouter` are **model scoping inside the `pi` harness**, not separate harnesses: upstream runs them through Pi, and `piModelsOf` already filters and qualifies model ids by provider. They appear as the Pi harness's model groups, never as their own pickers.
- Custom ACP is a **Workshop feature** (a user-defined command with a probe and strict defaults), not a fixed registry entry; design deferred until the fixed providers are in.

**Admission rule (from the provider credential requirements and ADR 0007).** A provider enters `HarnessName` only when its adapter demonstrably routes every sensitive action through ACP `session/request_permission` (or the runtime's equivalent) so Outlore can mediate by effective mode, fail closed when mediation is unavailable; when per-account isolation holds through a config variable; and when Outlore never reads, stores, or relays credentials. A CLI that can auto-approve its own actions or keep native subagents Outlore cannot see is **blocked**, not registered, with the evidence recorded here. Kimi split by generation on 2026-11-22: the archived Python kimi-cli 1.x (this machine's installed 1.6) can restore auto-approval (`default_yolo`) and stays unsupported, while kimi-code 2.x starts every ACP session in its manual-approval default mode and rejects on permission-request failure (verified in-source at clone e12cad1a, `packages/acp-server/src/interaction-bridge.ts:109-128`), so it is admissible behind a major-version gate.

**Staged rollout.** Contracts change in waves, each wave a fully verified set: wave 1 is Hermes (the only new provider live-verifiable on this machine, v0.22.6 with the `HERMES_HOME` + one-time `hermes pm repair` recipe). Providers whose CLIs are absent here (cursor, cline, devin, copilot, antigravity, pi, muse) may register only after their fixture suites prove permission mediation; their live checks stay listed as pending until the owner installs them. Kimi registers only where `kimi --version` passes `acceptsAcpProviderVersion` (major 2 or higher), launched with `KIMI_CODE_HOME` at an Outlore-managed per-account directory, the session mode kept at `default` (never `session/set_mode` with `auto` or `yolo`), and sign-in via `kimi acp --login` against that same home; this machine's 1.6 install does not register, and live 2.x checks stay pending until a 2.x is installed. Grok stays out until `--no-subagents` is proven effective in normal sessions, not just profile generation.

**Known facts gaps to fill at wiring time.** `harnessFacts.installVia` admits only npm and uv; Hermes reports "Install method: git" and may need a third path or a manual-install row. Cursor and Copilot have no demonstrated isolated added accounts (shared keychain or API-key-only secondaries), so they register with the computer's own sign-in only. Muse's account-home isolation is unverified. Inception inside Pi still needs its provider registration proven without Outlore handling keys. Upstream's stored-key providers (`pi-key-providers`) are not adopted: sign-in stays the unmodified CLI's own, in a Terminal, per the Vibe pattern.

**Wave 4/5 evidence (2026-11-22, seam owner; source-verified against the pinned upstream by both survey errands and re-checked at registration, live pending).** The five remaining ACP providers register together (CHG-0645; adapters in commits `8faa9f6e` and `f8420275`, registration after `a1a61117`): **Cursor** (`cursor-agent acp`, computer sign-in only - its upstream second account is a stored API key the no-credentials rule excludes), **GitHub Copilot** (`copilot --acp --no-auto-update` + `COPILOT_AUTO_UPDATE=false` on every spawn, keychain sign-in, driver carries no accounts entry), **Cline** (`cline --acp` + `CLINE_NO_AUTO_UPDATE`/`CLINE_SESSION_BACKEND_MODE=local`, generation-3 gate, `cline auth -p cline` device sign-in, npm platform packages `@cline/cli-<target>`), **Devin** (`devin acp`, no env of its own, state under the XDG data root, sign-in only through the ACP `devin-browser` flow - no CLI sign-in exists), and **Antigravity, label Gemini** (`antigravity acp --gemini-dir=<home> --app-data-dir=antigravity-acp` with `AGY_CLI_DISABLE_AUTO_UPDATE=true`, home = GEMINI_HOME else ~/.gemini, sign-in only through the ACP `oauth-personal` flow - no CLI sign-in exists; upstream pins accounts via GEMINI_HOME + the same flag, but the pinned tree never shows the CLI resolving a split between them, so added accounts stay blocked until a live check proves which channel wins). Each is a plain ACP server: every sensitive action rides `session/request_permission`, and their subagents (`spawn_agent`, `start|invoke_subagent`) are TOOL calls Outlore mediates per call - Grok's native-unmediated escape is absent from the pinned tree for all five. Registration consequences: Update refuses for all five (no update command of any of them exists upstream; self-updates stay suppressed exactly as each provider itself does), Install explains each provider's signed-distribution story (Cursor's ACP registry descriptor, Copilot's GitHub release archives with SHA-256, Cline's npm platform packages, Devin's Cognition manifest with SHA-256, Antigravity's GitHub releases), `readSignIn` stays Unknown across the five (no machine-readable sign-in status a read-only command answers), and the catalog gained two shapes: `signInArgs: null` (a harness with no verified CLI sign-in - Devin and Antigravity - whose Sign-in explains instead of running anything, mirroring Update's no-command refusal) and `signInEnv` (each provider's own sign-in environment: cursor-agent's NO_OPEN_BROWSER link flow, Copilot's and Cline's self-update squeezes) carried on both the headless and terminal sign-in paths. Adversarial evidence retained in the adapter files: Cursor's `cursorAccessDenied` usage surface (a credential-reading, undocumented api2.cursor.sh endpoint) is recorded and NOT adopted. Live checks queued for the owner: install each CLI, sign in (cursor/copilot/cline through the terminal flow; devin/antigravity through the provider's own surface), one probe and one real turn each, and Antigravity's flag-versus-env home question.

 **Wave 3 evidence (2026-11-22, seam owner; source-verified against the pinned upstream, live pending).** Pi registers as wave 3 on the Pi errand's handover, each fact checked in the pinned tree. Accounts isolate by directory: `PI_CODING_AGENT_DIR` (default `~/.pi/agent`) holds `auth.json` (the sign-in), `settings.json`, `models-store.json` and `sessions/` (`process-confinement.ts:325-338`), so added accounts get their own directory and the computer's own sign-in stays the unredirected default - no added-account refusal needed. Sign-in is `/login` inside Pi's own interactive screen (`agent-providers.ts` signInMessage: "Use /login in Pi on the host computer. Close Pi when sign-in is complete."), so a terminal window opens plain `pi` against the account's directory (empty `signInArgs`, terminal needed) and `readSignIn` stays Unknown until a live check proves a surface. The CLI ships as release archives of `earendil-works/pi` (tarball plus published SHA-256, `provider-runtime-releases.ts:93-98`, lock pins 1.1.0 MIT) and no npm package exists, so Install explains the download; no update command of Pi's own is verified (`pi update --models` at `pi-client.ts:561` only refreshes the model catalog), so Update refuses. Inception stays blocked as a Pi model group: stock Pi has no built-in inception provider (only an upstream extension carrying the API key through env + `globalThis`, `pi-key-providers.ts`), which the no-stored-keys rule excludes; its models simply stay absent from the probe. DeepSeek and OpenRouter are Pi's own built-in key-based providers: the owner supplies their keys through Pi's own channels in the terminal (DEEPSEEK_API_KEY / OPENROUTER_API_KEY or pi's auth.json) and Outlore stores nothing.

**Flag-set correction (2026-11-22, at registration).** The adapter draft carried `--no-approve` in the probe and denial flags; the pinned upstream knows no such flag anywhere (probe `pi-client.ts:515` runs `--no-session --no-tools`, profile generation `:705` and `:1276` add `--no-extensions --no-mcp`), so it is dropped from `probePiModels` and `piDenialArgs` before registration: every flag Outlore passes is one upstream itself passes. The breach reason now also names the tool call id (`toolCallId`, present in upstream tool records). The denial set stays `--no-tools --no-extensions --no-mcp`, extension UI requests stay cancelled, and any tool execution under denial still ends the turn.

 **Wave 2 live evidence (2026-11-22, seam owner; source-verified against the pinned upstream, live pending).** Muse registers as wave 2 on the errand's cited facts, each checked in the pinned tree: the `muse` CLI is on no package registry (only the npm SDK; the CLI ships through Meta's signed muse-stable manifest with SHA-256 checksums, `src/main/provider-runtime-releases.ts:110-152`), so Install explains rather than runs. No update command exists anywhere upstream, and `MUSE_NO_AUTO_UPDATE: "1"` is set at every spawn site (`muse-client.ts:351`, `muse-login.ts:35/122`, `provider-drivers.ts:636`), so Outlore refuses Update, suppresses the CLI's self-update on every spawn (harness and probes), and never runs upstream self-updaters. The muse driver entry has no `accounts.homeVariable` (unlike CODEX_HOME or GEMINI_HOME beside it), and its writable paths all sit under the shared XDG data root (`process-confinement.ts:340-352`), so the harness takes only the computer's own sign-in and `AddAccount` is refused (`supportsAddedAccounts: false`); `XDG_DATA_HOME` itself is machine-wide and cannot serve as a scoped account home. Sign-in opens a terminal (`muse login` opens its device page only from a real terminal; the in-protocol device flow rides experimental MSP this host does not opt into), so `readSignIn` stays Unknown until a live check proves a surface.

**Decided at wiring time.** Outlore's shared ACP `initialize` keeps advertising `fs` and `terminal` as false: kimi-code (and any provider with the same reverse-RPC surface) then executes file and terminal actions locally with `session/request_permission` as the only mediation. Advertising those capabilities later would add byte-level host mediation but widens the surface and the protocol burden, so they stay off until a concrete need is shown (kimi-code 2.7.2 verified in-source, `packages/acp-server/src/server.ts:130-132`).

**Wave 1 live evidence (2026-11-22, seam owner; host-running Hermes 0.22.6).** The generic probe is proven against a live provider: `probeAcpProviderModels({command: hermes, profile: {args: ["acp"], env: {HERMES_HOME: <account home>}}})` completed initialize → `session/new` → `configOptions` and returned 15 models. Requirements discovered on the way, binding for the Hermes account design:

- An unconfigured account home is **not probeable**: Hermes's `session/new` fails with `-32603 storage_unavailable` because `gateway/session_policy.py` `restore_policy` rejects a session policy with an empty model. The account home needs a `config.yaml` with a `model.default` (verified with the placeholder `anthropic/claude-opus-4.6`, no credentials); the account setup flow must therefore create that config before the first probe, and a probe against an unset-up account is reported as "not signed in", not retried.
- The isolated-home probe (temp `stateHomeEnv` redirect) works for Kimi but cannot work for Hermes, which requires its configured state home; the probe seam gets a caller-supplied state-home option for such profiles (errand work, in its owned files).
- Hermes's detached gateway keeps a control socket at `$HERMES_HOME/gateway.sock` when the path fits `sun_path` (≤100 bytes), else falls back to `XDG_RUNTIME_DIR` → `TMPDIR` → `/tmp`; the `/tmp` fallback failed with EPERM in a sandboxed run. Outlore-managed Hermes account homes must stay short enough for the direct socket.
- `initialize` advertises `loadSession`, image prompts, session fork/list/resume, and a single terminal auth method (`hermes-setup`, args `["--setup"]`): Hermes sign-in is an interactive `hermes --setup` in a terminal against the account's home, the same shape as the Vibe account flow. A live prompt/turn remains unverified until the owner signs an account in; it stays the outstanding check for wave 1 admission.

**Pi adapter interface (2026-11-22, fixture-verified by the Pi errand and re-verified by the seam owner).** The `pi` harness registers through `makePiHarness(options: {command, env?, idleTimeout, prefixArgs?, provider: "pi" | "inception" | "deepseek" | "openrouter"}): Effect<HarnessAdapter, never, Scope>` in `packages/service/src/harness/pi.ts`, riding the shared `makeHarnessProcesses` pool (restart key includes provider/model/effort/configDirectory/folder). Model ids are provider-qualified (`encodeURIComponent(provider) + "/" + modelId`, decoded by `piModelPartsOf`); `piModelsOf` filters catalog models per provider, and `probePiModels` (`piRpc.ts`) probes with `--no-session --no-extensions --no-mcp`. Per-account state is `PI_CODING_AGENT_DIR`. **Tool capability is fail-closed**: every turn starts with `piDenialArgs` (`--no-tools --no-extensions --no-mcp`), `extension_ui_request` is always answered cancelled, and any `tool_execution_start/end` during denial ends the turn as a breach (`piTools.ts`). Pi therefore registers (once a live CLI is verified) as a **no-tools harness first**; lifting the denial requires the askOwner → `extension_ui_response` mediation seam designed and vetted, plus Inception's sign-in story through unmodified Pi, both still open. Steer is provisional-false and cached images are refused (turn fails) until the live protocol check. Sixteen tests green; nothing live (no `pi` executable on this host).
