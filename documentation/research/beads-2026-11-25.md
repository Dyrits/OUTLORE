## What Beads is

- **One line.** "Distributed graph issue tracker for AI agents, powered by Dolt" (`README.md`), and "Beads provides a persistent, structured memory for coding agents. It replaces messy markdown plans with a dependency-aware graph, allowing agents to handle long-horizon tasks without losing context" (`README.md`).
  Its own orientation page puts the problem as "Coding agents lose their memory every time a session ends. Markdown plans rot, TODO comments scatter, and a crashed agent takes its context with it" (`docs/core-concepts/index.md`).
- **It is a CLI, `bd`, installed once and used in each project** (`README.md`: "don't clone this repo into your project").
  It is a Go program: `beads.go` and `cmd/bd/prime.go` import `github.com/steveyegge/beads/...`, although the repository now lives under the `gastownhall` organization and its docs site is `beads.gascity.com`.
  Install paths are `brew install beads`, `npm install -g @beads/bd`, an install script that verifies release checksums, `go install`, and Windows and Arch packages (`README.md`).
- **Scope is deliberately narrow.** `engdocs/PROJECT_CHARTER.md` says Beads owns "issues and issue lifecycle, dependency relationships and readiness, labels, comments, status, priority, and assignment, metadata attached to issues, local CLI workflows … import, export, sync, backup, and recovery".
  It then draws two fences: "Beads should not know about orchestration layers built on top of it" (routing, task assignment strategy, model choice, retry plans and scheduling belong to the layer above), and "Beads should not become a storage engine" (Dolt owns storage, versioning, sync and merge).

## Data model

- **A bead is an issue** ("Bead and issue name the same thing; the CLI says issue, the product says bead", `docs/core-concepts/index.md`).
  The `Issue` struct (`internal/types/types.go:20`) carries content fields (`title`, `description`, `design`, `acceptance_criteria`, `notes`, `spec_id`), a `status`, an integer `priority` (0 critical to 4 backlog), an `issue_type`, `assignee` and `owner`, timestamps with `close_reason` and `closed_by_session` ("Claude Code session that closed this issue"), a free-form JSON `metadata` extension point, labels, dependencies and comments.
- **Statuses**: `open`, `in_progress`, `blocked`, `deferred`, `closed`, `pinned`, `hooked` (`types.go:608-614`).
  **Types**: `bug`, `feature`, `task`, `epic`, `chore`, `decision`, `message`, `molecule`, `gate`, `spike`, `story`, `milestone`, `event` (`types.go:809-827`).
- **IDs are content hashes**, such as `bd-a1b2`, so two agents or branches cannot mint the same ID and merges never renumber work; hierarchy adds suffixes (`bd-a3f8`, `bd-a3f8.1`, `bd-a3f8.1.1`) (`docs/core-concepts/index.md`, `README.md`).
- **Dependencies are typed edges** (`types.go:1473-1503`; `docs/core-concepts/dependencies.md`).
  Blocking types (they change what is ready): `blocks`, `parent-child`, `conditional-blocks` ("B runs only if A fails"), `waits-for` ("wait for all of A's children").
  Non-blocking annotations: `related`, `tracks`, `discovered-from`, `caused-by`, `validates`, `supersedes`, `relates-to`, `duplicates`, `replies-to`, plus identity and approval edges (`authored-by`, `assigned-to`, `approved-by`, `attests`) and `delegated-from` ("Work delegated from parent; completion cascades up").
- **Ready work is a computed frontier.** `bd ready` returns "open beads with no open blockers, excluding anything in progress, blocked, deferred, or held by a gate", and the graph, "not a human dispatcher", decides what is workable next (`docs/core-concepts/index.md`).
  Readiness is persisted as `Issue.IsBlocked`, "the persisted readiness projection" (`types.go:37-41`), and the docs ship a repair command, `bd recompute-blocked`, "once per workspace" after some upgrades (`docs/index.md`), so a stored projection can go stale and needs repair.
- **Claiming is a guarded atomic compare-and-set.** `bd update <id> --claim` sets assignee and `in_progress` only while the issue is open and unassigned (or already the actor's, an idempotent success); a foreign holder gets `ErrAlreadyClaimed`; and "the actor is caller-asserted provenance, not authenticated identity" (`issueops/claimer.go`).
  A lease layer adds a claim TTL, heartbeat and reclaim of stale claims; leases live in "the ephemeral, node-local leases table", and a reclaim refuses a lease granted on another replica unless overridden (`types.go:57-73`, `issueops/heartbeater.go`, `issueops/leasereclaimer.go`).
- **Gates park a step on the outside world.** A gate is an issue that blocks its waiters until it closes; types are `human` (resolved only by `bd gate resolve`), `timer`, `gh:run`, `gh:pr` (both evaluated through the `gh` CLI by `bd gate check`) and `bead` (`docs/workflows/gates.md`).
- **Workflows are templates stamped into graphs.** A formula (TOML or JSON, with `vars`, `steps`, `needs`, and `type = "human"` steps) is cooked into a proto, then poured into a molecule, which is "just an epic" whose children flow through `bd ready`, or instantiated as an ephemeral **wisp** that stays out of sync and is deleted by `bd purge` (`docs/workflows/formulas.md`, `molecules.md`, `wisps.md`).
  `bd mol distill <epic-id> <formula-name>` extracts a reusable formula from an ad-hoc epic (`molecules.md`).
- **Messaging is issues too.** A message is an issue of type `message` with `sender`, `assignee` as recipient, `open` as unread and `closed` as read, threaded by `replies_to` edges and optionally `ephemeral`; `bd mail` "delegate[s] to an external mail provider (typically `gt mail` in an orchestrator)", so routing and delivery belong to the layer above (`engdocs/messaging.md`).
- **Compaction is "memory decay" for closed issues.** `bd compact` summarizes closed issues, "permanent graceful decay - original content is discarded"; only Tier 1 (30 days closed) exists and the command refuses Tier 2 as "not yet implemented"; the automatic mode needs `ANTHROPIC_API_KEY`, `MINIMAX_API_KEY` or `ai.api_key`, and an agent-driven analyze-then-apply mode needs no key (`cmd/bd/compact.go`).
  Whether Dolt history still holds the original text was not checked.

## Storage, sync and interfaces

- **Storage is Dolt**, a version-controlled SQL database; every write auto-commits to Dolt history (`docs/core-concepts/index.md`, `docs/architecture/dolt.md`).
  Embedded mode (default) runs Dolt in-process in `.beads/embeddeddolt/` with one file-locked writer; server mode (`bd init --server`) connects to an external `dolt sql-server` for concurrent writers, and `bd` refuses a Dolt older than the pinned 2.6.0 outside embedded mode (`docs/architecture/dolt.md`).
- **Sync is `bd dolt push` and `bd dolt pull` against `refs/dolt/data` on the project's git remote.**
  `.beads/issues.jsonl` is "an export for viewers and interchange, not the source of truth or a backup" (`README.md`, `docs/core-concepts/sync-concepts.md`); peer-to-peer federation across Dolt remotes (DoltHub, S3, GCS, SSH) with data-sovereignty tiers is a separate feature (`docs/multi-agent/federation.md`).
- **Schema changes are one-way.** A newer binary migrates the database and an older binary then exits with "schema version mismatch", unless `BD_IGNORE_SCHEMA_SKEW=1` (`README.md`); migration numbers up to 0073 appear in code comments (`types.go`).
- **Programmatic surfaces.** Every command has `--json`; `bd serve` exposes an HTTP API, `/v0/beads/*`, specified in `internal/httpapi/spec/openapi.v0.yaml` (`engdocs/design/bd-serve-v0.md`); an experimental HTTP backend (`bd connect`) lets a thin client use a remote server ("This surface is EXPERIMENTAL: pin an exact beads version", `README.md`); a Go package `beads.go` is "a minimal public API for extending bd".
  An optional **events journal** writes one ordered record per committed mutation, in the same transaction, for consumers that must replay every change from a checkpoint; a checkpoint below the retained window is an error, because "at the SQL level 'nothing new' and 'your prefix was deleted' are one empty result set" and a guess would lose data silently (`docs/reference/events-journal.md`, `journalops/` package comment).
  It is off by default and local to one clone.
- **An MCP server exists but is discouraged for shells.** `beads-mcp` is a Python package (`requires-python >=3.11`, MIT, version 1.3.4 in `integrations/beads-mcp/pyproject.toml`) that wraps the `bd` CLI; its own README says to prefer "CLI + hooks" where there is a shell, because MCP schemas cost "10-50k" tokens against "~1-2k" for `bd prime`.
- **Community surface.** `docs/community-tools.md` lists terminal UIs, web boards and editor extensions that call `bd list --json` or follow the events journal; `docs/related-projects.md` lists adjacent projects such as `scry`, a recall layer that it describes as a different job from Beads: "Beads is a task graph for *what to do next*, scry is a recall layer for *what was decided and why*".

## How agents use it

- **Setup writes into the project and the user's agent configuration.** `bd init` "creates or updates `AGENTS.md` by default … and also installs the project Claude Code, Codex, and Cursor integrations unless you pass `--skip-agents` or `--stealth`" (`README.md`).
  `bd setup <recipe>` (recipes: claude, cursor, gemini, copilot, codex, factory, mux, opencode, aider, junie, windsurf, cody, kilocode, kiro) writes managed sections and hook files, with `--check` and `--remove` (`docs/getting-started/ide-setup.md`).
- **`bd prime` is the single source of workflow context.** It prints "AI-optimized workflow context": about 50 tokens in MCP mode and roughly 1-2k tokens in CLI mode, designed for SessionStart hooks "to prevent agents from forgetting bd workflow after context compaction" (`cmd/bd/prime.go`, long help).
  For Claude Code the hook is `bd prime --hook-json` in `.claude/settings.json` or, with `--global`, `~/.claude/settings.json`; SessionStart fires again after compaction, so no PreCompact hook is needed (`docs/integrations/claude-code.md`).
  Codex gets SessionStart and PreCompact hooks through `bd codex-hook`, with refresh markers keyed by session, because Codex ignores plain stdout from compact hooks (`docs/integrations/codex.md`); OpenCode gets only a managed `AGENTS.md` section (`docs/integrations/opencode.md`).
  Beads declines to ship Claude skills so that the same CLI works in every editor (`docs/integrations/claude-code.md`).
- **The agent's loop** is `bd ready --json`, `bd update <id> --claim --json`, work, `bd close <id> --reason …`, and `bd dolt push` "ALWAYS … at session end"; discovered work is filed with `--deps discovered-from:<id>` (`docs/integrations/claude-code.md`).
  Handoffs between agents are comments plus reassignment (`bd comment`, `bd assign`) (`docs/multi-agent/coordination.md`).
- **Memory is one small keyed notes plane.** `bd remember "insight"` stores a note, `bd recall`, `bd forget` and `bd memories` read and delete it, and `bd prime` injects the notes; the README's suggested `AGENTS.md` text says to use it "for durable project facts; keep per-operator preferences in your harness's own memory" (`README.md`).
  Notes are stored in the config table under `kv.memory.<key>`; they are "USER DATA under a reserved namespace" whose merge conflicts auto-resolve with `--theirs` (`internal/storage/versioncontrolops/mergesettle.go`, as cited by the package comment), and "a workspace holds tens of" of them, so there is no paging; the package is marked EXPERIMENTAL (`memoryops/` package comment).
  `bd prime` caps injection with `--max-memories` and `--max-memory-chars` at whole-memory boundaries and prints "a banner ahead of the entries [that] reports how many were elided and how to browse the rest with `bd memories`", because "hosts truncate silently" (`cmd/bd/prime.go`).
  There are no scopes, kinds, fading or counted uses.

## How it compares with Outlore

Beads and Outlore are neighbours more than rivals.
Outlore's outline calls itself the place where "every piece of work is a mission carried out in a tree of threads" with delegation, messaging, handover, budgets and approvals (`documentation/outline.md`); Beads has none of those, and its charter forbids it from growing them.
Beads tracks units of work and what blocks what; Outlore runs and steers the agents that do the work.

| Beads | Outlore | Reading |
| --- | --- | --- |
| Bead (issue) with status, priority, type, assignee | No work-item entity: the glossary's Mission entry says "Avoid: Goal, objective, task, ticket, project"; the nearest are a quest and its errands, each a conversation on a harness | A different grain: a bead is a record, an errand is a running conversation |
| `parent-child`, hierarchical IDs, `delegated-from` | Thread tree: errands open beneath a thread (`documentation/architecture.md`, "Open a thread") | Same shape for hierarchy; Outlore has no `blocks` between errands |
| `blocks`, `waits-for`, `bd ready`, `bd blocked` | None: a parent waits on its children by state (Waiting, Resting); no ordering between siblings | The one real gap Beads shows |
| `--claim`, lease, heartbeat, reclaim | the thread lifecycle's "recover at startup" transition (`architecture.md`) | Outlore has one host and no concurrent claimers, so a lease has less to do |
| Gate (`human`, `timer`, `gh:pr`, `gh:run`) | `request_approval` and the Attention state wait on the owner; Rituals run on a schedule; webhook and event triggers are "not built" (`outline.md`) | A gate is one primitive for three things Outlore has separately or not yet |
| Formula, proto, molecule, wisp | `workflow-running` is a bare line in the capability map with no specification (`outline.md`) | A concrete reference design for the unbuilt capability |
| `bd remember` plus `bd prime` | Lore (scope, kind, fading, counted uses, history with undo) and the starting-context note (`glossary.md`, `architecture.md`) | Lore is far richer; Beads is flat keys with no fading |
| Issue comments, `notes`, `bd history <id> --events` | Journal: a rewritten briefing plus an append-only change log read by every thread of the quest (`glossary.md`, "Journal") | Nothing in Beads is a briefing; its comments are per-issue |
| `message` issues, `replies-to`, ephemeral purge | Thread messages and the Slack-like thread replies (CHG-0735, CHG-0736; Cookout entry in `inspirations.md`) | Beads delegates routing to an external mail provider; not a model for Outlore |
| `bd compact` (Tier 1 only, original discarded) | Journal compression idea, keeping raw entries (`backlog.md`, from souls.house) | Beads is the cautionary example: lossy by design |
| Events journal with checkpoints | Changes announced after each committed command (`architecture.md`, "Commands") | Worth comparing for paired-device refresh, not yet judged |
| Dolt push/pull, federation | Local SQLite host, encrypted relay for paired devices, no peer sync (`architecture.md`, `requirements.md` "Local data") | Different bets; not interchangeable |

Beads' own `bd prime` problem is Outlore's problem too: how much context to re-inject, and how to keep it from silently truncating.
Outlore's backlog already says each turn re-sends the journal's briefing and the full active lore, "about 2-3k tokens, of which 3 guided the work" (`backlog.md`, "A leaner turn preamble and finding past work").

The repository's own working documents sit where Beads says markdown plans rot.
`documentation/work-in-progress.md` is 1,219 lines, `documentation/backlog.md` 104 lines of long paragraphs, and `.agents/handoffs/` holds 383 files; `AGENTS.md` asks every session to read the newest handoff and verify its claims.
That is a fit for what Beads targets, but the process is the owner's documented convention (batches with the iterate skill, changelog and verification files), and Beads would not replace it without the owner choosing to change it.

## Integration options

**(a) A connector (stdio MCP over `beads-mcp`).** Poor fit.
Outlore's stdio backend runs one self-contained, vendored file under a system Node, chosen so that a packaged app needs no network and no `npx` (`packages/service/vendor/README.md`); `beads-mcp` is a Python 3.11 package that also needs the `bd` binary and Dolt data on disk.
Beads' own documents say to avoid MCP where a shell exists, and Outlore threads do have a shell in their sandbox.
Beads' license is acceptable (MIT, OSI-approved), so the obstacle is packaging and value, not licensing.

**(b) Threads use `bd` through their shell in a realm the owner chooses.** Possible without any Outlore change, but the pieces Beads relies on do not line up with Outlore's launches.
- **Hooks do not fire.** `bd setup claude` writes a SessionStart hook to `.claude/settings.json`, but Outlore launches Claude Code with `--strict-mcp-config --setting-sources ""` (`packages/service/src/harness/claudeArgs.ts:43-46`), which ignores those settings, the same obstacle recorded for Hindsight's hooks in [hindsight-vectorize-2026-11-21.md](hindsight-vectorize-2026-11-21.md).
  The `bd prime` text would have to reach a thread through Outlore's own starting context.
  Whether Outlore's Codex launch loads `.codex/hooks.json` was not checked.
- **Telemetry.** Threads would run `bd` with default-on usage metrics sent to a third-party host, against Outlore's requirement that nothing leaves the computer "except what a harness, provider, or connected service needs for the work" (`requirements.md`, "Local data").
  Outlore would need to set `BD_DISABLE_METRICS=1` and `DO_NOT_TRACK=1` in the thread's environment.
  The queue is written to `~/.beads/eventsData`, outside a sandboxed thread's writable folder (not tested).
- **Worktrees and parallel errands.** All worktrees of a repository share one `.beads` workspace (`docs/reference/worktrees.md`), and embedded mode has a single file-locked writer (`docs/core-concepts/index.md`); several errands in own copies (`.worktrees/<name>`) would therefore contend for it, so server mode would be needed (inferred from the two documents, not tried).
- **Sync needs approval.** `bd dolt push` publishes `refs/dolt/data` to the git remote, which is a push the owner would approve, and `bd init` edits `AGENTS.md` by default, a document this repository governs by hand.
- **Secrets.** Beads' own secret fix shows the config table, which replicates on push, can end up holding credentials; Outlore's Vault rule says connector secrets reach no conversation, journal, lore or log (`requirements.md`).

**(c) Beads as Outlore's own store for quests, errands or lore.** No.
Outlore keeps its state in its own SQLite store, where one module owns each table's writes (`documentation/architecture.md`, "Lore store", "Thread lifecycle"), and Beads' Dolt-backed Go engine would be a second database and runtime to ship, with a data model its roadmap says is being reshaped.

**(d) A reference for Outlore's unbuilt `workflow-running` and for ordering errands.** This is where Beads is useful.
Formula steps with `needs`, `vars`, human steps, gates, and "distill an ad-hoc epic into a template" map straight onto "running a workflow, each step as a thread" (`outline.md`).

## Ideas worth adopting

Ranked by how directly they meet something already in the backlog or the capability map.
None is adopted by this note; each needs the owner's choice and, for 2 to 4, a specification first.

1. **Say how much was left out when injecting memory.** `bd prime` caps entries "at whole-memory boundaries", always emits at least one, and prints how many were elided and where to browse them.
   This matches candidate 1 of the backlog's leaner-preamble item, "list realm lore in the turn preamble as a one-line index, as global lore already is": add an explicit "N more entries, read with `search_intel`" line, so a thread knows the list was cut.
2. **Errand dependencies and a ready frontier.** Typed `blocks`/`waits-for` edges plus a computed "ready" set would let a thread or Chronicler open five errands with an order and have each wake when its blockers finish.
   Beads also shows the cost: its stored `IsBlocked` flag needs `bd recompute-blocked` repair, so Outlore should compute readiness from the edges when read rather than store it.
3. **Gates as one waiting primitive.** A thread waiting for "PR merged", "CI green", "this time" or "the owner" is a single idea in Beads; Outlore has the owner and schedule cases and lists webhook and event triggers as not built.
   A gate on a merged pull request would need the same `gh` dependency Beads uses (`gh pr view`).
4. **Templates from a finished errand tree.** `bd mol distill` (turn what worked into a reusable formula) is a cleaner idea than hand-written workflow files for Outlore's `workflow-running`, and the parameter and human-step vocabulary of formulas is a reasonable starting list.
5. **A replay feed that fails loudly.** If Outlore's paired devices or the web client resume from a position, the events-journal rule "a checkpoint below the retained window is an error, never a smaller answer" is worth comparing with how Outlore's refresh handles a gap.
   Not judged here because Outlore's change-announcement path was not re-read for this note.
6. **Managed instruction sections with `--check` and `--remove`.** Beads' marker-bounded sections in `AGENTS.md` and `CLAUDE.md`, plus a divergence reminder when the two files differ (`cmd/bd/prime_divergence.go` exists), are a model for any future Outlore step that edits a project's agent instructions; no such step exists now.

Not worth taking: hash IDs (one host, no concurrent minters), lossy compaction (Outlore's journal-compression idea keeps raw entries, the safer choice), mail delegation, and Dolt federation (Outlore has agreed a different multiplayer design).

## Risks and reasons not to adopt

- **Default-on telemetry** to a third-party host, against Outlore's local-data requirement; manageable by environment variables, but an easy thing to miss.
- **Churn.** 115 releases in about 13 months, a release candidate every few days at the time of reading, one-way schema migrations, experimental planes, and a roadmap that reshapes the graph model; pinning an exact `bd` version would be mandatory, as its own HTTP docs advise.
- **Overlap with Outlore's own surfaces.** Lore, journal, handoffs, approvals and messaging already exist and are richer in scope and fading; a second memory plane (`bd remember`) would split what a thread believes, the same objection recorded for Hindsight.
- **Wiring.** Outlore's harness launches ignore project hooks and external MCP configuration is not built, so Beads' main integration path (hooks that prime context) does not run inside Outlore threads.
- **A new binary and database** in every realm that uses it, with Dolt as a pinned dependency and a writer lock that parallel worktrees would hit.
- **Quality signal is thin.** Most recent commits come from a bot and the open-issue and pull-request count is 1,829; the shallow clone and counts say nothing about defect rates, and GitHub issues were not read.

## Recommendation: borrow ideas, do not adopt or integrate

- **Do not** ship Beads as a connector or a dependency, and do not make it Outlore's store.
  The real fit of the product is a single agent's or small team's coding task list in a repository, which Outlore's threads already reach through a shell if the owner wants it.
- **Do** take the six ideas above into the backlog as candidates, starting with the elision line (idea 1), which is small, and with errand dependencies, gates and templates (ideas 2 to 4) as input to a future `workflow-running` specification.
- **Optional, the owner's call and separate from the product:** trying `bd` in this repository's own development to replace `backlog.md` and part of `work-in-progress.md` is a process question.
  If tried at all, run it in a throwaway clone with `--stealth`, `--skip-agents` and metrics off, and compare with the handoff convention after a few batches.
