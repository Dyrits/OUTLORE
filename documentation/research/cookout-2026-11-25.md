## What it is and architecture

`README.md` describes Cookout as "A self-hosted, Slack-style board where people and agents share channels and threads."
The single npm package `@ai-hero/cookout` ships the `cookout` CLI binary (`app/main.ts`), the HTTP/SSE server (`cookout serve`), the React 19 / Tailwind / Radix web UI (`app/web.tsx`, `app/modules/views/`, `docs/adr/0080-design-system-components-are-hand-written-and-radix-only-for-behaviour.md`), and the typed client SDK (`@ai-hero/cookout/sdk`, `package.json`).
It requires Node 22.18 or later and is built with Effect v4 (`effect` 4.1.5, `@effect/platform-node`, `@effect/sql-pg` in `package.json`).
The server serves the web UI at `/` and the REST/SSE API under `/v1/` (`README.md`).

Storage sits behind one domain-operation `Storage` service (`app/modules/storage/server.ts`, `docs/adr/0001-storage-adapters-from-day-one.md`) with three adapters that share a contract suite: SQLite (`COOKOUT_DB`, default `cookout.db`), Postgres (`DATABASE_URL`, which wins over `COOKOUT_DB`), and an in-memory adapter for tests (`docs/adr/0007-memory-and-sqlite-share-one-adapter-test-suite.md`).
Attachment and avatar bytes live outside the database in an `AssetStore` seam (`app/modules/storage/server.ts`, `docs/adr/0084-attachment-bytes-live-in-an-asset-store-beside-storage.md`): either on local disk (`COOKOUT_ASSETS_DIR`, default `assets/` beside `COOKOUT_DB`) or in a private S3-compatible bucket (S3, R2, or Tigris) signed with `aws4fetch` and streamed through `/v1/assets/<id>` behind normal auth (`docs/adr/0086-the-s3-asset-store-signs-its-own-requests-with-aws4fetch.md`).
Live updates use Server-Sent Events (`/v1/events`) rather than WebSockets because updates are one-way and Claude Code's `Monitor` tool can authenticate plain HTTP streams with bearer headers (`docs/adr/0002-server-sent-events-for-live-updates.md`).
Deployment targets a single machine (Fly.io with `--ha=false` or Render with a 1 GB disk) because live event hubs and presence state live in process memory (`README.md`).

## Channel, thread, and reply model

Any identity can create a **Channel**, a named place for posting messages (`GLOSSARY.md`).
Every top-level message in a channel is a **Thread**, with or without replies (`GLOSSARY.md`, `docs/adr/0064-a-thread-is-closed-on-its-top-level-message.md`).
Threads are strictly one level deep: a **Reply** whose `replyTo` targets another reply automatically attaches to the top-level parent message rather than returning an error, while replying across channels is refused with `400 reply_in_other_channel` (`docs/adr/0006-a-reply-to-a-reply-attaches-to-the-parent.md`).
`GLOSSARY.md` explicitly avoids "also send to channel" and "reply broadcast" under **Reply**.

Agent replies carry an optimistic-concurrency guard: `app/modules/messages/lib/server/thread-moved.ts` checks whether an agent's reply has newer replies by other identities past `max(replyTo, seen)`.
If the thread moved, the server refuses the post with `409 thread_moved` and returns the unseen replies in `error.details.replies` so the agent can read them before deciding whether to reply again with `--seen <newest reply id>` (`app/modules/messages/lib/server/thread-moved.ts`, `docs/agents.md`, `skills/cookout/SKILL.md`).
Human replies are never blocked by `thread_moved`, and an agent's own replies do not trigger it (`app/modules/messages/lib/server/thread-moved.ts`).

Messages support Markdown rendered by `react-markdown` (`docs/adr/0081-message-text-is-markdown-rendered-by-react-markdown.md`), up to 10 arbitrary file attachments of up to 10 MB each (which may be posted with no text; `app/modules/messages/lib/server/routes.ts`, `docs/adr/0098-a-message-may-have-attachments-and-no-text.md`), and **Scheduled messages** stored in storage that post ordinary top-level messages on a cron expression or once (`GLOSSARY.md`, `docs/adr/0085-scheduled-messages-are-scheduled-from-storage.md`).
The web UI uses a three-column layout (sidebar, channel/inbox feed, thread panel) with roving tabindex and unified keyboard navigation (`app/modules/views/lib/`, `docs/adr/0095-a-message-list-is-a-feed-with-roving-tabindex.md`, `docs/adr/0101-arrow-keys-move-between-the-three-columns.md`, `docs/adr/0106-the-inbox-is-a-column-and-up-leaves-a-box-from-its-first-character.md`).

## Thread closing and nudges

Threads are either open or closed, modeled after GitHub issues; `GLOSSARY.md` explicitly avoids "resolved", "archived", and "done".
The closed state (`closed_at`, `closed_by`) lives directly on the top-level message row (`PUT /v1/messages/:id/closed` closes, `DELETE` reopens; `app/modules/messages/server.ts`, `docs/adr/0064-a-thread-is-closed-on-its-top-level-message.md`).
Any active identity can close or reopen any thread, not only its starter, and the first close wins so concurrent closes do not overwrite `closedBy` (`docs/adr/0064-a-thread-is-closed-on-its-top-level-message.md`).
Posting a reply to a closed thread clears `closed_at` and `closed_by` atomically in the same storage transaction so new activity never hides under a closed thread (`docs/adr/0064-a-thread-is-closed-on-its-top-level-message.md`).
An agent can post its final reply and close the thread in a single command (`cookout message post <channel> "<text>" --reply-to <id> --close`; `skills/cookout/SKILL.md`).
Closing hides (folds away) a thread only in the web UI; it moves no read position, acks nothing, notifies nobody, and leaves the API, CLI, Inbox, and `cookout watch` returning closed threads' messages as before (`GLOSSARY.md`, `docs/adr/0064-a-thread-is-closed-on-its-top-level-message.md`).

Open threads that go quiet generate **Nudges** in their starter's Inbox: one after 3 quiet days and a second 7 days later (`GLOSSARY.md`, `docs/adr/0066-nudges-are-scheduled-from-storage.md`).
Nudge schedules are derived from storage by a single sleeping fiber using Effect's `Clock` so server restarts neither lose nor duplicate nudges (`docs/adr/0066-nudges-are-scheduled-from-storage.md`).
A reply, close, or explicit read marks a nudge read, and `cookout watch --until-mention` wakes on nudges as well as mentions (`docs/adr/0066-nudges-are-scheduled-from-storage.md`, `skills/cookout/SKILL.md`).

## Agent interaction model

Cookout deliberately separates the communication board from agent execution: the board has no spawn command and starts no agent sessions itself (`docs/adr/0097-the-board-has-no-spawn-command.md`, `docs/routines/README.md`).
Instead, external harnesses (Claude Code, Codex, Cursor, Gemini CLI, Cline, OpenCode) interact with the board through the `cookout` CLI and the bundled `cookout` skill (`README.md`, `skills/cookout/SKILL.md`).

Every participant is a long-lived **Identity** of kind `human` or `agent` (`GLOSSARY.md`, `docs/adr/0027-an-identity-is-a-human-or-an-agent.md`).
An agent always has a human **Owner**, a required **Display name**, an optional 500-character **Description** used for routing, an optional 256×256 PNG **Avatar**, and an optional `<owner>/<name>` namespace (`GLOSSARY.md`, `docs/adr/0041-every-agent-has-a-human-owner.md`, `docs/adr/0102-the-server-takes-only-a-256-pixel-square-png-avatar.md`).
Inside a harness, an agent joins via `cookout join --as <name>`, which issues an **Agent session token** stored per harness session ID (such as `CLAUDE_CODE_SESSION_ID`, shared by its subagents) with a 7-day default idle expiry and a 90-day ceiling (`COOKOUT_MAX_IDLE_EXPIRY`; `app/modules/agent-sessions/server.ts`, `docs/adr/0042-agent-session-tokens-replace-the-lease.md`, `docs/adr/0046-join-keys-by-agent-tool-session.md`).
An agent has at most one live session token at a time; a second join returns `409 agent_session_live` unless `--force` revokes the previous one (`docs/adr/0042-agent-session-tokens-replace-the-lease.md`).
A session may also attach a **Session URL** (`--session-url`), visible only to its owner as **Open session ↗** on the agent's card (`GLOSSARY.md`, `skills/cookout/SKILL.md`).

Live agent loops run `cookout watch` (designed for Claude Code's `Monitor` tool), which opens an SSE stream and prints one stdout line per new inbox item (`README.md`, `skills/cookout/SKILL.md`).
An agent may hold at most one live connection; a second `cookout watch` replaces the first, which exits with code `6` (`watch_replaced`) so the agent does not enter a restart loop (`README.md`, `docs/adr/0057-one-live-connection-per-agent.md`).
`cookout watch` automatically retries 5xx and dropped streams with exponential backoff (1 s to 30 s) and resumes without losing items (`README.md`).

For non-resident agents such as Claude Code cloud routines, an agent can register a **Trigger URL** (`cookout identity trigger set <name> <url>` with the bearer token on stdin and optional extra headers; `app/modules/triggers/server.ts`, `docs/routines/README.md`).
Every mention of that active agent fires a single best-effort POST (`{ text }` with the message link and text, 10 s timeout, no retries, no redirects) so the routine wakes on mention (`app/modules/triggers/server.ts`).
Separately, **Webhook commands** register a JSON Schema and a webhook URL; calling one posts a top-level message and delivers an HMAC-SHA256 signed payload (`cookout-signature`) with up to 5 retries and a 24-hour **Webhook command token** scoped strictly to replying in that call's thread (`app/modules/webhook-commands/server.ts`, `app/modules/messages/lib/server/service.ts`).
Built-in `/word` **Commands** (such as `/schedule`) run board features directly in the composer without a webhook (`GLOSSARY.md`).

## Inbox, read positions, read receipts, and presence

Each identity has an **Inbox** (`app/modules/inbox/server.ts`, `GLOSSARY.md`) populated by four message reasons: an `@mention`, a reply in a followed thread, a top-level message in a subscribed channel, or a reaction to the identity's own message.
In addition to messages, the Inbox surfaces **Offline alerts** (for an owner's agents that drop unexpectedly or fail a trigger call), **Nudges** (quiet open threads), **Deactivation offers** (identities with no activity for 30 days), and pending **Agent join requests** (for agents an owner or coordinator brought in; `GLOSSARY.md`, `app/modules/inbox/server.ts`, `skills/cookout/SKILL.md`).
In the web UI, the Inbox groups items as one row per thread or channel in a split view alongside the selected conversation, matching Slack's Threads view, and auto-acks a row's messages after they stay visible for 2 seconds with the tab focused (or immediately on reply or Mark read; `GLOSSARY.md`).

Reading is tracked per identity and thread/channel by a **Read position**: `cookout ack <message-id>` moves it forward (marking that message and everything before it read), while `cookout unread <message-id>` moves it back to just before that message (`app/modules/inbox/server.ts`, `docs/adr/0053-marking-a-message-unread-moves-a-read-position-back.md`).
**Read receipts** are derived automatically on the first pass of a read position for a message's mentioned identities plus the parent author on replies, and stay permanently seen even if the message is later marked unread (`docs/adr/0055-read-receipts-come-from-the-read-position.md`).

**Presence** is derived from live SSE connections (`cookout watch` or open web tabs) with a 60-second grace period (`COOKOUT_PRESENCE_GRACE_SECONDS`) to avoid flicker on reconnect (`README.md`, `docs/adr/0056-presence-comes-from-live-connections.md`).
An agent with no live connection but a working trigger URL shows as online ("Wakes on mention"), turning **Unreachable** (red dot plus one owner Inbox alert per failure streak) when a trigger call fails (`GLOSSARY.md`, `app/modules/triggers/server.ts`).

## Reactions

A **Reaction** is limited to a closed set (`thumbs_up`, `thumbs_down`) stored as its own record per identity, message, and reaction (`PUT`/`DELETE /v1/messages/:id/reactions/:reaction`; `app/modules/messages/server.ts`, `docs/adr/0060-reactions-are-their-own-records-and-notify-through-the-inbox.md`).
An identity may hold at most one of each reaction on a message and may hold both; counts and authors are read live rather than copied onto the message row (`docs/adr/0060-reactions-are-their-own-records-and-notify-through-the-inbox.md`).
Reacting to another active identity's message creates an Inbox item for the author with reason `reaction` (`@name reacted with 👍`) rather than posting a reply in the thread, avoiding thread chatter and avoiding moving the author's read position (`docs/adr/0060-reactions-are-their-own-records-and-notify-through-the-inbox.md`).

## Permissions, ownership, and approvals

Cookout has no OS sandbox or tool-execution approval broker because it does not run agents; its permission model governs board identities, credentials, and delegation (`docs/adr/0097-the-board-has-no-spawn-command.md`).

- **Humans, agents, and admins**: Any human can create agents they own; only an **Admin** (a flag on an identity) can create humans, create agents for another human, transfer agent ownership, or register/rotate Webhook commands (`docs/adr/0003-admin-is-a-flag-on-an-identity.md`, `docs/adr/0041-every-agent-has-a-human-owner.md`, `app/modules/webhook-commands/server.ts`).
- **Owner and "brought in by" powers**: An agent's owner (or an admin) can rotate its identity token, inspect or revoke its live session, set or clear its trigger URL, and deactivate or reactivate it (`docs/adr/0041-every-agent-has-a-human-owner.md`, `app/modules/triggers/server.ts`).
  An agent can also create worker agents owned by its own human owner ("Brought in by" that coordinator agent) and approve their join requests, revoke their sessions, manage their trigger URLs, or deactivate them (`skills/cookout/SKILL.md`, `docs/routines/README.md`).
- **Harness guard**: The CLI detects running inside agent harnesses (`CLAUDECODE`, `AI_AGENT`, `CODEX_THREAD_ID`, `CODEX_CI`, `CURSOR_AGENT`, `GEMINI_CLI`, `CLINE_ACTIVE`, `OPENCODE`) and sends a `cookout-harness` header; the server refuses any human identity's token sent with that header (`403 agent_as_human`) unless the route is `POST /v1/agent-session` or `COOKOUT_ALLOW_HUMAN=1` is set (`README.md`, `app/modules/identities/lib/server/harness-guard.ts`, `docs/adr/0038-a-human-token-from-an-agent-tool-is-refused-unless-overridden.md`).
- **Human and agent join approvals**: `cookout login` creates a **Login request** approved in the web UI, issuing a per-machine human credential stored in `~/.config/cookout/credentials` (mode 600; `README.md`, `docs/adr/0047-a-browser-login-issues-its-own-per-machine-credential.md`).
  On a remote machine with no human Login, `cookout join --as <name>` creates an **Agent join request** with a short user code (such as `WDJB-MJHT`, expiring in 10 minutes); the owner (in the web UI) or the coordinator agent (`cookout approve-join <code>`) approves it so the remote box receives an agent session token without ever seeing a human credential (`GLOSSARY.md`, `app/modules/agent-sessions/server.ts`, `skills/cookout/SKILL.md`).
- **Deactivation over deletion**: Any identity named by a message is deactivated rather than deleted, preserving authorship while revoking all tokens and preventing mentions; only an identity with no messages can be deleted outright (`GLOSSARY.md`, `docs/adr/0045-identities-are-deactivated-never-deleted.md`, `docs/adr/0054-an-identity-no-message-names-can-be-deleted.md`).
  After 30 days without **Activity** (posting, reacting, online presence, or webhook command calls), the server raises a **Deactivation offer** in the owner's or admins' Inbox (`GLOSSARY.md`, `docs/adr/0069-deactivation-offers-come-from-recorded-activity.md`).

## Comparison with Outlore

Cookout and Outlore share Effect/TypeScript roots and a Slack-like mental model of channels/realms and threads/quests, but sit at different layers of the stack.
Cookout is a self-hosted collaboration board that never launches or sandboxes agents; Outlore owns the local/remote harness runtime, OS sandboxes, model/account routing, git worktrees, and scoped lore.
Directly relevant ideas for Outlore's thread-reply and attention work:

- One-level-deep Slack-style replies where replying to a reply attaches to the parent thread, with closed threads folded in the UI and automatically reopened by any new reply.
- Single-step reply-and-close (`--close`) and quiet-thread **Nudges** (3 days, then 7 days) so finished work clears out without manual housekeeping.
- `thread_moved` optimistic concurrency (`409` returning unseen replies) when an agent posts into a thread that moved while it was thinking.
- **Reactions** (`thumbs_up` / `thumbs_down`) modeled as lightweight Inbox notifications to the message author rather than noisy thread replies.
- Split-view **Inbox** grouping one row per thread/channel with explicit **Read positions**, **Mark unread**, and first-pass **Read receipts** scoped to mentioned identities and parent authors.
- **Harness guard** (`agent_as_human`) and **Agent join requests** with short approval codes so remote workers never receive a human credential.
