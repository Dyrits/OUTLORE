# Apple Automation after an Outlore restart · 2026-11-19

The macOS SDK provides a prompt-free query for the current Apple Events sender. The current Outlore package has no verified way to issue that query under the same authorization as its vendored Apple tools. Keep the explicit host check until a packaged sender can be tested. A past grant can explain the last known state in the UI, but it cannot enable tools after restart.

## What the operating system exposes

- `AEDeterminePermissionToAutomateTarget` with `askUserIfNeeded=false` checks the calling application and a running target without sending an Apple event or showing consent UI. The SDK distinguishes success, denial, consent needed and target not running (`procNotFound`). A closed target therefore gives no current answer about its grant. Source: installed macOS SDK, `CoreServices.framework/Frameworks/AE.framework/Headers/AppleEvents.h`, around lines 557–615. Apple also demonstrates this API at 37:10 in [Advances in macOS Security](https://developer.apple.com/videos/play/wwdc2019/701/).
- The same header documents `kAEDoNotPromptForUserConsent` for the actual Apple event send. The sender can decline to prompt even if consent changes after a successful preflight. The installed `osascript(1)` manual exposes no flag for that send option. The `-s` flags control result and error formatting.
- Apple distinguishes the immediate launcher from responsible code and describes cases where TCC cannot follow a helper to its enclosing app. A result from a new helper is insufficient to establish the packaged connector's authorization. Apple also documents that ad hoc designated requirements are specific to the signed version. Continuity across rebuilds and updates needs separate evidence from continuity across a restart of one build. [Apple launch environment documentation](https://developer.apple.com/documentation/security/applying-launch-environment-and-library-constraints), [Apple DTS on TCC responsibility](https://developer.apple.com/forums/thread/702907), [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements/).

## Outlore's packaged sender

Read at `eeaa5207`. `apps/desktop/src/main.ts:60` forks the service as an Electron utility process. `packages/service/src/connectors/backends/stdioMcp.ts:33` then starts system Node with the vendored `mcp-icloud.cjs`. The vendor starts `osascript` for both AppleScript and JavaScript for Automation (`packages/service/vendor/mcp-icloud.cjs:86128` and `:86153`). The host's permission action uses a read tool over that same backend (`packages/service/src/connectors/applePermission.ts`) and can prompt. Messages is a separate path. Its `list-chats` probe calls `imsg`, and the vendor reports Full Disk Access errors from that binary (`mcp-icloud.cjs:101027`). An Automation result cannot establish its access.

`apps/desktop/electron-builder.yml` bundles the vendor and uses ad hoc signing with the hardened runtime off. The package configuration does not declare an Apple Events usage description. Apple documents this key for an app that sends Apple events. Verify the generated bundle's purpose string and applicable entitlements for the actual sender before relying on consent in an installed build. [Apple usage description documentation](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription), [Apple Events entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.automation.apple-events).

The worktree had no packaged Outlore build, and Spotlight returned no installed bundle with identifier `app.outlore.desktop`. A terminal `osascript -l JavaScript` experiment found that `ObjC.import("CoreServices")` exposes the preflight function. Passing `NSAppleEventDescriptor.aeDesc` from a bundle-identifier descriptor directly to it failed with `Ref has incompatible type (-2700)`. The only possible call in that experiment used `false` for prompting. This shows that the direct bridge call needs additional work and provides no result for the packaged sender.

## Viable choices

1. **Keep the current explicit host check.** It exercises the real sender, handles stopped targets through the normal read path, and preserves the host-only consent boundary. A paired device cannot restore Apple tools after a host restart.
2. **Prototype preflight in the vendor's `osascript` path.** If the descriptor can be passed successfully, run the fixed prompt-free check from the same packaged process chain and compare it against actual sends. This can only restore access for running targets. The unmodified sender also lacks a documented way to keep later sends silent if authorization changes between check and use.
3. **Give the connector a controlled Apple Events sender.** Have the same packaged sender preflight and send with the SDK's no-prompt send flag for automatic and remote use. Keep prompting as a separate host-only operation. This requires a native sender and adaptation of the vendor's AppleScript and JavaScript execution, plus a separate check for Messages. Test whether both scripting engines route every protected send through the controlled sender before using it. Compare clean consent-needed, granted then restarted, explicitly denied, revoked, closed-target and grant-restored cases on a disposable packaged Mac setup. Verify the prompt attribution and that automatic paths show no UI. Assess signing across releases separately.
